# 第 14 章 插曲：内存 API

> 英文原题：*Interlude: Memory API*

在这篇插曲里，我们来聊聊 UNIX 系统中的内存分配接口。这里提供的接口相当简单，所以本章又短又直接[^1]。我们要解决的核心问题是：

!!! danger "问题核心"
    **如何分配和管理内存？**

    在 UNIX/C 程序中，理解如何分配和管理内存，是构建健壮、可靠软件的关键。常用的接口有哪些？又该避免哪些错误？

## 14.1 内存的类型

运行一个 C 程序时，会用到两类被分配的内存。第一类叫**栈内存(stack memory)**，它的分配和释放由编译器替你（也就是程序员）隐式管理；正因如此，它有时也叫**自动内存(automatic memory)**。

在 C 里，在栈上声明内存很容易。比方说，你在某个函数 `func()` 里需要一块空间来放一个名为 `x` 的整数。要声明这么一块内存，只要这么写就行：

```c
void func() {
    int x; // 在栈上声明一个整数
    ...
}
```

剩下的交给编译器：当你调用 `func()` 时，它会负责在栈上腾出空间。等你从函数返回，编译器又替你释放掉这块内存；所以说，如果你想让某些信息活过这次函数调用，最好别把它留在栈上。

正是这种"需要长寿的内存"的诉求，把我们引向了第二类内存——**堆内存(heap memory)**，它的分配和释放全都得由你这位程序员显式打理。责任重大，这没得说！它也肯定是无数 bug 的源头。不过只要你小心、上心，就能正确使用这些接口，不会惹太多麻烦。下面是在堆上分配一个整数的例子：

```c
void func() {
    int *x = (int *) malloc(sizeof(int));
    ...
}
```

关于这一小段代码，有几点要说明。首先，你可能注意到，这一行同时发生了栈分配和堆分配：编译器一看到你声明那个指针（`int *x`），就知道要为一个指向整数的指针腾出位置；随后程序调用 `malloc()`，向堆申请一块放整数的空间；这个例程返回该整数的地址（成功时如此，失败则返回 `NULL`），这个地址再被存到栈上，供程序使用。

由于堆内存的显式性质，也由于它的用法更加五花八门，它对使用者和系统双方都提出了更多挑战。因此，它是我们接下来讨论的重点。

## 14.2 `malloc()` 调用

`malloc()` 调用相当简单：你传给它一个大小，向堆申请一些空间；它要么成功，回给你一个指向新分配空间的指针，要么失败，返回 `NULL`[^2]。

手册页会告诉你要用 `malloc` 该做些什么；在命令行里敲 `man malloc`，你会看到：

```c
#include <stdlib.h>
...
void *malloc(size_t size);
```

从这些信息你能看出，用 `malloc` 只需要包含头文件 `stdlib.h`。其实你压根儿不包含也行，因为所有 C 程序默认都会链接的 C 标准库，里面就有 `malloc()` 的代码；加这个头文件只不过让编译器检查你有没有正确调用 `malloc()`（比如传的参数个数对不对、类型对不对）。

`malloc()` 接受的唯一参数类型是 `size_t`，它描述的就是你需要多少字节。不过大多数程序员不会在这儿直接敲一个数字（比如 `10`）；真这么干，会被认为掉价。大家用的是各种例程和宏。比如，要为双精度浮点值分配空间，你只要这么写：

```c
double *d = (double *) malloc(sizeof(double));
```

!!! tip "提示：拿不准就动手试试"
    如果你不确定某个例程或运算符到底怎么表现，那没有任何东西比得上亲自试一把、确认它是不是如你所愿。读手册页或其他文档固然有用，但真正要紧的是它在实践中怎么工作。写点代码测一测！这无疑是确保代码如你所愿的最佳办法。事实上，我们当年正是这么干，才核实了自己关于 `sizeof()` 的说法确实没错！

哇，好多"double"！这次 `malloc()` 调用用 `sizeof()` 运算符来申请恰当大小的空间；在 C 里，它一般被看作编译期运算符，意思是实际大小在编译时已知，于是会有一个数字（这里对 `double` 来说就是 8）被替换成 `malloc()` 的参数。也正因如此，`sizeof()` 被正确地视为运算符，而不是函数调用（函数调用会在运行时发生）。

你也可以把变量名（不只是类型名）传给 `sizeof()`，但有些情况下你可能得不到想要的结果，所以要当心。来看下面这段代码：

```c
int *x = malloc(10 * sizeof(int));
printf("%d\n", sizeof(x));
```

第一行里，我们声明了一块能放 10 个整数的数组空间，这挺好挺美。可当我们在下一行用 `sizeof()` 时，它返回的却是个小值，比如 4（32 位机器上）或 8（64 位机器上）。原因在于，这里 `sizeof()` 以为我们只是在问一个指向整数的指针有多大，而不是我们动态分配了多少内存。不过，有时 `sizeof()` 又确实如你所料：

```c
int x[10];
printf("%d\n", sizeof(x));
```

这种情况下，静态信息足够多，编译器知道分配了 40 个字节。

另一个要当心的地方是字符串。为字符串声明空间时，用这个惯用法：`malloc(strlen(s) + 1)`，它用函数 `strlen()` 求出字符串长度，再加 1，好给字符串末尾的结束字符留出位置。这里用 `sizeof()` 可能会惹麻烦。

你可能还注意到，`malloc()` 返回的是 `void` 类型的指针。这不过是 C 里回传一个地址、让程序员自己决定怎么用的方式罢了。程序员再进一步帮忙的方式叫**类型转换(cast)**；在上面那个例子里，程序员把 `malloc()` 的返回类型转换成了指向 `double` 的指针。类型转换其实什么实质作用都没有，只是告诉编译器以及别的可能读你代码的程序员："行，我知道自己在干嘛。" 把 `malloc()` 的结果转一下型，无非是给点安慰；正确性上并不需要这个转换。

## 14.3 `free()` 调用

结果你会发现，分配内存是这道题里简单的部分；知道何时、如何、甚至到底该不该释放内存，才是难的部分。要释放不再使用的堆内存，程序员只需调用 `free()`：

```c
int *x = malloc(10 * sizeof(int));
...
free(x);
```

这个例程只接受一个参数，即 `malloc()` 返回的指针。于是你会注意到，所分配区域的大小并不是由用户传进来的，必须由内存分配库自己记着。

## 14.4 常见错误

使用 `malloc()` 和 `free()` 时，会冒出许多常见错误。下面这些，是我们在教本科操作系统课时一遍又一遍见到的。这些例子全都能编译、能运行，编译器连哼都不哼一声；虽说编译是构建正确 C 程序的必要步骤，但远远不够——这一点你早晚会（常常是狠狠地）领教。

事实上，正确的内存管理一直是个大难题，以至于许多较新的语言都支持自动内存管理。在那类语言里，你调用类似 `malloc()` 的东西分配内存（通常是 `new` 或类似的写法，用来分配一个新对象），却从不需要调用什么来释放空间；取而代之的是一个**垃圾回收器(garbage collector)**，它会跑起来，弄清楚你不再引用的内存有哪些，然后替你释放掉。

### 忘记分配内存

许多例程都期望你调用它们之前，内存已经分配好了。比如，例程 `strcpy(dst, src)` 把一个字符串从源指针复制到目标指针。可你要是不留神，就可能干出这种事：

```c
char *src = "hello";
char *dst;         // 糟糕！没有分配
strcpy(dst, src);  // 段错误，然后挂掉
```

运行这段代码，多半会引发一次**段错误(segmentation fault)**[^3]；这词儿是对"你在内存上搞砸了，你这糊涂程序员，我生气了"的一种花哨说法。

!!! tip "提示：编译通过或跑通了 ≠ 它是对的"
    一个程序编译通过（！），甚至一次或多次跑对了，并不意味着它就是对的。可能有一堆巧合把你送到"它没问题"的错觉里，可一旦某些东西变了，它立马就崩。学生常见的反应是嚷嚷（或怒吼）："可是刚才还好好的！"然后去怪编译器、操作系统、硬件，甚至（我们敢说吗）老师。但问题通常恰恰就在你以为它该在的地方——你的代码里。先把活干起来，调试它，再去怪别的组件。

这种情况下，正确的代码也许该长这样：

```c
char *src = "hello";
char *dst = (char *) malloc(strlen(src) + 1);
strcpy(dst, src); // 正常工作
```

或者，你可以用 `strdup()`，让日子更省心。详情请读 `strdup` 的手册页。

### 分配的内存不够

一个相关的错误是分配的内存不够，有时叫**缓冲区溢出(buffer overflow)**。在上面的例子里，一个常见错误是为目标缓冲区留出"差不多够"的空间：

```c
char *src = "hello";
char *dst = (char *) malloc(strlen(src)); // 太小了！
strcpy(dst, src); // 正常工作
```

说来也怪，取决于 `malloc` 怎么实现以及许多别的细节，这个程序往往还能看似正确地跑起来。有些情况下，字符串复制执行时会写到所分配空间末尾之外的一个字节，但有时这无伤大雅，也许只是覆盖了一个已经不再使用的变量。有些情况下，这类溢出可能危害极大，事实上它们正是系统里许多安全漏洞的根源 [W06]。还有些情况下，`malloc` 库本来就多分配了一点空间，于是你的程序其实没涂改到别的变量的值，跑得挺顺。更有一些情况下，程序真的会出错、崩溃。于是我们又学到一条宝贵的教训：它曾经跑对过一次，不代表它就是对的。

### 忘记初始化已分配的内存

这个错误是：你正确地调用了 `malloc()`，却忘了往新分配的数据类型里填值。别这么干！要是真忘了，程序迟早会撞上一次**未初始化读(uninitialized read)**，从堆里读到某个值不明的数据。谁知道里面是什么玩意儿？运气好的话，某个值让程序照样能跑（比如 0）。运气不好，就是一个随机又有害的东西。

### 忘记释放内存

另一个常见错误叫**内存泄漏(memory leak)**，发生在你忘了释放内存的时候。在长时间运行的应用程序或系统（比如操作系统本身）里，这是个天大的问题，因为缓慢泄漏的内存最终会让人把内存耗光，到那时就得重启了。所以总的来说，当你用完一块内存，就该确保释放它。注意，用带垃圾回收的语言也帮不上忙：只要你手里还留着一块内存的引用，垃圾回收器就永远不会释放它，因此内存泄漏即便在更现代的语言里也依旧是个问题。

有些情况下，不调用 `free()` 似乎也说得过去。比如你的程序是个短命鬼，马上就要退出；这时进程一死，操作系统会清理掉它所有已分配的页，因此严格来说并不会发生内存泄漏。这当然"管用"（见下面那则边栏），但恐怕是个不该养成的坏习惯，选这种策略时要警惕。从长远看，作为程序员的目标之一就是养成好习惯；其中一个习惯，就是搞明白自己在如何管理内存，并且（在 C 这类语言里）释放掉你分配的那些块。哪怕你可以侥幸不这么做，养成"显式分配的每一个字节都去释放"的习惯，多半是好事。

### 还用着就提前释放

有时程序会在还没用完某块内存时就把它释放了；这种错误叫**悬空指针(dangling pointer)**，你猜得到，它同样不是什么好事。随后对它的使用可能让程序崩溃，或者覆盖掉有效内存（比如你调用了 `free()`，接着又调用 `malloc()` 分配了别的东西，而后者恰好回收了那块被错误释放的内存）。

### 重复释放内存

程序有时还会把同一块内存释放不止一次；这叫做**重复释放(double free)**。这么干的结果是未定义的。你可以想象，内存分配库可能会被搞糊涂，干出各种莫名其妙的事；崩溃是常见的下场。

### 错误地调用 `free()`

我们要讨论的最后一个问题，是错误地调用 `free()`。毕竟，`free()` 只希望你传给它一个之前从 `malloc()` 拿到的指针。当你传进去别的值时，坏事就可能（而且确实会）发生。因此，这类非法释放很危险，当然也该避免。

!!! note "边栏：进程退出后为什么内存没有泄漏"
    你写一个短命程序时，也许会用 `malloc()` 分配一些空间。程序跑起来，眼看就要结束了：需要在退出前把 `free()` 挨个调一遍吗？虽然不调似乎不太对，但并不会有任何真正意义上的内存"丢失"。原因很简单：系统里其实有两层内存管理。

    第一层内存管理由操作系统负责，它把内存发给运行中的进程，又在进程退出（或以别的方式死掉）时收回。第二层管理发生在每个进程内部，比如你调用 `malloc()` 和 `free()` 时的堆里。哪怕你没调用 `free()`（也就是在堆里泄漏了内存），当程序运行结束，操作系统也会收回该进程的全部内存（包括代码、栈，以及这里相关的堆所占的那些页）。无论你地址空间里的堆处于什么状态，进程一死，操作系统就收回所有这些页，从而确保即使你没释放，也没有内存真正丢失。

    因此，对短命程序来说，泄漏内存往往不会造成什么运行上的问题（尽管可能被认为不太体面）。而当你写一个长时间运行的服务器（比如永不退出的 Web 服务器或数据库管理系统）时，泄漏的内存就是个严重得多的问题，最终会在程序耗尽内存时导致崩溃。当然，在一类特殊程序——操作系统本身——内部，泄漏内存更是天大的事。这又一次告诉我们：写内核代码的人，干的是最苦的活儿……

### 小结

如你所见，折腾内存的法子多得是。正因为内存错误频发，一整个工具生态发展了起来，帮你找出代码里的这些问题。看看 purify [HJ92] 和 valgrind [SN05]；两款工具都很擅长帮你就定位内存相关问题的源头。等你用惯了这些强力工具，就会纳闷以前没有它们是怎么活过来的。

## 14.5 底层操作系统支持

你可能注意到，讨论 `malloc()` 和 `free()` 时，我们一直没提系统调用。原因很简单：它们不是系统调用，而是库调用。`malloc` 库管理的是你虚拟地址空间内的空间，但它本身是搭建在一些系统调用之上的，这些系统调用会进入操作系统，申请更多内存，或把一些内存归还给系统。

其中一个系统调用叫 `brk`，用来改变程序**断点(break)**的位置，也就是堆的末尾。它接受一个参数（新断点的地址），于是会根据新断点比当前断点大还是小，来增加或减少堆的大小。还有一个调用 `sbrk`，传的是一个增量，但用途差不多。

注意，你绝不该直接调用 `brk` 或 `sbrk`。它们是给内存分配库用的；你要是想自己用，多半会把什么东西搞得（极其）不对劲。老老实实用 `malloc()` 和 `free()` 就好。

最后，你还可以通过 `mmap()` 调用从操作系统获取内存。传入正确的参数，`mmap()` 就能在你的程序里创建一块**匿名内存区域(anonymous memory region)**——这块区域不与任何特定文件关联，而是关联到**交换空间(swap space)**，这个我们到虚拟内存部分再详细讨论。这块内存随后也可以当堆来对待和管理。更多细节请读 `mmap()` 的手册页。

## 14.6 其他调用

内存分配库还支持另外几个调用。比如，`calloc()` 在分配内存之余，还会在返回前把它清零；这能避免某些错误——就是你误以为内存已经清零、于是忘了自己初始化（见上文关于"未初始化读"的那段）。例程 `realloc()` 也很有用：当你为某个东西（比如一个数组）分配了空间，随后又需要往里加内容时，`realloc()` 会造一块更大的新内存，把旧区域复制进去，再返回指向新区域的指针。

## 14.7 小结

我们介绍了一些涉及内存分配的 API。一如既往，我们只讲了基础；更多细节别处有。更多信息请读 C 语言圣经 [KR88] 和 Stevens 的著作 [SR05]（第 7 章）。想看一篇关于如何自动检测并纠正其中许多问题的现代酷文，参见 Novark 等人 [N+07]；这篇论文还出色地总结了常见问题，并就如何发现和修复它们给出了一些巧妙思路。

## 作业（代码）

这份作业会让你对内存分配熟悉起来。首先，你要写一些有 bug 的程序（好玩吧！）。然后，你要用一些工具帮你找出自己埋下的 bug。接着，你会意识到这些工具有多棒，并在以后用上它们，从而让自己更快乐、更高效。这些工具是调试器（比如 `gdb`）和一个叫 `valgrind` 的内存 bug 检测器 [SN05]。

### 问题

1. 首先，写一个名为 `null.c` 的简单程序：创建一个指向整数的指针，把它设为 `NULL`，然后尝试解引用它。把它编译成一个名为 `null` 的可执行文件。运行这个程序会发生什么？
2. 接着，带着符号信息编译这个程序（用 `-g` 标志）。这样做会把更多信息放进可执行文件，让调试器能获取变量名之类的有用信息。在调试器下运行程序：输入 `gdb null`，等 `gdb` 起来后，输入 `run`。`gdb` 给你显示了什么？
3. 最后，对这个程序使用 `valgrind` 工具。我们用 `valgrind` 里的 `memcheck` 工具来分析发生了什么。这样运行：`valgrind --leak-check=yes null`。运行时发生了什么？你能解读工具的输出了吗？
4. 写一个简单程序，用 `malloc()` 分配内存，却在退出前忘了 `free` 它。这个程序运行时会发生什么？你能用 `gdb` 找出任何问题吗？`valgrind` 呢（同样加上 `--leak-check=yes` 标志）？
5. 写一个程序，用 `malloc` 创建一个名为 `data`、大小为 100 的整数数组；然后，把 `data[100]` 设为零。运行这个程序会发生什么？用 `valgrind` 运行这个程序又会怎样？这个程序正确吗？
6. 创建一个程序，分配一个整数数组（同上），释放它，然后尝试打印数组某个元素的值。程序能运行吗？对它用 `valgrind` 会发生什么？
7. 现在给 `free` 传一个滑稽的值（比如指向你上面所分配数组中间某个位置的指针）。会发生什么？要找到这类问题，你需要工具吗？
8. 试试内存分配的其他一些接口。比如，创建一个简单的类向量(vector)数据结构和相关例程，用 `realloc()` 来管理这个向量。用一个数组存储向量的元素；当用户往向量里加一项时，用 `realloc()` 为它分配更多空间。这样的向量性能如何？和链表比起来怎么样？用 `valgrind` 帮你找 bug。
9. 多花点时间，读一读如何使用 `gdb` 和 `valgrind`。熟悉自己的工具至关重要；花时间学会如何在 UNIX 和 C 环境里成为一名专家级调试者。
