# 第 40 章 文件系统实现

> 英文原题：*File System Implementation*

本章介绍一个名为 **vsfs（Very Simple File System，极简文件系统）**的简单实现。它是典型 UNIX 文件系统的简化版，用来认识许多现代文件系统都具备的磁盘数据结构、访问方法与策略。

文件系统完全由软件构成。研究 CPU 和内存虚拟化时，我们会增加硬件功能来改善系统；这里不需要这么做，不过仍要关注设备特性，免得文件系统在理论上健步如飞、落到磁盘上却原地喘气。

软件的自由度极大，于是人们造出了许多文件系统，字母表上从 AFS（Andrew File System）[H+88] 一路排到 ZFS（Sun 的 Zettabyte File System）[B07]。它们采用不同数据结构，各有擅长与不擅长之处。因此我们用案例学习：本章先用 vsfs 引入主要概念，之后再考察真实文件系统，看看现实中的设计如何分道扬镳。

!!! danger "问题核心：怎样实现一个简单文件系统"
    怎样构建简单文件系统？磁盘上需要哪些结构？它们要跟踪什么？系统怎样访问它们？

## 40.1 思考方式

理解文件系统通常要抓住两个方面。

第一是**数据结构**：文件系统用什么磁盘结构组织数据和元数据？vsfs 等简单文件系统使用块或其他对象的数组；SGI XFS 等复杂系统则使用树形结构 [S+96]。

第二是**访问方法**：它怎样把进程发出的 `open()`、`read()`、`write()` 等调用映射到这些结构？执行某个调用时要读哪些结构、写哪些结构？效率如何？

理解了数据结构和访问方法，就建立起了文件系统实际怎样工作的心理模型，这是系统思维的重要部分。

!!! note "边栏：文件系统的心理模型"
    学习系统真正要培养的是心理模型。对文件系统，你最终应能回答：哪些磁盘结构保存数据和元数据？进程打开文件时发生什么？读写要访问哪些磁盘结构？完善这种模型，才能获得抽象理解，而不是只认得某份实现代码里的几行语句——当然，读代码也很有用。

## 40.2 总体组织

先设计 vsfs 的磁盘布局。我们把磁盘划分为固定大小的块；简单文件系统通常只使用一种块大小，这里选常见的 4 KB。一个包含 $N$ 个块的分区，块地址便从 0 到 $N-1$。为了让图能塞进脑子而不把脑子撑坏，假设磁盘只有 64 块。

多数空间理应存放用户数据。我们把最后 56 块保留为**数据区(data region)**，记为 `D`。文件系统还必须保存每个文件的元数据，例如文件由哪些数据块组成、大小、所有者、访问权限和时间戳；这些信息通常放在 **inode** 中。这里用 5 块组成 **inode 表(inode table)**，记为 `I`。

假设一个 inode 为 256 字节，一个 4 KB 块可容纳 16 个 inode；5 块共 80 个 inode，也就是这个微型文件系统最多容纳 80 个文件。磁盘大些时，只需分配更大的 inode 表。

系统还得知道哪些 inode 与数据块空闲。我们分别使用一张 **inode 位图(inode bitmap)** `i` 和一张**数据位图(data bitmap)** `d`；每一位表示对应对象空闲（0）还是已用（1）。用整个 4 KB 块只追踪 80 个 inode 或 56 个数据块，确实奢侈得像用体育馆停一辆自行车，不过这样最简单。

细心的读者——也就是还没睡着的读者——会发现还剩一块。它留给**超级块(superblock)** `S`。超级块记录此文件系统有多少 inode 和数据块、inode 表从哪里开始，以及标识文件系统类型的魔数等信息。

| 块号 | 0 | 1 | 2 | 3–7 | 8–63 |
|---|---|---|---|---|---|
| 内容 | 超级块 `S` | inode 位图 `i` | 数据位图 `d` | inode 表 `I` | 数据区 `D` |

挂载文件系统时，操作系统先读超级块，初始化各种参数，再把卷接到目录树上。以后访问卷中的文件时，系统就知道所需结构躲在哪里了。

## 40.3 文件组织：inode

inode 是文件系统最重要的磁盘结构之一，几乎所有文件系统都有类似东西。名字是 **index node（索引节点）**的缩写，至少可以追溯到 UNIX [RT74]，可能还更早；当年的 inode 排成数组，inode 号正好用作数组索引。

!!! note "数据结构：inode"
    inode 是许多文件系统对“保存单个文件元数据的结构”的通称，其中包括长度、权限和组成文件的数据块位置。现代系统通常为每个文件维护类似结构，只是可能叫 `dnode`、`fnode` 等。inode 的设计是文件系统设计的核心之一。

每个 inode 由 **i-number**（即 inode 号）隐式引用。在 vsfs 之类的简单系统中，给定 i-number 就能直接算出 inode 的磁盘位置。

例如 inode 表从 12 KB 处开始，共 5 个 4 KB 块，每个 inode 为 256 字节。inode 32 在 inode 区内的偏移为 $32\times256=8192$ 字节，加上表起点 12 KB，得到 20 KB。磁盘按扇区而非字节寻址；若扇区为 512 字节，就读取第 $20\times1024/512=40$ 号扇区。一般公式为：

```c
blk    = (inumber * sizeof(inode_t)) / blockSize;
sector = ((blk * blockSize) + inodeStartAddr) / sectorSize;
```

inode 几乎包含文件的一切元数据：类型、大小、已分配块数、所有者与访问权限、创建/修改/访问时间，以及指向数据块的指针。凡不是纯用户数据的文件系统信息，通常都叫元数据。

| 大小（字节） | ext2 字段 | 含义 |
|---:|---|---|
| 2 | `mode` | 文件能否读、写、执行 |
| 2 | `uid` | 所有者 |
| 4 | `size` | 文件字节数 |
| 4 | `time` | 上次访问时间 |
| 4 | `ctime` | 创建时间 |
| 4 | `mtime` | 上次修改时间 |
| 4 | `dtime` | inode 删除时间 |
| 2 | `gid` | 所属组 |
| 2 | `links_count` | 硬链接数 |
| 4 | `blocks` | 已分配块数 |
| 4 | `flags` | ext2 应如何处理该 inode |
| 4 | `osd1` | 操作系统相关字段 |
| 60 | `block` | 15 个磁盘指针 |
| 4 | `generation` | 文件版本，供 NFS 使用 |
| 4 | `file_acl` | 超越模式位的 ACL 权限模型 |
| 4 | `dir_acl` | 目录 ACL |

### 多级索引

inode 设计中的关键决定，是怎样指向文件数据块。最简单的方法是在 inode 中放若干**直接指针(direct pointer)**，每个指向文件的一个磁盘块。但容量受限：文件若大于“直接指针数 × 块大小”，好运就用完了。

为支持大文件，可以加入**间接指针(indirect pointer)**。它不指向用户数据，而指向一个装满更多指针的块，后者再指向数据块。若 inode 有 12 个直接指针和 1 个间接指针，在 4 KB 块、4 字节地址下，间接块可再放 1024 个指针，文件最大为 $(12+1024)\times4\text{ KB}=4144\text{ KB}$。

还嫌不够？加入**二级间接指针(double indirect pointer)**，它指向一块“指向间接块的指针”，可再覆盖 $1024\times1024$ 个 4 KB 块，把文件推到 4 GB 以上。再往上自然是三级间接指针；它能管多大文件，请自行算算，提示是：挺大。

这种不平衡树称为**多级索引(multi-level index)**。12 个直接指针，加一级与二级间接指针，可表示略多于 4 GB：

$$
(12+1024+1024^2)\times4\text{ KB}.
$$

原始 UNIX 文件系统、Linux ext2/ext3、NetApp WAFL 等都使用多级索引；SGI XFS 与 Linux ext4 等则使用区段。

!!! tip "考虑基于区段的方法"
    **区段(extent)**由一个磁盘指针加块数长度组成，不必为文件的每一块都保存指针。单个区段要求连续空间，限制太大，因此实际文件系统通常允许一个文件使用多个区段。

    指针方案最灵活，却为大文件消耗很多元数据；区段方案不那么灵活但更紧凑，尤其适合磁盘空闲空间充足、文件能连续放置的情况——而连续放置本来就是几乎所有分配策略的愿望。

为什么使用这种头重脚轻的不平衡树，而不是“更优雅”的平衡结构？几十年的测量不断发现：**多数文件很小**。设计应优化常见情况；12 个直接指针就能直接覆盖 48 KB，只有较大文件才需要间接块。

| 测量结论 | 典型结果 |
|---|---|
| 多数文件很小 | 最常见大小约 2 KB |
| 平均文件大小在增长 | 平均接近 200 KB |
| 大部分字节位于大文件中 | 少数大文件占用大部分空间 |
| 文件系统包含很多文件 | 平均接近 10 万个 |
| 文件系统约半满 | 磁盘变大后仍约 50% 满 |
| 目录通常很小 | 许多目录只有少量条目，多数不超过 20 个 |

*图 40.2：文件系统测量结果摘要 [A+07]。*

inode 终究只是数据结构。只要能保存并高效查询所需信息，其他设计也完全可行。工作负载或技术发生变化时，文件系统软件也应敢于换设计。

## 40.4 目录组织

vsfs 中的目录很简单，本质上就是一列“名称—inode 号”二元组。若名称可变长，每项还会保存长度。

假设目录 `dir` 的 inode 号为 5，其中有 `foo`、`bar`、`foobar_is_a_pretty_longname` 三个文件，inode 号分别为 12、13、24，磁盘内容可能如下：

| `inum` | `reclen` | `strlen` | `name` |
|---:|---:|---:|---|
| 5 | 12 | 2 | `.` |
| 2 | 12 | 3 | `..` |
| 12 | 12 | 4 | `foo` |
| 13 | 12 | 4 | `bar` |
| 24 | 36 | 28 | `foobar_is_a_pretty_longname` |

每项包含 inode 号、记录总长度、名称实际长度和名称。`.` 是当前目录 `dir`，`..` 是父目录，本例中为根目录。

调用 `unlink()` 删除文件会在目录中留下空洞，可以用保留 inode 号 0 标记。记录长度之所以有用，原因之一就是新条目能复用较大的旧条目，剩余空间继续留在记录里。

目录通常被当成特殊文件：它有位于 inode 表中的 inode，只是类型标记为“目录”；inode 指向位于普通数据区的目录数据块，必要时也可有间接块。因此磁盘总体布局无需另起炉灶。

线性表并非唯一方案。XFS 用 B 树保存目录 [S+96]，创建文件时可更快确认名称是否已存在；线性表则可能要从头扫到尾，目录一大，耐心先小。

!!! note "边栏：基于链表的分配"
    inode 还可以只保存指向文件第一块的指针，每个数据块末尾再指向下一块，于是链表可以支持任意大文件。但读取最后一块或随机访问时，必须沿链一路走，性能不妙。

    一些系统把链接信息集中到内存表中。表以数据块地址 $D$ 为索引，表项保存 $D$ 的下一块地址，也可用空值表示文件结尾、用特殊标记表示空闲。随机访问时先在内存表中追链，再直接访问目标磁盘块。

    听起来耳熟吗？这就是 **FAT（File Allocation Table，文件分配表）**文件系统的基本结构。这个 NTFS [C94] 之前的经典 Windows 文件系统没有真正的 inode；目录项既保存文件元数据，也直接指向首块，因此无法创建硬链接。更多不甚优雅的细节见 Brouwer [B02]。这里说的是文件系统 FAT，不是培根油脂；不过必须承认，培根油大概更香。

## 40.5 空闲空间管理

文件系统必须跟踪空闲和已用的 inode、数据块，以便创建文件或目录时找到位置。vsfs 用两张位图完成这项工作。

创建文件时，系统扫描 inode 位图寻找空闲 inode，将对应位置 1，并最终把位图更新到磁盘。分配数据块时流程类似。

分配策略还会考虑性能。例如 ext2/ext3 在新文件需要数据块时，会寻找一段连续空闲块（比如 8 块），预先分给文件，以保证其中一部分在磁盘上连续。**预分配(pre-allocation)**是常用启发式策略。

!!! note "边栏：空闲空间管理"
    位图只是众多方法之一。早期文件系统常用空闲链表：超级块指向第一空闲块，该块再指向下一空闲块。需要块时取走表头并更新链表。

    现代系统会用更复杂的结构，例如 XFS 以某种 B 树紧凑表示空闲磁盘区段。和其他数据结构一样，这里也有各种时间—空间取舍。

## 40.6 访问路径：读取与写入

知道文件和目录怎样落盘后，接着跟踪读写时究竟发生什么。这条访问路径是理解文件系统的第二把钥匙，请打起精神。

以下假设文件系统已经挂载，超级块在内存中；inode 与目录等其他内容仍在磁盘上。

### 从磁盘读取文件

假设要打开 `/foo/bar`，读取后关闭；文件为 12 KB，即 3 块。

调用 `open("/foo/bar", O_RDONLY)` 后，文件系统首先要找到 `bar` 的 inode，以取得权限、大小等信息。但手里只有完整路径，所以必须逐级遍历。

遍历从根目录 `/` 开始。根没有父目录，其 inode 号必须是挂载时已知的固定值；多数 UNIX 文件系统使用 2。系统读取包含 inode 2 的块，再由其中指针读取根目录数据，寻找 `foo` 项。找到后便得到 `foo` 的 inode 号（假设为 44），再读取其 inode 与目录数据，终于找到 `bar` 的 inode 号。

最后把 `bar` 的 inode 读入内存，执行权限检查，为进程分配文件描述符并返回。之后第一次 `read()` 默认从偏移 0 开始：系统查 inode 得到首个数据块的位置，读入数据，也可能写 inode 以更新最后访问时间；同时推进内存中打开文件表的偏移。后续读取依次取得第二、第三块。`close()` 主要释放文件描述符，本例无需磁盘 I/O。

| 调用阶段 | 主要磁盘访问 |
|---|---|
| `open("/foo/bar")` | 读根 inode → 读根目录 → 读 `foo` inode → 读 `foo` 目录 → 读 `bar` inode |
| 第 1 次 `read()` | 读 `bar` 数据块 0，写 inode 的访问时间 |
| 第 2 次 `read()` | 读 `bar` 数据块 1，写 inode 的访问时间 |
| 第 3 次 `read()` | 读 `bar` 数据块 2，写 inode 的访问时间 |
| `close()` | 无磁盘 I/O |

*图 40.3：文件读取时间线；时间自上而下。*

`open()` 产生的 I/O 与路径长度成正比：路径每多一层，就要多读目录 inode 和目录数据。大目录更糟，寻找一个条目可能要读许多块。读文件已经不轻松；马上你会发现，写文件——尤其创建文件——更勤快得令人感动。

!!! note "边栏：读取不会访问分配结构"
    许多同学误以为只读文件也要查询位图。并非如此。位图等分配结构只在需要分配时访问；inode、目录和间接块已经提供了读取所需的全部位置。inode 都指向那个块了，没必要再去位图问一句“它真的分配了吗”。

### 向磁盘写入文件

写入同样先打开文件，再调用 `write()` 更新内容，最后关闭。但若不是覆盖已有块，写入还要分配新块。

给新文件追加一块数据时，逻辑上要做 5 次 I/O：读数据位图、写回标记了新块的位图；读 inode、写回记录了新块位置的 inode；最后写数据块本身。

创建文件更忙：读 inode 位图寻找空闲项，写位图标记已用，写新 inode 初始化它，写父目录数据以建立“名称—inode”映射，还要读写父目录 inode。若目录需要扩容，还得访问数据位图并写新目录块。只是创建一个文件，阵仗已经像搬家。

以创建 `/foo/bar` 并写入三个 4 KB 块为例：

| 阶段 | 主要工作 | 典型 I/O 数 |
|---|---|---:|
| `open()` 并创建 | 遍历路径；分配并写 inode；更新 inode 位图；更新父目录数据与 inode | 10 |
| 每次分配式 `write()` | 读写 inode；读写数据位图；写数据块 | 5 |
| 三次 `write()` | 重复上述流程三次 | 15 |

*图 40.4：文件创建时间线；时间自上而下。*

!!! danger "问题核心：怎样降低文件系统 I/O 成本"
    即便打开、读取、写入这类最简单的操作，也会产生大量散布在磁盘各处的 I/O。文件系统怎样降低这些 I/O 的高昂成本？

## 40.7 缓存与缓冲

读写文件很昂贵，因此多数文件系统积极使用 DRAM 缓存重要块。

没有缓存时，`open()` 对路径中的每一级目录至少要读两次：一次读 inode，一次读目录数据。像 `/1/2/3/.../100/file.txt` 这样的路径，光打开就会进行数百次读取。

早期文件系统设置固定大小的块缓存，使用 LRU 等策略决定保留什么，启动时通常划出约 10% 内存。但静态划分可能浪费：文件系统暂时用不上这 10% 时，空闲页也不能改作他用。

现代系统多采用动态划分，把虚拟内存页和文件系统页合并进统一的**页缓存(page cache)** [S00]；谁当时更需要内存，谁便多用一些。

!!! tip "理解静态划分与动态划分"
    **静态划分**一次性给各用户固定份额，保证人人有份，性能更可预测，也常更易实现。**动态划分**随时间调整份额，让资源饥渴者使用原本闲置的资源，利用率更高；代价是实现复杂，而且某用户被借走资源后，真正需要时可能很久才收得回来。

    没有永远最佳的方法。应根据眼前问题选择合适方案——说到底，难道不该一直如此吗？

有缓存后，第一次打开文件仍可能产生许多 I/O；以后再次打开同一文件或同目录文件，大多命中缓存，无需磁盘访问。

缓存对写入的作用不同。读取可以完全被缓存吸收；写入若要持久，终究必须到磁盘。但**写缓冲(write buffering)**仍有三项收益：

1. 延迟写入能合并更新。例如接连创建两个文件时，inode 位图可以改两次后只写回一次。
2. 内存中攒下多次写入后，系统可以重新调度 I/O，提高性能。
3. 有些写入能完全避免。例如创建文件后立即删除，若创建状态尚未落盘，系统就不必写出再擦掉。在这里，懒惰是一种美德。

现代文件系统通常把写入在内存中缓冲 5～30 秒。这又是一项取舍：留得越久，越能合并、调度甚至消除写入；但系统若在落盘前崩溃，更新也会丢失。

!!! tip "理解持久性与性能的取舍"
    若用户要求写入立即持久，系统必须完成全部落盘工作，写入慢但安全。若能容忍少量数据丢失，系统便可先缓存在内存、后台再写，表面速度很快；崩溃时尚未提交的数据则会消失。

    正确取舍取决于应用。浏览器刚下载的几张图片丢了或许可接受；银行数据库给你加钱的事务丢了一半，多半不太能接受。除非你富得流油——那你怎么还在意最后那几分钱？

数据库等应用不喜欢默认取舍，会调用 `fsync()` 强制落盘，使用绕开缓存的直接 I/O，或干脆访问裸磁盘、完全绕开文件系统。多数应用接受文件系统默认策略；不满意时，接口也留出了控制手段。

## 40.8 小结

构建文件系统需要一些基本部件：每个文件的元数据通常放在 inode 中；目录是一种保存“名称 → inode 号”映射的特殊文件；位图等结构跟踪 inode 与数据块空闲还是已分配。

文件系统设计最迷人的地方是自由。接下来研究的系统会用这种自由优化不同方面。还有许多策略尚未讨论，例如创建新文件时究竟放在磁盘哪里。未来章节会讲到它们。真的会吗？此处请自行播放神秘音乐，让你对文件系统愈发欲罢不能。

数据库课程会讲老派数据库为何坚持绕开操作系统、凡事亲力亲为。不过要小心：数据库那帮人总爱说操作系统坏话。数据库同学们，羞不羞，羞不羞。

## 参考文献

- [A+07] “A Five-Year Study of File-System Metadata” by Nitin Agrawal et al. FAST '07, 2007. 对文件系统实际使用方式的优秀分析；沿其参考文献还能一路追到 20 世纪 80 年代初。
- [B07] “ZFS: The Last Word in File Systems” by Jeff Bonwick and Bill Moore. 一个较新的重要文件系统，功能与精彩想法塞得满满当当。本书真该有一章讲它，也许很快就有。
- [B02] “The FAT File System” by Andries Brouwer. September 2002. 对 FAT 的清晰说明。是文件系统那个 FAT，不是培根那个 fat；不过培根油恐怕更好吃。
- [C94] “Inside the Windows NT File System” by Helen Custer. Microsoft Press, 1994. 一本介绍 NTFS 的小书；别处大概还有技术细节更多的资料。
- [H+88] “Scale and Performance in a Distributed File System” by John H. Howard et al. *ACM TOCS* 6:1, February 1988. 经典分布式文件系统论文，后面还会深入，别急。
- [P09] “The Second Extended File System: Internal Layout” by Dave Poirier. 2009. 介绍 ext2 的一些细节；它是受 Berkeley FFS 影响的简单 Linux 文件系统。
- [RT74] “The UNIX Time-Sharing System” by M. Ritchie, K. Thompson. *CACM* 17:7, 1974. UNIX 原始论文，能从中看到现代操作系统许多根基。
- [S00] “UBC: An Efficient Unified I/O and Memory Caching Subsystem for NetBSD” by Chuck Silvers. FREENIX, 2000. 介绍 NetBSD 如何统一文件系统缓冲缓存与虚拟内存页缓存；许多系统采用类似做法。
- [S+96] “Scalability in the XFS File System” by Adam Sweeney et al. USENIX '96. 较早把操作可扩展性推到中心位置的工作，例如目录中容纳数百万文件。其关键想法：一切皆树。本书也该给它一章。
