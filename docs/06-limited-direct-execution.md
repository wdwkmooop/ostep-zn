# 第 6 章 机制：受限制的直接执行

> 英文原题：*Mechanism: Limited Direct Execution*

为了虚拟化 CPU，操作系统必须设法让许多看似同时运行的作业共享物理 CPU。基本思路很简单：先运行一个进程一小会儿，再运行另一个，如此往复。用这种方式对 CPU 进行时间共享，就实现了虚拟化。

然而，构建这种虚拟化机制有几个难题。首先是**性能(performance)**：怎样实现虚拟化，又不给系统增加过多开销？其次是**控制(control)**：怎样高效运行进程，同时保持对 CPU 的控制？控制对操作系统尤其重要，因为它负责管理资源；一旦失去控制，某个进程可能永远运行并霸占机器，也可能访问自己无权接触的信息。因此，在保持控制的同时获得高性能，是构建操作系统的核心挑战之一。

!!! danger "问题核心"
    **如何在保持控制的前提下高效虚拟化 CPU？**

    操作系统必须高效地虚拟化 CPU，同时保有对系统的控制。为此，既需要硬件支持，也需要操作系统支持。操作系统常常会审慎地借助少量硬件功能，有效完成自己的工作。

## 6.1 基本技术：受限制的直接执行

为了让程序以预期的速度运行，操作系统开发者不出所料地想出了一项技术，我们称之为**受限制的直接执行(limited direct execution, LDE)**。「直接执行」这部分很简单：直接让程序在 CPU 上运行。因此，操作系统想启动某个程序时，会在进程列表中为它创建一个进程项，分配一些内存，把程序代码从磁盘加载到内存中，找到它的入口点（即 `main()` 例程或类似位置），跳转过去，开始运行用户代码。

| 为程序分配内存 | |
| 把程序加载进内存 | |

图 6.1 展示了这种基本的直接执行协议（目前还没有任何限制）：操作系统用普通的调用和返回跳到程序的 `main()`，之后再回到内核。

听起来很简单，对吧？但在虚拟化 CPU 的道路上，这种方法引出了几个问题。第一，如果直接运行程序，操作系统怎样在保持高效的同时，确保程序不会做我们不想让它做的事？第二，当进程正在运行时，操作系统怎样让它停下来，再切换到另一个进程，从而实现虚拟化 CPU 所需的时间共享？

回答这些问题时，我们会更清楚地认识虚拟化 CPU 需要什么。随着这些技术逐步成形，你也会明白名称里的「受限制」从何而来：如果运行中的程序不受限制，操作系统就什么也控制不了，只会沦为「一个函数库」——对一个胸怀大志的操作系统来说，实在太悲惨了！

## 6.2 问题一：受限操作

直接执行的明显优势是快：程序直接在硬件 CPU 上原生运行，因此能以预期的速度执行。但在 CPU 上运行也会带来问题：如果进程想执行某种**受限操作(restricted operation)**，例如向磁盘发出 I/O 请求，或者获取更多 CPU、内存等系统资源，该怎么办？

!!! danger "问题核心"
    **如何执行受限操作？**

    进程必须能执行 I/O 和其他受限操作，却又不能获得对整个系统的完全控制。操作系统与硬件该如何协作，才能做到这一点？

一种办法，是干脆允许任何进程随意执行 I/O 及相关操作。然而这样一来，许多我们想要的系统就无从构建。例如，假如要构建一个访问文件前检查权限的文件系统，就不能让任意用户进程直接向磁盘发出 I/O；否则，进程大可读写整块磁盘，所有保护都会化为乌有。

因此，我们引入一种新的处理器模式，称为**用户态(user mode)**；运行在用户态的代码能做的事情受到限制。例如，用户态进程不能发出 I/O 请求；如果执意这么做，处理器会引发异常，操作系统随后很可能杀死该进程。

与用户态相对的是**内核态(kernel mode)**，操作系统（或内核）在这种模式下运行。内核态代码可以为所欲为，包括发出 I/O 请求、执行各种受限指令等**特权操作(privileged operation)**。

不过挑战仍然存在：用户进程想执行某种特权操作，比如读取磁盘时，该怎么办？为解决这个问题，几乎所有现代硬件都允许用户程序执行**系统调用(system call)**。这种机制由 Atlas 等古老机器开创 [K+61, L78]；系统调用让内核可以谨慎地向用户程序开放某些关键功能，例如访问文件系统、创建和销毁进程、与其他进程通信，以及分配更多内存。大多数操作系统提供几百个调用（详见 POSIX 标准 [P10]）；早期 UNIX 系统提供的子集更加精简，大约只有二十个。

!!! note "边栏：为什么系统调用看起来像过程调用"
    你也许会奇怪，为什么 `open()`、`read()` 等系统调用，看起来和典型的 C 过程调用一模一样？既然看起来只是过程调用，系统怎么知道它其实是系统调用，并完成所有正确的工作？原因很简单：它确实是一次过程调用，只不过这个过程调用里面藏着那条著名的**陷入(trap)** 指令。

    更具体地说，调用 `open()` 时，你执行的是一次进入 C 库的过程调用。无论 `open()` 还是其他系统调用，库都会按照与内核约定的**调用约定(calling convention)**，把 `open()` 的参数放到大家都知道的位置（例如栈上或特定寄存器中），也把**系统调用号(system-call number)** 放到约定位置，然后执行陷入指令。库中位于陷入之后的代码会解包返回值，再把控制权交还发起系统调用的程序。因此，C 库中负责系统调用的部分是用汇编手工编写的：它必须严格遵循约定，正确处理参数和返回值，并执行与硬件相关的陷入指令。

    现在你知道，为什么自己不必编写汇编代码来陷入操作系统了：已经有人替你写好了。

要执行系统调用，程序必须执行一条特殊的陷入指令。它会同时跳入内核并把特权级提升到内核态。进入内核后，系统便能执行所需的特权操作（只要获得允许），替调用进程完成工作。结束后，操作系统调用一条特殊的**从陷入返回(return-from-trap)** 指令；正如你可能猜到的，它会返回发起调用的用户程序，同时把特权级降回用户态。

硬件执行陷入时必须相当谨慎：它得保存调用者足够多的寄存器，才能在操作系统发出从陷入返回指令时正确返回。例如，在 x86 上，处理器会把程序计数器、标志位和另外几个寄存器压入每个进程自己的**内核栈(kernel stack)**；从陷入返回会从栈中弹出这些值，恢复用户态程序的执行（详见 Intel 系统手册 [I11]）。其他硬件系统使用不同约定，但各平台上的基本概念相似。

!!! tip "提示：使用受保护的控制权转移"
    硬件通过提供不同执行模式来帮助操作系统。在用户态下，应用程序不能完全访问硬件资源；在内核态下，操作系统可以访问机器的全部资源。硬件还会提供陷入内核、从陷入返回用户程序的特殊指令，以及让操作系统告诉硬件陷阱表位于内存何处的指令。

讨论中还遗漏了一个重要细节：陷入怎么知道该运行操作系统里的哪段代码？显然，调用进程不能自己指定跳转地址（不能像过程调用那样）；否则，程序就能跳进内核中的任意位置，这显然是个「非常糟糕的主意」[^1]。因此，内核必须严格控制发生陷入时执行的代码。

内核会在启动时设置**陷阱表(trap table)**。机器启动时处于特权模式（内核态），可以按需要自由配置硬件。因此，操作系统最先做的事情之一，就是告诉硬件：出现特定异常事件时应该运行哪段代码。例如，硬盘中断、键盘中断或程序执行系统调用时，应该运行什么代码？操作系统通常用某种特殊指令，把这些**陷阱处理程序(trap handler)** 的位置通知硬件。硬件获知后，会一直记住这些位置，直到下次重启；于是，发生系统调用或其他异常事件时，硬件就知道该做什么（即跳到哪段代码）。

为了指明具体的系统调用，系统通常为每个调用分配一个系统调用号。用户代码负责把所需的系统调用号放进寄存器或栈上的指定位置；操作系统在陷阱处理程序中处理系统调用时，会检查该号码，确认它有效，再执行相应代码。这一层**间接寻址(indirection)** 构成了一种保护：用户代码不能指定确切的跳转地址，只能用号码请求某项服务。

最后补充一点：把陷阱表位置告诉硬件的指令威力非常大。正如你可能已经猜到的，它也是一项特权操作。要是在用户态尝试执行，硬件不会答应，而你大概也能猜到后果（提示：再见了，肇事程序）。值得思考：如果能安装自己的陷阱表，你可以对系统做出哪些可怕的事情？能接管整台机器吗？

!!! tip "提示：安全系统要警惕用户输入"
    尽管我们煞费苦心地在系统调用期间保护操作系统（增加硬件陷入机制，并确保对操作系统的所有调用都通过它），实现安全操作系统时仍有许多其他方面需要考虑。其中之一，是处理系统调用边界上的参数：操作系统必须检查用户传入的内容，确认参数格式正确，否则就拒绝调用。

    例如，在 `write()` 系统调用中，用户会指定一块缓冲区的地址，作为写入操作的数据源。如果用户有意或无意地传入一个「坏」地址（例如内核地址空间里的地址），操作系统必须发现并拒绝调用。否则，用户就可能读取全部内核内存；由于内核（虚拟）内存通常还包含系统的全部物理内存，这么一个小疏忽就能让程序读取系统中任意其他进程的内存。

    一般来说，安全系统必须对用户输入高度怀疑。做不到这一点，必然会产生很容易被攻破的软件，让过分轻信的操作系统开发者感叹世界既不安全又可怕，最后连饭碗也丢掉。

下面的时间线（越往下时间越晚）总结了这套协议。我们假设每个进程都有一个内核栈；进出内核时，硬件会在这里保存和恢复寄存器，包括通用寄存器和程序计数器。

| 操作系统 | 硬件 | 程序 |
|---|---|---|
| **启动时（内核态）**：初始化陷阱表 | 记住系统调用处理程序的地址 | |

受限制的直接执行协议分为两个阶段。第一阶段发生在启动时：内核初始化陷阱表，CPU 记住表的位置，内核通过特权指令完成这件事。第二阶段是运行进程：内核先设置若干内容（例如在进程列表中分配节点、分配内存），再用从陷入返回指令启动进程；CPU 随之切换到用户态，开始运行进程。

进程想发出系统调用时，会陷回操作系统；操作系统处理调用，再次通过从陷入返回把控制权交还进程。进程完成工作并从 `main()` 返回；这通常会进入一小段存根代码，由它正确退出程序（比如调用 `exit()` 系统调用，再次陷入操作系统）。此时操作系统完成清理，整个过程结束。

## 6.3 问题二：在进程之间切换

直接执行的下一个问题，是如何实现进程切换。进程之间切换应该很简单，对吧？操作系统只要决定停掉一个进程，再启动另一个。能有多大事？可实际上它有点棘手：某个进程正在 CPU 上运行，按定义就意味着操作系统没有运行。既然操作系统没在运行，它还能做什么？（提示：什么也做不了。）这听起来近乎哲学问题，却是真正的问题：操作系统不在 CPU 上运行，显然就无法采取任何行动。于是，我们来到了问题核心。

!!! danger "问题核心"
    **如何重新取得 CPU 的控制权？**

    操作系统怎样重新取得 CPU 的控制权，从而在进程之间切换？

### 协作方式：等待系统调用

过去有些系统——例如早期版本的 Macintosh 操作系统 [M11]，以及古老的 Xerox Alto 系统 [A79]——采用过一种称为**协作方式(cooperative approach)** 的方法。在这种模式下，操作系统相信系统中的进程会规矩行事；运行太久的进程应该定期主动放弃 CPU，让操作系统决定是否运行其他任务。

那么，在这个乌托邦世界里，一个友善的进程怎样放弃 CPU？事实证明，大多数进程都会频繁执行系统调用，从而把 CPU 控制权交给操作系统，例如打开并读取文件、向另一台机器发送消息，或者创建新进程。这类系统通常还提供一个显式的 `yield` 系统调用，它什么也不做，只把控制权交给操作系统，让后者能够运行其他进程。

应用程序做出非法操作时，也会把控制权交给操作系统。例如，应用除以零，或者尝试访问自己无权访问的内存，都会触发陷入。操作系统随即重新取得 CPU 控制权（并且很可能终止肇事进程）。

!!! tip "提示：处理行为不端的应用"
    操作系统经常要对付行为不端的进程：它们可能出于设计（恶意），也可能出于意外（bug），试图做不该做的事。现代系统处理这类恶行的方法，通常是直接终止肇事者。一击出局！也许有些残酷，但你试图非法访问内存或执行非法指令时，操作系统还能怎么办？

因此，在**协作式调度(cooperative scheduling)** 系统中，操作系统通过等待系统调用或某种非法操作发生，重新获得 CPU 控制权。你可能也想到了：这种被动方法并不理想吧？例如，一个恶意满满或只是 bug 缠身的进程陷入死循环、永远不执行系统调用时，会怎么样？操作系统能怎么办？

### 非协作方式：操作系统夺回控制权

如果进程拒绝执行系统调用（也不犯错），不把控制权还给操作系统，而硬件又不提供额外帮助，那么操作系统几乎什么也做不了。事实上，在协作方式下，进程卡进死循环时，你唯一的办法就是祭出解决所有计算机系统问题的古老绝招：重启机器。于是，在重新取得 CPU 控制权这项总任务下，我们又遇到了一个子问题。

!!! danger "问题核心"
    **没有协作时，如何取得控制权？**

    即使进程不肯合作，操作系统怎样才能取得 CPU 控制权？操作系统如何确保某个失控进程不会霸占整台机器？

答案很简单，而且许多年前就被多位计算机系统构建者发现了：**时钟中断(timer interrupt)** [M+63]。可以把定时器设备设成每隔若干毫秒引发一次中断；中断发生时，当前运行的进程会暂停，操作系统中预先配置好的中断处理程序开始运行。此刻操作系统重新获得 CPU 控制权，可以随心所欲：停止当前进程，启动另一个进程。

和前面讨论系统调用时一样，操作系统必须告诉硬件：时钟中断发生时要运行哪段代码。因此，操作系统会在启动时完成这项设置。其次，同样在启动过程中，操作系统必须启动定时器；这当然也是一项特权操作。定时器开始工作后，操作系统就可以放心了：控制权最终总会回到自己手中，因此它可以自由运行用户程序。定时器也可以关闭（同样是特权操作）；以后深入理解并发时，我们会再讨论这件事。

!!! tip "提示：用时钟中断重新取得控制权"
    有了时钟中断，即使进程不肯合作，操作系统也能再次在 CPU 上运行。因此，这项硬件功能对于帮助操作系统控制机器至关重要。

!!! tip "提示：重启很有用"
    前面说过，在协作式抢占下，应付死循环（及类似行为）的唯一办法是重启机器。你或许会嘲笑这招太糙，但研究人员已经证明，重启（更一般地说，让某个软件组件从头开始）可以成为构建健壮系统的强大工具 [C+04]。

    重启之所以有用，是因为它会把软件带回一个已知的、很可能经过更多测试的状态。重启还会回收陈旧或泄漏的资源（例如内存）；这些资源用其他方式可能很难处理。最后，重启很容易自动化。基于这些原因，大规模集群互联网服务的系统管理软件定期重启一批机器、将其复位并获得上述好处，并不罕见。

    所以，下次重启时，你不只是在用某个丑陋的权宜之计，而是在采用一种久经考验的方法改善计算机系统行为。干得漂亮！

注意，中断发生时，硬件也承担一些责任。尤其是，它必须保存足够多的程序状态，才能让后续的从陷入返回指令正确恢复被中断程序。这组操作与显式系统调用陷入内核时的硬件行为很相似：各种寄存器被保存下来（例如压入内核栈），随后可以由从陷入返回指令轻松恢复。

### 保存与恢复上下文

现在，无论通过系统调用让进程主动配合，还是通过时钟中断强行介入，操作系统总算重新取得了控制权。接下来必须作出决定：继续运行当前进程，还是切换到另一个进程？这个决定由操作系统中称为**调度器(scheduler)** 的部分作出；后面几章会详细讨论调度策略。

如果决定切换，操作系统会执行一小段底层代码，我们称之为**上下文切换(context switch)**。从概念上说，上下文切换很简单：操作系统只需保存当前进程的几个寄存器值（例如保存到它的内核栈），再为即将运行的进程恢复几个寄存器值（从其内核栈中恢复）。这样，当最终执行从陷入返回指令时，系统不会回到原先运行的进程，而会恢复另一个进程的执行。

为了保存当前进程的上下文，操作系统会执行一些底层汇编代码，保存它的通用寄存器、PC 和内核栈指针；随后恢复即将运行进程的这些寄存器与 PC，并切换到它的内核栈。通过切换栈，内核以一个进程（刚被中断的进程）的上下文进入切换代码，却以另一个进程（即将运行的进程）的上下文从中返回。最后，当操作系统执行从陷入返回指令时，即将运行的进程正式成为当前进程。上下文切换就此完成。

| 操作系统 | 硬件 | 程序 |
|---|---|---|
| **启动时（内核态）**：初始化陷阱表 | 记住系统调用处理程序、时钟处理程序的地址 | |
| **启动时**：执行**启动中断定时器** | 启动定时器；在 $X$ 毫秒后中断 CPU | |
| | | **用户态，进程 A**：…… |
| | **时钟中断**：把 A 的寄存器保存到 A 的内核栈；转入内核态；跳到陷阱处理程序 | |
| 处理陷入；调用 `switch()`；把 A 的寄存器保存到 A 的进程结构；从 B 的进程结构恢复 B 的寄存器；切换到 B 的内核栈；执行**从陷入返回（进入 B）** | | |
| | 从 B 的内核栈恢复寄存器；转入用户态；跳到 B 的 PC | **用户态，进程 B**：…… |

*图 6.3：受限制的直接执行协议（时钟中断）。*

图 6.3 展示了整个过程的时间线。在这个例子中，进程 A 正在运行，随后被时钟中断打断。硬件把它的寄存器保存到它的内核栈，然后进入内核（切换到内核态）。操作系统在时钟中断处理程序中决定从进程 A 切换到进程 B。它调用 `switch()` 例程，小心地保存当前寄存器值（存入 A 的进程结构），恢复进程 B 的寄存器（从 B 的进程结构项取出），再切换上下文——具体来说，就是修改栈指针，改用 B 的内核栈而不再使用 A 的。最后，操作系统从陷入返回，恢复 B 的寄存器，开始运行 B。

注意，这套协议中会发生两类寄存器保存/恢复。第一类发生在时钟中断时：硬件隐式地把运行中进程的用户寄存器保存到该进程的内核栈。第二类发生在操作系统决定从 A 切换到 B 时：软件（也就是操作系统）显式保存内核寄存器，不过这次是保存到进程结构的内存中。后一个动作把系统从「仿佛刚由 A 陷入内核」的状态，变成「仿佛刚由 B 陷入内核」的状态。

图 6.4 是 xv6 的上下文切换代码，可以让你更具体地感受这种切换如何完成。试试看能否读懂它（你需要了解一点 x86，也要了解一点 xv6）。`old` 和 `new` 上下文结构分别位于旧进程和新进程的进程结构中。

```asm
# void swtch(struct context **old, struct context *new);
#
# 把当前寄存器上下文保存到 old，
# 然后从 new 加载寄存器上下文。
.globl swtch
swtch:
    # 保存旧寄存器
    movl 4(%esp), %eax      # 把 old 指针放进 eax
    popl 0(%eax)            # 保存旧 IP
    movl %esp, 4(%eax)      # 以及栈
    movl %ebx, 8(%eax)      # 以及其他寄存器
    movl %ecx, 12(%eax)
    movl %edx, 16(%eax)
    movl %esi, 20(%eax)
    movl %edi, 24(%eax)
    movl %ebp, 28(%eax)

    # 加载新寄存器
    movl 4(%esp), %eax      # 把 new 指针放进 eax
    movl 28(%eax), %ebp     # 恢复其他寄存器
    movl 24(%eax), %edi
    movl 20(%eax), %esi
    movl 16(%eax), %edx
    movl 12(%eax), %ecx
    movl 8(%eax), %ebx
    movl 4(%eax), %esp      # 在这里切换栈
    pushl 0(%eax)           # 把返回地址放到位
    ret                     # 最后返回新上下文
```

## 6.4 担心并发吗？

有些认真又善于思考的读者，现在可能会问：「嗯……执行系统调用时发生时钟中断，会怎么样？」或者：「处理一个中断时又来了一个中断，会怎么样？内核里不会很难处理吗？」问得好——看来你还有救！

答案是肯定的：在处理中断或陷入时又发生另一个中断，操作系统确实必须认真对待。事实上，这恰好是本书第二部分「并发」的完整主题；详细讨论留到那里。

先勾勒几个基本做法，给你开开胃。一个简单办法，是让操作系统在处理中断时**禁用中断(disable interrupts)**；这样，处理某个中断期间，就不会再有其他中断送到 CPU。当然，操作系统必须谨慎：禁用中断太久可能导致中断丢失——用技术术语说，这很糟。

操作系统还开发了多种精巧的**加锁(locking)** 方案，保护内部数据结构的并发访问。这样，内核中就能同时开展多项活动，对多处理器尤其有用。不过我们会在本书下一部分看到，加锁可能相当复杂，并导致各种有趣而难以发现的 bug。

!!! note "边栏：上下文切换要多久"
    你很自然地会问：上下文切换这样的操作要花多长时间？系统调用呢？如果你好奇，有个名为 `lmbench` 的工具 [MS96] 专门测量这些时间，以及另外几项可能相关的性能指标。

    随时间推移，结果已经改善很多，大致跟上了处理器性能。例如，1996 年在 200 MHz P6 CPU 上运行 Linux 1.3.37 时，系统调用大约需要 4 微秒，上下文切换大约需要 6 微秒 [MS96]。现代系统的表现几乎好一个数量级：在 2～3 GHz 处理器上，耗时已经低于 1 微秒。

    值得注意的是，并非所有操作系统操作都会跟随 CPU 性能一起进步。正如 Ousterhout 指出的，许多操作系统操作是内存密集型的，而内存带宽随时间的改善远没有处理器速度那么显著 [O90]。因此，具体取决于负载，买来最新最强的处理器，可能并不会像你希望的那样让操作系统快多少。

## 6.5 小结

本章介绍了实现 CPU 虚拟化的一些关键底层机制；我们把这组技术统称为受限制的直接执行。基本思路很直白：直接在 CPU 上运行想要运行的程序，不过要先设置好硬件，限制进程在没有操作系统帮助时能做的事情。

现实生活中也采用这种通用方法。例如，家里有孩子——或者至少听说过孩子——的读者，可能熟悉「把房间改造成婴儿安全环境」：锁上装有危险物品的柜子，盖住电源插座。房间准备妥当后，就可以放心让宝宝自由活动，因为最危险的部分都已经受到限制。

同样，操作系统也会把 CPU 改造成「婴儿安全环境」：先在启动时设置陷阱处理程序、启动中断定时器，随后只让进程在受限模式下运行。这样，操作系统就能相当放心地让进程高效运行；只有在执行特权操作，或者进程霸占 CPU 太久、需要被换下时，才需要操作系统介入。

至此，虚拟化 CPU 的基本机制已经就位。但还有一个大问题没有回答：某个时刻究竟应该运行哪个进程？这个问题必须由调度器回答，也正是下一个研究主题。

!!! note "边栏：CPU 虚拟化关键词（机制）"
    - CPU 应至少支持两种执行模式：受限的用户态，以及有特权（不受限）的内核态。
    - 典型用户应用在用户态运行，通过系统调用陷入内核，请求操作系统服务。
    - 陷入指令会仔细保存寄存器状态，把硬件状态切换到内核态，再跳进操作系统中预先指定的目的地——陷阱表。
    - 操作系统完成系统调用服务后，通过另一条特殊的从陷入返回指令回到用户程序；这条指令会降低特权级，把控制权交给那条跳入操作系统的陷入指令之后的指令。
    - 操作系统必须在启动时设置陷阱表，并确保用户程序无法轻易修改它。这些都是受限制的直接执行协议的一部分；该协议既能高效运行程序，又不会让操作系统失去控制。
    - 程序开始运行后，操作系统必须用硬件机制确保用户程序不会永远运行，这项机制就是时钟中断。这是一种非协作式 CPU 调度方式。
    - 在时钟中断或系统调用期间，操作系统有时会想从当前进程切换到另一个进程；这项底层技术称为上下文切换。

## 作业（测量）

!!! note "边栏：测量作业"
    测量作业是一些小练习：你要编写代码并在真实机器上运行，以测量操作系统或硬件性能的某个方面。这类作业旨在让你获得一些亲手使用真实操作系统的经验。

这份作业要测量系统调用和上下文切换的成本。测量系统调用成本相对容易。例如，可以反复调用一个简单的系统调用（比如执行 0 字节读取），记录耗时；用总时间除以迭代次数，就能估算一次系统调用的成本。

需要考虑的一点，是计时器的精度和准确度。一个常用计时器是 `gettimeofday()`；详情请阅读手册页。你会看到，`gettimeofday()` 返回自 1970 年以来经过的微秒数；但这并不意味着计时器精确到微秒。连续调用两次 `gettimeofday()`，测量它的真实精度；由此可以知道，空系统调用测试需要迭代多少次，才能得到可靠的测量结果。如果 `gettimeofday()` 不够精确，可以考虑使用 x86 机器提供的 `rdtsc` 指令。

测量上下文切换成本稍微麻烦一些。`lmbench` 的做法是，让两个进程运行在同一颗 CPU 上，并在它们之间建立两条 UNIX 管道；管道只是 UNIX 系统中进程相互通信的许多方式之一。第一个进程向第一条管道写入，再等待从第二条管道读取。操作系统发现第一个进程在等待读取，就把它置于阻塞态，切换到另一个进程；后者从第一条管道读取，再写入第二条管道。当第二个进程再次尝试读取第一条管道时，它也会阻塞，于是这种来回通信的循环继续进行。通过测量重复通信的成本，`lmbench` 可以较准确地估算上下文切换成本。你可以试着用管道重现类似测试，也可以使用 UNIX 套接字等其他通信机制。

在多 CPU 系统上测量上下文切换成本有一个难点：必须确保参与切换的进程位于同一处理器。幸好，大多数操作系统都提供把进程绑定到特定处理器的调用；例如，在 Linux 上应该使用 `sched_setaffinity()`。确保两个进程都在同一处理器上，才能保证测量的是操作系统在同一颗 CPU 上停止一个进程、恢复另一个进程的成本。

[^1]: 想象一下：跳进文件访问代码，却恰好落在权限检查之后。事实上，这种能力很可能让狡猾的程序员诱使内核运行任意代码序列 [S07]。一般来说，请避开这类「非常糟糕的主意」。
