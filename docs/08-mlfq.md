# 第 8 章 调度：多级反馈队列

> 英文原题：*Scheduling: The Multi-Level Feedback Queue*

这一章，我们来对付最著名的调度方法之一：**多级反馈队列(Multi-Level Feedback Queue, MLFQ)**。MLFQ 调度器最早由 Corbato 等人在 1962 年描述 [C+62]，用在一个叫做**兼容分时系统(Compatible Time-Sharing System, CTSS)** 的系统中；这项工作，连同后来在 Multics 上的工作，让 ACM 把最高荣誉——图灵奖——颁给了 Corbato。此后这个调度器历经多年打磨，成了你在一些现代系统里会碰到的那些实现。

MLFQ 要解决的根本问题有两个方面。第一，它想优化周转时间——如前一章所说，这靠先运行较短的作业来实现；可惜操作系统通常并不知道一个作业会运行多久，而这恰恰是 SJF（或 STCF）这类算法所需要的知识。第二，MLFQ 想让系统对交互式用户（也就是坐在屏幕前盯着、等某个进程结束的用户）显得响应迅速，从而最小化响应时间；可惜像轮转这样的算法虽然降低了响应时间，却对周转时间极不友好。于是问题就是：既然我们通常对一个进程一无所知，怎样才能构建一个调度器来达成这些目标？调度器如何在系统运行过程中不断学习它所运行作业的特征，从而作出更好的调度决策？

!!! danger "问题核心"
    **没有完美知识时如何调度？**

    在不预先知道作业长度的前提下，我们怎样设计一个既能让交互式作业响应时间最小、又能让周转时间最小的调度器？

!!! tip "提示：从历史中学习"
    多级反馈队列是一个绝佳的例子，说明系统可以从过去学习以预测未来。这类方法在操作系统里很常见（在计算机科学的许多其他地方也是，包括硬件分支预测器和缓存算法）。当作业的行为带有阶段性、因而可预测时，这类方法就管用；当然，用这类技术得小心，它们很容易出错，反而把系统带向比一无所知时更糟的决策。

## 8.1 MLFQ：基本规则

要构建这样一个调度器，本章将描述多级反馈队列背后的基本算法；尽管许多实际实现的 MLFQ 各不相同 [E95]，大多数做法仍大同小异。

在我们的处理里，MLFQ 有若干个不同的队列，每个队列赋予不同的**优先级(priority)**。任一时刻，一个准备运行的作业只待在一个队列里。MLFQ 用优先级来决定此刻该运行哪个作业：优先级更高（也就是位于更高队列）的作业会被选中运行。

当然，某个队列里可能不止一个作业，它们的优先级相同。这时我们就在这些作业之间采用轮转调度。

于是我们得到 MLFQ 的头两条基本规则：

* **规则 1**：如果 Priority(A) > Priority(B)，则运行 A（不运行 B）。
* **规则 2**：如果 Priority(A) = Priority(B)，则 A 和 B 以轮转方式运行。

因此，MLFQ 调度的关键，在于调度器如何设置优先级。MLFQ 不是给每个作业一个固定优先级，而是根据观测到的行为来调整作业的优先级。比如，一个作业若反复在等待键盘输入时让出 CPU，MLFQ 会让它的优先级保持高位，因为交互式进程正是这种表现。反过来，一个作业若长时间密集占用 CPU，MLFQ 就会降低它的优先级。这样一来，MLFQ 会随着进程运行去了解它，并用该作业的历史来预测它未来的行为。

如果画一张某时刻队列可能长什么样的图，大概会像下面这样（图 8.1）。图中两个作业 A 和 B 位于最高优先级，作业 C 在中间，作业 D 在最低优先级。按我们目前对 MLFQ 的了解，调度器只会在 A 和 B 之间轮换时间片，因为它们是系统中优先级最高的作业；可怜的 C 和 D 根本轮不到运行——岂有此理！

## 8.2 尝试一：如何改变优先级

现在我们得决定：在一个作业的整个生命周期里，MLFQ 如何改变它的优先级（进而决定它在哪个队列）。要做到这一点，得牢记我们的负载：既有运行时间短（且可能频繁让出 CPU）的交互式作业，也有一些运行更久的"CPU 密集"作业——它们需要大量 CPU 时间，但响应时间并不重要。下面是我们对优先级调整算法的第一次尝试：

* **规则 3**：作业进入系统时，放在最高优先级（最顶上的队列）。
* **规则 4a**：如果作业在运行时用完了整个时间片，就降低其优先级（也就是下移一个队列）。
* **规则 4b**：如果作业在时间片用完之前让出 CPU，则保持同一优先级。

### 例 1：单个长时间运行的作业

来看几个例子。首先看一个长时间运行的作业在系统里会发生什么。图 8.2 展示了这个作业在一个三队列调度器中随时间的变化。

| 时间 | 队列 | 说明 |
|---|---|---|
| 0 | Q2（最高） | 作业进入，开始运行 |
| 10 | Q1 | 用完一个 10 ms 时间片，下降一级 |
| 20 | Q0（最低） | 再次下降 |
| 20+ | Q0 | 一直停留在最低优先级 |

*图 8.2：长时间运行的作业随时间的变化。*

如例中所示，作业从最高优先级进入（Q2）。经过一个 10 ms 的时间片后，调度器把它的优先级降低一级，于是它到了 Q1。在 Q1 运行一个时间片后，作业最终被降到系统里最低的优先级（Q0），并在那里一直待下去。挺简单，对吧？

### 例 2：来了个短作业

现在看一个更复杂的例子，希望你能看到 MLFQ 如何试图逼近 SJF。这个例子里有两个作业：A 是长时间运行的 CPU 密集作业，B 是运行时间短、交互式的作业。假设 A 已经运行了一段时间，然后 B 到达。会发生什么？MLFQ 会给 B 一个近似 SJF 的待遇吗？

图 8.3 画出了这个场景的结果。A（黑色）一直在最低优先级队列里跑着（任何长时间运行的 CPU 密集作业都这样）；B（灰色）在时刻 $T=100$ 到达，于是

| 时间 | 事件 |
|---|---|
| 0–100 | A 在 Q0 运行 |
| 100 | B 到达，进入 Q2 |
| 100–110 | B 在 Q2 运行一个时间片 |
| 110–120 | B 在 Q1 运行一个时间片 |
| 120 | B 完成（只需运行 20 ms，未跌到最低队列） |
| 120+ | A 在 Q0 恢复运行 |

*图 8.3：来了个交互式作业。*

被插入最高队列；由于它的运行时间很短（只有 20 ms），B 在两个时间片内就完成了，根本没跌到底部队列；随后 A（在低优先级）恢复运行。

从这个例子你大概能理解该算法的一个主要目标：因为它不知道一个作业会是短作业还是长作业，就先假定它可能是短作业，因而给它高优先级。如果它真是短作业，就会很快跑完；如果不是，它会慢慢往下降，很快也就证明自己是一个长时间运行的、更偏批处理的进程。MLFQ 就这样逼近了 SJF。

### 例 3：那 I/O 呢？

再看一个带有 I/O 的例子。如上面规则 4b 所述，如果一个进程在时间片用完之前让出处理器，我们就把它保持在原来的优先级。这条规则的用意很简单：比如一个交互式作业做了大量 I/O（比如在等待键盘或鼠标输入），它就会在时间片没结束前让出 CPU；这种情况下我们不想惩罚它，于是让它保持原级别。

图 8.4 展示了这如何运作：一个交互式作业 B（灰色），只需要用 CPU 1 ms 就要做一次 I/O，它与一个长时间运行的批处理作业 A（黑色）争夺 CPU。MLFQ 让 B 保持最高优先级，因为 B 不断释放 CPU；如果 B 是交互式作业，MLFQ 就进一步实现了"让交互式作业快速运行"的目标。

### 当前 MLFQ 的问题

于是我们有了一个基本的 MLFQ。它看起来干得还不错：在长时间运行的作业之间公平地共享 CPU，同时让短作业或 I/O 密集的交互式作业快速运行。可惜，我们迄今开发出来的做法含有严重缺陷。你能想到哪些吗？

（这里就是你停顿下来、尽量往阴险处想的地方。）

| 时间 | 事件 |
|---|---|
| 0 | A 在 Q0、C 在 Q0 |
| 100 | A 到达（进入 Q2，跑一个时间片后下降） |
| … | A 逐步下降，C 被饿死 |

*图 8.5（左）：没有优先级提升时的情形。*

| 时间 | 事件 |
|---|---|
| 0 | 长作业开始下降 |
| 50 | 所有作业被提升回 Q2（Boost） |
| 100 | 再次提升 |
| … | 长作业周期性获得运行机会 |

*图 8.5（右）：有优先级提升时的情形。*

第一，存在**饥饿(starvation)** 问题：如果系统中"交互式"作业"太多"，它们合起来会吃掉全部 CPU 时间，长时间运行的作业就永远得不到 CPU（它们被饿死）。就算在这种情形下，我们也希望这些作业能有所进展。

第二，聪明的用户可以改写程序来**钻调度器的空子(gaming the scheduler)**。钻空子一般指耍花招骗过调度器，让你拿到超过应得份额的资源。我们描述的算法容易受到下面这种攻击：在时间片结束前主动发起一个 I/O 操作（操作某个你根本不在乎的文件），从而让出 CPU；这样你就能留在原来的队列里，于是拿到更高比例的 CPU 时间。操作得当时（比如用掉时间片的 99% 之后再让出 CPU），一个作业几乎能独占 CPU。

最后，一个程序的行为可能随时间变化；原本 CPU 密集的作业也许过渡到交互阶段。用我们现在的做法，这样的作业就倒霉了，得不到系统里其他交互式作业那样的待遇。

!!! tip "提示：调度必须能抵御攻击"
    你也许以为，调度策略——无论是在操作系统内部（如本章讨论的），还是在更广的语境里（例如分布式存储系统的 I/O 请求处理 [Y+18]）——都算不上安全问题；但在越来越多的场景里，它恰恰就是。想想现代数据中心：来自世界各地的用户共享 CPU、内存、网络和存储系统；如果策略的设计与执行不够用心，单个用户就可能损害他人、为自己谋利。因此调度策略构成了系统安全的重要一环，应当谨慎构造。

| 时间 | 事件 |
|---|---|
| 0–99 | 作业几乎用满时间片，然后发起 I/O 让出 CPU |
| 99–100 | 发起 I/O，保持在原队列 |
| … | 反复如此，几乎独占 CPU |

*图 8.6（左）：没有抗钻空子保护。*

| 时间 | 事件 |
|---|---|
| 0–99 | 用掉全部分配额度后仍被降级 |
| 99 | 无论 I/O 与否，累计用满时间片即下降 |
| … | 无法独占 CPU |

*图 8.6（右）：有抗钻空子保护。*

## 8.3 尝试二：优先级提升

我们来改改规则，看看能不能避开饥饿问题。为了确保 CPU 密集作业也能取得一些进展（哪怕不多），我们能做点什么？

这里的简单想法是：定期提升系统中所有作业的优先级。实现方式很多，我们就来点简单的：把它们统统扔进最顶上的队列。于是新增一条规则：

* **规则 5**：经过某个时间段 $S$ 后，把系统中所有作业移到最顶上的队列。

新规则一举解决两个问题。第一，进程保证不会被饿死：只要待在顶部队列里，作业就会以轮转方式和其他高优先级作业分享 CPU，因而最终能得到服务。第二，如果某个 CPU 密集作业转为交互式，一旦它获得优先级提升，调度器就会正确对待它。

看个例子。这个场景里，我们只展示一个长时间运行的作业与两个运行时间短的交互式作业争夺 CPU 时的表现。图 8.5 给出两张图。左图没有优先级提升，于是长作业在两个短作业到达后就被饿死；右图每 50 ms 做一次优先级提升（这个值很可能太小，这里只是为举例而用），于是至少能保证长作业取得一些进展——每 50 ms 被提升到最高优先级，从而周期性地运行一会儿。

当然，加入时间段 $S$ 立刻引出一个显而易见的问题：$S$ 该设成多少？John Ousterhout 是一位备受尊敬的系统研究者 [O11]，他过去把系统中这类取值叫做 **voo-doo 常数(voo-doo constants)**，因为它们似乎得靠某种黑魔法才能设对。不幸的是，$S$ 就有这股味道。设得太高，长作业可能饿死；设得太低，交互式作业可能拿不到应有的 CPU 份额。

## 8.4 尝试三：更好的计费

现在还剩一个问题要解决：如何防止有人钻我们调度器的空子？真正的祸首，你可能已经猜到，就是规则 4a 和 4b——它们让作业通过"在时间片到期前让出 CPU"来保住优先级。那该怎么办？

这里的解决办法，是在 MLFQ 的每一层更精确地对 CPU 时间**计费(accounting)**。调度器不应忘记一个进程在某一层用了多少时间片，而应记录下来；一旦一个进程用完了它的配额，就把它降到下一个优先级队列。它是一次性用掉长突发、还是分很多小突发用掉，都无关紧要。于是我们把规则 4a 和 4b 重写成下面这单独一条规则：

* **规则 4**：一旦作业在某一层用完它的时间配额（无论它让出过多少次 CPU），就降低其优先级（也就是下移一个队列）。

看个例子。图 8.6 展示了当一个负载试图用旧的规则 4a、4b（左）以及新的抗钻空子规则 4（右）钻调度器空子时会发生什么。没有任何抗钻空子保护时，一个进程可以在时间片快结束前发起一次 I/O，从而霸占 CPU 时间。有了这种保护后，无论进程的 I/O 行为如何，它都会慢慢往下降，因而无法拿到不公平的 CPU 份额。

## 8.5 调优 MLFQ 及其他问题

MLFQ 调度还有几个问题。一个大问题是：这样的调度器该怎样参数化。比如，该有多少个队列？每个队列的时间片该多大？为了避免饥饿、并照顾行为变化，该多久做一次优先级提升？这些问题没有轻松答案，只有凭借一些负载经验、再对调度器进行调优，才能达到令人满意的平衡。

!!! tip "提示：避免 voo-doo 常数（Ousterhout 定律）"
    只要可能，避免 voo-doo 常数就是个好主意。不幸的是，如上面的例子所示，这往往很难。有人可能试着让系统自己学出一个好取值，但那同样不简单。常见的结果是：一个满是默认参数值的配置文件，经验丰富的管理员可以在出问题时去调它。你可以想象，这些参数常常原封不动；于是我们只能指望默认值在实际环境里管用。这个提示来自我们当年的操作系统教授 John Ousterhout，因此我们把它叫做 Ousterhout 定律。

比如，大多数 MLFQ 变体允许不同队列采用不同的时间片长度。高优先级队列通常给较短的时间片；毕竟它们装的是交互式作业，快速轮换才合理（比如 10 毫秒或更少）。相比之下，低优先级队列装的是长时间运行、CPU 密集的作业，因此较长的时间片效果好（比如几百毫秒）。图 8.7 展示了一个例子：两个作业在最高队列各运行 20 ms（时间片 10 ms），在中间队列运行 40 ms（时间片 20 ms），在最低队列时间片为 40 ms。

Solaris 的 MLFQ 实现——**分时调度类(Time-Sharing scheduling class, TS)**——配置起来特别方便；它提供一组表格，精确规定了进程的优先级在其生命周期内如何变化、每个时间片多长、以及多久提升一次作业的优先级 [AD00]；管理员可以摆弄这张表，让调度器表现出不同行为。表格的默认值是 60 个队列，时间片长度从 20 毫秒（最高优先级）缓慢增长到几百毫秒（最低），优先级大约每秒提升一次。

其他 MLFQ 调度器不使用表格，也不完全采用本章描述的规则；它们改用数学公式来调整优先级。比如，FreeBSD 调度器（4.3 版）用公式计算作业当前的优先级，依据是进程已用了多少 CPU [LM+89]；此外，用量还会随时间衰减，以一种不同于本章所述的方式提供所需的优先级提升。关于这类"衰减用量(decay-usage)"算法及其性质的出色综述，见 Epema 的论文 [E95]。

最后，许多调度器还有一些你可能遇到的其他特性。比如，有些调度器把最高优先级留给操作系统的工作；因此普通用户作业永远拿不到系统的最高优先级。有些系统还允许用户给出一些建议来帮助设定优先级；例如，用命令行工具 `nice` 你可以（在一定程度上）提高或降低作业的优先级，从而增加或减少它在任一时刻运行的机会。细节见手册页。

!!! tip "提示：尽可能利用建议"
    由于操作系统很少清楚什么对系统中的每个进程最好，提供接口让用户或管理员向操作系统给出一些提示往往很有用。我们常把这样的提示叫做**建议(advice)**，因为操作系统不必一定理会它，但可以把它纳入考虑，以作出更好的决策。这类提示在操作系统的许多部分都有用，包括调度器（比如 `nice`）、内存管理器（比如 `madvise`）和文件系统（比如告知式预取与缓存 [P+95]）。

## 8.6 MLFQ：小结

我们描述了一种叫做多级反馈队列（MLFQ）的调度方法。你现在大概明白它为什么叫这个名字了：它有多个层次的队列，并用反馈来决定某个作业的优先级。历史是它的向导：注意作业随时间如何表现，并据此对待它们。

本章中散落各处的、经过改良的 MLFQ 规则，这里再完整列一遍，供你欣赏：

* **规则 1**：如果 Priority(A) > Priority(B)，则运行 A（不运行 B）。
* **规则 2**：如果 Priority(A) = Priority(B)，则 A 和 B 以轮转方式运行，使用该队列的时间片（量子长度）。
* **规则 3**：作业进入系统时，放在最高优先级（最顶上的队列）。
* **规则 4**：一旦作业在某一层用完它的时间配额（无论它让出过多少次 CPU），就降低其优先级（也就是下移一个队列）。
* **规则 5**：经过某个时间段 $S$ 后，把系统中所有作业移到最顶上的队列。

MLFQ 有意思的地方在于：它不要求预先知道作业的性质，而是观察作业的执行、据此排定优先级。这样它就能两全其美：对运行时间短的交互式作业给出出色的整体性能（类似 SJF/STCF），同时对长时间运行的 CPU 密集负载保持公平、让它有进展。正因如此，许多系统——包括 BSD UNIX 家族 [LM+89, B86]、Solaris [M06] 以及 Windows NT 及其后续操作系统 [CS97]——都把某种形式的 MLFQ 用作基础调度器。

## 参考文献

[AD00] "Multilevel Feedback Queue Scheduling in Solaris" by Andrea Arpaci-Dusseau. Available: http://www.ostep.org/Citations/notes-solaris.pdf. 本书作者之一写的一组很棒的简短笔记，讲 Solaris 调度器的细节。好吧，我们这么说是有点偏心，但这些笔记确实相当不错。

[B86] "The Design of the UNIX Operating System" by M.J. Bach. Prentice-Hall, 1986. 讲述真实 UNIX 操作系统如何构建的经典老书之一；内核黑客的必读。

[C+62] "An Experimental Time-Sharing System" by F. J. Corbato, M. M. Daggett, R. C. Daley. IFIPS 1962. 有点难读，但它是多级反馈调度许多最初思想的源头。这些思想后来不少进了 Multics，而有人会说 Multics 是有史以来最有影响力的操作系统。

[CS97] "Inside Windows NT" by Helen Custer and David A. Solomon. Microsoft Press, 1997. NT 那本书，如果你想了解 UNIX 以外的东西。当然，你为什么会想呢？好吧，开个玩笑；说不定哪天你还真会给微软打工呢。

[E95] "An Analysis of Decay-Usage Scheduling in Multiprocessors" by D.H.J. Epema. SIGMETRICS '95. 一篇不错的论文，讲 20 世纪 90 年代中期调度的最新进展，包括对衰减用量调度器背后基本方法的良好综述。

[LM+89] "The Design and Implementation of the 4.3BSD UNIX Operating System" by S.J. Leffler, M.K. McKusick, M.J. Karels, J.S. Quarterman. Addison-Wesley, 1989. 又一本操作系统经典，由 BSD 背后四位核心人物写成。这本书的后续版本虽然更紧跟时代，却比不上这一版的美。

[M06] "Solaris Internals: Solaris 10 and OpenSolaris Kernel Architecture" by Richard McDougall. Prentice-Hall, 2006. 一本关于 Solaris 及其工作原理的好书。

[O11] "John Ousterhout's Home Page" by John Ousterhout. www.stanford.edu/~ouster/. 著名教授 Ousterhout 的主页。本书两位合著者读研时都有幸上过 Ousterhout 的研究生操作系统课；其实，两位合著者正是在那里相识，最终走向婚姻、孩子，乃至这本书。所以，你现在陷进的这堆烂摊子，还真得怪 Ousterhout。

[P+95] "Informed Prefetching and Caching" by R.H. Patterson, G.A. Gibson, E. Ginting, D. Stodolsky, J. Zelenka. SOSP '95, Copper Mountain, Colorado, October 1995. 一篇有趣的论文，讲文件系统里一些非常酷的想法，包括应用程序如何向操作系统给出建议：它在访问哪些文件、打算怎样访问。

[Y+18] "Principled Schedulability Analysis for Distributed Storage Systems using Thread Architecture Models" by Suli Yang, Jing Liu, Andrea C. Arpaci-Dusseau, Remzi H. Arpaci-Dusseau. OSDI '18, San Diego, California. 我们小组的一项新工作，展示了在现代分布式存储系统（如 Hive/HDFS、Cassandra、MongoDB、Riak）中调度 I/O 请求的困难。稍不留神，单个用户就可能独占系统资源。
