# 第 42 章 崩溃一致性：FSCK 与日志

> 英文原题：*Crash Consistency: FSCK and Journaling*

文件系统管理一组数据结构，以实现文件、目录以及支撑这些抽象的各种元数据。它们与运行中程序的内存数据结构不同，必须长期存在于断电后仍能保留信息的设备上，例如硬盘与闪存 SSD。

文件系统的一大挑战，是在断电或系统崩溃随时可能发生时更新持久数据结构。若更新磁盘结构进行到一半，有人绊到电源线怎么办？操作系统撞上 bug 当场倒下又怎么办？这个问题称为**崩溃一致性(crash consistency)**。

问题并不难理解。假设一次操作要更新磁盘结构 A 与 B，而磁盘一次只能处理一个请求，于是总有一个先落盘。若它完成后系统崩溃，磁盘状态就只更新了一半，A 与 B 彼此矛盾。

!!! danger "问题核心：系统崩溃时怎样更新磁盘"
    系统可能在任意两次写入之间崩溃或断电，磁盘状态因此只有部分更新。重启后还要重新挂载并使用文件系统。既然崩溃时刻不可预测，怎样保证磁盘映像始终处于合理状态？

本章先详细描述问题，再介绍两类解决方案。老式文件系统使用 `fsck`，即文件系统检查器；之后出现**日志(journaling)**，也称**预写日志(write-ahead logging, WAL)**。日志让每次写入多做一点工作，却能在崩溃后迅速恢复。我们还会讨论 Linux ext3 [T98, PAA05] 提供的几种日志模式。

## 42.1 一个详细示例

假设工作负载很简单：向已有文件追加一个数据块。程序打开文件，用 `lseek()` 移到末尾，写入 4 KB，再关闭。

微型文件系统含一张 8 位 inode 位图、一张 8 位数据位图、8 个 inode（编号 0～7，分布在 4 块中）和 8 个数据块（编号 0～7）。当前只分配了 inode 2 与数据块 4；inode 的第一个版本记为 `I[v1]`，已有数据块记为 `Da`：

```text
┌────────────┬────────────┬───────────────────────┬───────────────────────┐
│ inode 位图 │ 数据块位图 │        Inodes         │      Data Blocks      │
│   inode 2  │   block 4  │        I[v1]          │          Da           │
└────────────┴────────────┴───────────────────────┴───────────────────────┘
```

简化后的 `I[v1]`：

```text
owner       : remzi
permissions : read-write
size        : 1
pointer     : 4
pointer     : null
pointer     : null
pointer     : null
```

文件大小为 1 块，第一个直接指针指向块 4（`Da`），其他指针未使用。

追加时必须更新三个磁盘结构：inode 要记录新块与新大小；新数据块 `Db` 要写入；数据位图的新版本 `B[v2]` 要标记新块已经分配。内存中的新版 inode 为：

```text
owner       : remzi
permissions : read-write
size        : 2
pointer     : 4
pointer     : 5
pointer     : null
pointer     : null
```

`B[v2]` 为 `00001100`，`Db` 则装着用户写入的数据——也许是偷来的音乐？理想的最终状态是 inode 指向 `Da`、`Db`，位图也标记两块已用。

系统必须分别写 `I[v2]`、`B[v2]` 和 `Db`。这些写入通常不会在用户调用 `write()` 时立刻发生；脏 inode、位图和数据会先在页缓存或缓冲缓存中待 5～30 秒，再发给磁盘。若只完成一部分时崩溃，文件系统就会进入某种滑稽——对用户而言通常并不好笑——的状态。

### 崩溃场景

若只有一次写入成功，有三种结果：

1. **只写入 `Db`**：数据在盘上，却没有 inode 指向它，位图也称它空闲。文件系统看来此次写入从未发生，一致性没有问题；用户刚丢了数据，可能会对“一致性没问题”这句话另有看法。
2. **只写入 `I[v2]`**：inode 指向块 5，但 `Db` 尚未写入，读取会得到块 5 的旧垃圾内容。位图称块 5 空闲、inode 却称它已用，元数据也不一致。
3. **只写入 `B[v2]`**：位图称块 5 已分配，却没有 inode 指向它，形成**空间泄漏(space leak)**；若不修复，这块空间永远无法使用。

若两次写入成功、最后一次失败，也有三种结果：

1. **inode 与位图成功，数据失败**：元数据完全自洽，但 inode 指向垃圾。
2. **inode 与数据成功，位图失败**：数据正确，inode 也指向它，但旧位图称块 5 空闲，仍不一致。
3. **位图与数据成功，inode 失败**：块已经写好、位图也称它已用，却没有任何 inode 表明它属于哪个文件。

可见崩溃会造成数据结构不一致、空间泄漏、向用户返回垃圾等问题。理想情况是文件系统从追加前的一致状态，**原子地**切换到 inode、位图、数据全已更新的另一一致状态；但磁盘逐次提交写入，崩溃又可能插在中间，这就是崩溃一致性问题，也可称**一致更新问题(consistent-update problem)**。

## 42.2 方案一：文件系统检查器

早期文件系统采取一种朴素办法：先允许不一致发生，重启时再修。典型工具是 UNIX 的 `fsck` [M86]。不同系统也有类似的分区检查修复工具。

`fsck` 不能修好一切；若元数据自洽但 inode 指向垃圾，它便无从知道。目标只是让文件系统**元数据内部一致**。它在挂载文件系统之前运行，并假设期间没有其他文件系统活动；完成后，磁盘状态应足够一致，可以交给用户。

按照 McKusick 与 Kowalski [MK96] 的总结，基本阶段如下：

- **超级块**：检查文件系统大小应大于已分配块数等基本合理性。若主超级块疑似损坏，系统或管理员可改用备份副本。
- **空闲块**：扫描 inode、间接块、二级间接块等，重新确定哪些块已分配，据此生成正确的分配位图。位图与 inode 冲突时信任 inode。也检查所有看似在用的 inode 是否在 inode 位图中标为已用。
- **inode 状态**：检查每个 inode 是否损坏，例如已分配 inode 的类型是否为合法的普通文件、目录或符号链接。难以修复的可疑 inode 会被清除，位图也相应更新。
- **inode 链接**：从根开始扫描整棵目录树，重新计算每个文件与目录被引用的次数，与 inode 链接计数比较；不匹配时通常修正 inode。若某 inode 已分配却没有目录引用，就把它移到 `lost+found`。
- **重复指针**：检查两个 inode 是否指向同一块。若某 inode 显然损坏，可清除它；也可复制被指向的块，让两个 inode 各有一份。
- **坏块**：扫描指针时检查是否越界，例如指向分区之外。`fsck` 也变不出聪明办法，只能从 inode 或间接块中清除坏指针。
- **目录检查**：`fsck` 不理解用户文件内容，却知道目录的特定格式。它会确认 `.`、`..` 位于开头，目录项指向的 inode 已分配，并保证目录层次中没有一个目录被链接多次。

实现可靠的 `fsck` 需要深入理解文件系统，让所有边角情况都正确相当困难 [G+08]。更根本的问题是它太慢：大卷需要扫描全部磁盘与整棵目录树，可能耗费数十分钟乃至数小时；磁盘容量和 RAID 规模增长后，代价越发不可接受，尽管近年已有改进 [M+13]。

从更高层看，这个思路也略显不理性。刚才只更新了三个块，修复时却扫描整块磁盘，好比钥匙掉在卧室地板上，你却启动“搜遍整栋房子找钥匙”算法，从地下室开始逐屋翻箱倒柜。它能奏效，只是浪费得很有仪式感。

顺带一提，`fsck` 可以念 “eff-ess-see-kay” 或 “eff-ess-check”；若你不喜欢它，也有人念成 “eff-suck”。是的，严肃的专业人士真的这么说。

## 42.3 方案二：日志（预写日志）

最流行的解决方案从数据库管理系统借来：**预写日志**。文件系统因历史原因通常称它为**日志记录(journaling)**。Cedar [H87] 最早将其用于文件系统，Linux ext3/ext4、reiserfs、IBM JFS、SGI XFS、Windows NTFS 等现代系统都采用了这一思想。

基本做法是：覆盖原位置之前，先在磁盘上一个已知位置写张“小纸条”，说明马上要做什么。这张纸条放入**日志(log/journal)**，所以叫“预写”。若覆盖途中崩溃，重启后读纸条并重做即可；无需扫描全盘，就知道要修什么、怎样修。日志让日常更新多付一点成本，换取恢复时少做大量工作。

以 Linux ext3 为例，它大部分结构与 ext2 相同：磁盘分成块组，每组有 inode 位图、数据位图、inode 和数据块。新增的关键结构是日志，可位于分区的一小块区域、另一设备，或文件系统内的一个文件。

```text
ext2: [ Super ][ Group 0 ][ Group 1 ] ... [ Group N ]
ext3: [ Super ][ Journal ][ Group 0 ][ Group 1 ] ... [ Group N ]
```

### 数据日志

仍要更新 `I[v2]`、`B[v2]`、`Db`。在写最终位置之前，先把它们放进日志：

```text
[ TxB ][ I[v2] ][ B[v2] ][ Db ][ TxE ]
```

`TxB` 是**事务开始(transaction begin)**块，记录待更新块的最终地址和事务标识符 TID。中间三块保存更新的精确物理内容，这叫**物理日志(physical logging)**。另一种**逻辑日志(logical logging)**只记录“把 `Db` 追加到文件 X”之类更紧凑的操作描述，能省空间、可能更快，但也更复杂。`TxE` 标记事务结束，并携带同一 TID。

事务安全落到日志后，系统把 `I[v2]`、`B[v2]`、`Db` 写到最终位置，这叫**检查点(checkpointing)**。最初的协议为：

1. **日志写入**：把 `TxB`、所有待提交数据与元数据、`TxE` 写入日志，并等待完成。
2. **检查点**：把更新的数据与元数据写到文件系统最终位置。

但日志写入期间也可能崩溃。逐块写并逐块等待很安全，却很慢；若把五块作为一次顺序写发出，磁盘内部又可能重排成先写 `TxB`、`I[v2]`、`B[v2]`、`TxE`，最后才写 `Db`。若倒数第二步后断电，日志看似有首尾匹配的完整事务，中间 `Db` 位置却是垃圾；恢复时会把垃圾复制到最终位置。若那是用户数据已经很糟，若是超级块等关键元数据，整个文件系统可能无法挂载。

解决办法是分两步提交：先并发写除 `TxE` 外的所有块并等待完成，再单独写 `TxE`。磁盘保证单次 512 字节写要么完整发生、要么完全不发生，因此 `TxE` 应装进一个 512 字节块。协议变为：

1. **日志写入**：写 `TxB`、元数据和数据，等待完成。
2. **日志提交**：写含 `TxE` 的提交块并等待；此后事务称为已提交。
3. **检查点**：把元数据和数据写到最终位置。

!!! note "边栏：强制写入磁盘"
    过去要保证 A 先于 B，只需写 A、等待磁盘中断确认，再写 B。磁盘加入写缓存后，事情复杂了：有些设备把数据放进自身内存就向操作系统报告完成，尚未真正落盘；后续 B 可能先到持久介质。

    可以禁用写缓冲；现代系统也会发出显式**写屏障(write barrier)**，屏障完成后，可保证屏障前的写入先于屏障后的写入落盘。

    这一切都依赖磁盘诚实工作。遗憾的是，研究发现有些制造商为了让设备看起来“性能更高”，会无视写屏障 [C+13, R+11]，以正确性换跑分。正如 Kahan 所言，快的几乎总会击败慢的——哪怕快的是错的。

!!! note "边栏：优化日志写入"
    先写 `TxB` 与事务内容、等待完成，再写 `TxE`，通常多付一次磁盘旋转。Vijayan Prabhakaran 提出简单修复 [P+05]：在事务首尾保存日志内容的校验和。这样可以一次写出整个事务；恢复时若计算值与记录值不符，就知道写到一半发生了崩溃，丢弃此次更新。

    这项小改动让常见路径更快，还让日志读取受校验和保护、更可靠。Linux 文件系统开发者把它纳入下一代系统——你猜对了，ext4。它随 Android 等平台运行在数百万台设备上；许多 Linux 系统每次写盘时，都有一点 Wisconsin 写出的代码让它更快、更可靠。

### 恢复

若第 2 步完成前崩溃，事务尚未安全提交，恢复时直接跳过。若已提交、但检查点尚未完成，启动时扫描日志，找到已提交事务，按顺序**重放(replay)**，再次把其中各块写到最终位置。这种最简单的日志形式称为**重做日志(redo logging)**。

检查点执行到任何位置都可崩溃；最坏不过是恢复时重复写几块。恢复只在意外崩溃后发生，几次冗余写没什么可担心的——除非你什么都担心，那我们也没办法。少操点心，对健康有好处！不过你现在可能开始担心自己担心得太多了。

### 批处理日志更新

基本协议可能带来大量额外流量。若在同一目录接连创建 `file1`、`file2`，每次都要更新 inode 位图、新 inode、父目录数据和父目录 inode；若两个新 inode 还位于同一 inode 块，不加小心就会反复写同一批块。

Linux ext3 等系统不会逐项提交，而把更新缓冲进一个全局事务。内存中的 inode 位图、文件 inode、目录数据和目录 inode 先标脏并加入当前事务，等 5 秒之类的超时到来后，一次性提交。批处理因此能避免大量重复写。

### 让日志保持有限

日志空间有限，一直追加事务很快会填满：

```text
[ Tx1 ][ Tx2 ][ Tx3 ][ Tx4 ][ Tx5 ] ...
```

日志越大，恢复时要重放的事务越多；完全写满后，新事务无法提交，文件系统就变得“不太有用”——学名叫没用了。

日志文件系统把它当成**循环日志(circular log)**反复使用。事务完成检查点后，系统释放其日志空间。日志超级块可以记录最老和最新的尚未检查点事务，其他区域即可复用；注意日志超级块不是文件系统主超级块。

最终的数据日志协议是：

1. **日志写入**：写 `TxB` 和更新内容，等待完成。
2. **日志提交**：写 `TxE`，等待完成，事务已提交。
3. **检查点**：把更新写到文件系统最终位置。
4. **释放**：稍后更新日志超级块，标记该事务空间可复用。

问题仍在：每个数据块写两次，为很少发生的崩溃付出沉重日常代价。能否既保持一致，又不重复写用户数据？

### 元数据日志

全数据日志恢复很快，却让每块数据先写日志、再写最终位置，写流量翻倍；顺序写吞吐量可能只有磁盘峰值一半，日志区与主文件系统之间的寻道也不便宜。

更常见的**有序日志(ordered journaling)**，也叫**元数据日志(metadata journaling)**，只记录元数据，不把用户数据写进日志：

```text
日志：[ TxB ][ I[v2] ][ B[v2] ][ TxE ]
数据：Db 只写到文件系统最终位置
```

磁盘 I/O 大多是数据，因此避免重复写数据会显著减负。但 `Db` 何时写很重要。若在元数据事务提交后才写，崩溃可能让恢复重放 `I[v2]` 与 `B[v2]`，得到元数据一致、inode 却指向垃圾的系统。

因此 ext3 等先把普通文件数据写到最终位置，再提交相关元数据：

1. **写数据**：把数据写到最终位置并完成；严格等待可以放宽，见下文。
2. **写日志元数据**：写 `TxB` 与元数据，等待完成。
3. **日志提交**：写 `TxE` 并等待，事务（包括数据）已提交。
4. **元数据检查点**：把元数据更新写到最终位置。
5. **释放**：稍后在日志超级块中标记事务空间可复用。

“先写被指向的对象，再写指向它的对象”是崩溃一致性的核心规则，Soft Updates 等方案还会进一步利用它 [GP94]。

多数系统更青睐元数据日志。Windows NTFS 与 SGI XFS 都采用某种形式；Linux ext3 可选 data、ordered 或 unordered 模式。三者都保持元数据一致，用户数据语义则不同。

正确性并不要求数据写在第 2 步之前单独等待完成。数据、`TxB` 和日志元数据可以并发发出，只要数据写与日志元数据都在发出 `TxE` 前完成即可。

### 棘手情况：块复用

块复用带来许多边角问题。ext3 的主要设计者 Stephen Tweedie 说：“整个系统最可怕的部分是什么？……删除文件。凡是跟删除有关的都很难搞。删除的一切……一想到块被删除后又重新分配会发生什么，你就做噩梦。”[T00]

假设使用元数据日志，目录 `foo` 位于块 1000。用户向它加入目录项，于是目录数据作为元数据写入日志：

```text
[ TxB id=1 ][ I[foo] ptr:1000 ][ D[foo] final:1000 ][ TxE id=1 ]
```

随后用户删除目录全部内容和 `foo` 本身，块 1000 被释放；再创建文件 `foobar`，恰好复用块 1000。其 inode 进入日志，数据只写最终位置：

```text
[ 事务 1：foo 的旧目录数据 -> 1000 ][ 事务 2：I[foobar] -> 1000 ]
```

若此时崩溃且两项仍在日志中，恢复按顺序重放时会把事务 1 的旧目录内容重新写到块 1000，覆盖 `foobar` 的用户数据。用户打开文件发现里面突然是一段旧目录，惊喜程度可想而知。

一种方案是等删除事务完成检查点后才复用块。Linux ext3 则在日志中加入**撤销记录(revoke record)**：删除目录时记录块已撤销；恢复先扫描所有撤销记录，被撤销的数据绝不重放。

### 用时间线收束日志协议

数据日志中，`TxB` 与事务内容可以同时发出、以任意顺序完成；它们全部完成后才能发 `TxE`。`TxE` 提交后，才能向最终位置写数据与元数据检查点：

| 顺序 | 日志 | 文件系统元数据 | 文件系统数据 |
|---:|---|---|---|
| 1 | 发出 `TxB` 与事务内容 | — | — |
| 2 | 二者均完成 | — | — |
| 3 | 发出并完成 `TxE` | — | — |
| 4 | — | 发出检查点写 | 发出检查点写 |
| 5 | — | 完成 | 完成 |

*图 42.1：数据日志时间线。阶段之间的顺序屏障必须遵守；阶段内部完成次序可变化。*

元数据日志中，用户数据可与 `TxB` 和日志元数据同时发出，但数据和日志内容都必须在发出 `TxE` 前完成：

| 顺序 | 日志 | 文件系统元数据 | 文件系统数据 |
|---:|---|---|---|
| 1 | 发出 `TxB` 与元数据 | — | 发出数据写 |
| 2 | 日志内容完成 | — | 数据写完成 |
| 3 | 发出并完成 `TxE` | — | — |
| 4 | — | 发出并完成元数据检查点 | — |

*图 42.2：元数据日志时间线。*

图中的具体完成时刻只是示意；实际 I/O 子系统会为性能重排写入。唯一固定的是协议正确性要求的那些顺序。

## 42.4 方案三：其他方法

`fsck` 和日志并非仅有的选择。

**Soft Updates** [GP94] 由 Ganger 与 Patt 提出。它仔细排列所有文件系统写入，使磁盘结构永不进入不一致状态。例如先写数据块，再写指向它的 inode，便不会让 inode 指向垃圾。可为全部结构推导类似规则。它实现起来颇具挑战：日志层不必深知每种结构的细节，Soft Updates 却必须深入理解它们，系统复杂度也随之上升。

**写时复制(copy-on-write, COW)**用于 Sun ZFS [B07] 等文件系统。它不在原位置覆盖文件或目录，而把更新写到未使用位置；一批更新完成后，再切换文件系统根结构，让它指向新结构。一致性因此较易保持。后面讨论日志结构文件系统 LFS 时会继续研究；LFS 是 COW 的早期例子。

Wisconsin 团队还提出**基于反向指针的一致性(backpointer-based consistency, BBC)** [C+12]，不强制写入顺序，而给每个块增加反向指针。例如数据块记录自己属于哪个 inode。访问文件时，检查 inode 的正向指针所到之块是否反指回来；匹配说明双方已安全落盘，不匹配则说明不一致并返回错误。反向指针由此实现一种新的惰性崩溃一致性。

最后是**乐观崩溃一致性(optimistic crash consistency)** [C+13]。它用事务校验和 [P+05] 的推广形式尽量并发发出写入，再用其他技术检测可能的不一致，减少日志协议等待磁盘完成的次数。有些负载能加速一个数量级，不过要发挥良好，还需要略有不同的磁盘接口。

## 42.5 小结

本章介绍了崩溃一致性及其解决方法。传统文件系统检查器能够修复元数据，却可能慢得无法适应现代大容量系统。日志把恢复复杂度从 $O(\text{磁盘卷大小})$ 降为 $O(\text{日志大小})$，所以现代文件系统广泛采用。

日志也有多种形式。最常见的是有序元数据日志：它减少日志流量，同时为文件系统元数据和用户数据提供合理的一致性保证。归根结底，对用户数据提供强保证恐怕是最重要的事情之一；奇怪的是，近期研究表明，这项工作至今仍未真正结束 [P+14]。

## 参考文献

- [B07] “ZFS: The Last Word in File Systems” by Jeff Bonwick and Bill Moore. ZFS 同时使用写时复制与日志，因为某些情况下把写入记入日志性能更好。
- [C+12] “Consistency Without Ordering” by Vijay Chidambaram et al. FAST '12. 基于反向指针的新型崩溃一致性；刺激细节尽在正文。
- [C+13] “Optimistic Crash Consistency” by Vijay Chidambaram et al. SOSP '13. 性能更高的乐观日志协议；对频繁调用 `fsync()` 的负载，改善显著。
- [GP94] “Metadata Update Performance in File Systems” by Gregory R. Ganger and Yale N. Patt. OSDI '94. 以谨慎安排写入顺序实现一致性的巧妙论文，后来用于 BSD 系统。
- [G+08] “SQCK: A Declarative File System Checker” by Haryadi S. Gunawi et al. OSDI '08. 用 SQL 查询构建文件系统检查器的新方法，也揭示传统检查器因 `fsck` 复杂性而产生的大量 bug 与怪异行为。
- [H87] “Reimplementing the Cedar File System Using Logging and Group Commit” by Robert Hagmann. SOSP '87. 据我们所知，最早把预写日志用于文件系统的工作。
- [M+13] “ffsck: The Fast File System Checker” by Ao Ma et al. FAST '13. 让 `fsck` 加速一个数量级；部分思想已进入 BSD 检查器并实际部署。
- [MK96] “Fsck – The UNIX File System Check Program” by Marshall Kirk McKusick and T. J. Kowalski. Revised 1996. 描述第一套全面的同名文件系统检查工具，作者也参与了 FFS。
- [MJLF84] “A Fast File System for UNIX” by Marshall K. McKusick et al. *ACM TOCS* 2:3, 1984. 你已经很了解 FFS 了，对吧？不过重要论文重复引用完全没问题。
- [P+14] “All File Systems Are Not Created Equal: On the Complexity of Crafting Crash-Consistent Applications” by Thanumalayan S. Pillai et al. OSDI '14. 研究崩溃后文件系统真正保证什么，并说明应用期望往往不同，由此滋生各种有趣问题。
- [P+05] “IRON File Systems” by Vijayan Prabhakaran et al. SOSP '05. 主要研究文件系统面对磁盘故障的反应；末尾提出事务校验和，后来被 Linux ext4 采用。
- [PAA05] “Analysis and Evolution of Journaling File Systems” by Vijayan Prabhakaran, Andrea C. Arpaci-Dusseau, Remzi H. Arpaci-Dusseau. USENIX '05. 对日志文件系统工作方式的早期分析。
- [R+11] “Coerced Cache Eviction and Discreet-Mode Journaling” by Abhishek Rajimwale et al. DSN '11. 研究磁盘明明被要求落盘却仍把写入留在内存缓存的问题。其解法颇妙但不太实用：若要 A 先于 B，先写 A，再塞给磁盘大量“虚假”写入，希望缓存被挤满后不得不把 A 落盘。
- [T98] “Journaling the Linux ext2fs File System” by Stephen C. Tweedie. Linux Expo, 1998. Tweedie 为 ext2 加日志做了大量工作，结果自然叫 ext3；设计特别重视向后兼容，例如给现有 ext2 加一个日志文件便可按 ext3 挂载。
- [T00] “EXT3, Journaling Filesystem” by Stephen Tweedie. Ottawa Linux Symposium, July 2000. Tweedie 关于 ext3 演讲的文字稿。
- [T01] “The Linux ext2 File System” by Theodore Ts’o. June 2001. 基于 FFS 思想的简单 Linux 文件系统，曾广泛使用，如今仍作为简单实现范例留在内核中。
