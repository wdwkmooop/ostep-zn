# 第 23 章 完整虚拟内存系统

> 英文原题：*Complete Virtual Memory Systems*

在结束内存虚拟化的学习之前，先来仔细看看一整套虚拟内存系统到底是怎么拼装起来的。这类系统的关键部件我们其实都见过了：各种页表设计、与 TLB 的交互（有时候连 TLB 都由操作系统亲自打理），以及决定哪些页留在内存、哪些页踢出去的策略。不过，一套完整的虚拟内存系统还包含许多别的特性，涉及性能、功能和安全。于是就有了我们的问题核心：

!!! danger "问题核心"
    **如何构建一套完整的虚拟内存系统？**

    要实现一套完整的虚拟内存系统，需要哪些特性？它们如何提升性能、增强安全，或者以别的方式改进系统？

接下来，我们会讲两套系统。第一套是最早的"现代"虚拟内存管理器之一，出自 VAX/VMS 操作系统 [LL82]，诞生于 20 世纪 70 年代到 80 年代初。从这套系统里冒出来的技术和方法多得惊人，至今仍在沿用，因此非常值得研究。有些想法哪怕已经 50 岁了，也依然值得了解——这在物理学之类的大多数领域里是常识，可在计算机科学这种由技术驱动的学科里，却得特意强调一下。第二套是 Linux，理由不言自明。Linux 使用广泛，从手机这种又小又弱的设备，到现代数据中心里可扩展性极强的多核机器，都能跑得起来。因此，它的虚拟内存系统必须足够灵活，才能在这所有场景下都成功运行。我们会逐一讨论这两套系统，展示前面各章提出的概念是如何在一套完整的内存管理器里汇合的。

## 23.1 VAX/VMS 虚拟内存

VAX-11 小型机(minicomputer)架构由数字设备公司(Digital Equipment Corporation, DEC)在 20 世纪 70 年代末推出。在小型机时代，DEC 是计算机行业里的巨头；可惜一连串错误决策，再加上个人电脑的兴起，慢慢（却确凿地）把它带向了灭亡 [C03]。这套架构有好几款实现，包括 VAX-11/780 和性能较弱的 VAX-11/750。

该系统的操作系统叫 VAX/VMS（或者干脆简称 VMS），主要架构师之一是 Dave Cutler，他后来主导了微软 Windows NT 的开发 [C93]。VMS 面临一个普遍的难题：它要跑在各种各样、跨度极大的机器上，从最便宜的 VAXen（对，这就是它的正确复数形式）到同一架构家族里极其高端强悍的机器。因此，这套操作系统必须拥有能跨越这般巨大范围、都能正常运行（而且运行良好）的机制和策略。

还有一个问题：VMS 是绝佳的例子，展示了如何用软件上的创新去掩盖架构的某些固有缺陷。操作系统常常依赖硬件来搭建高效的抽象和幻觉，可有时候硬件设计师未必样样都做对。在 VAX 硬件里我们就会看到几个这样的例子，以及 VMS 操作系统如何在硬件有缺陷的情况下，照样搭出一套有效、能用的系统。

### 内存管理硬件

VAX-11 为每个进程提供 32 位的虚拟地址空间(virtual address space)，按 512 字节的页划分。于是，一个虚拟地址由 23 位的虚拟页号(virtual page number, VPN) 和 9 位的偏移组成。此外，VPN 的最高两位用来区分页落在哪个段里；所以这套系统是我们之前见过的分页与分段的混合体。

地址空间的低半部分叫"进程空间(process space)"，每个进程各不相同。在进程空间的前半（称为 P0），放的是用户程序，以及一个向下增长的堆。在进程空间的后半（P1），是向上增长的栈。地址空间的高半部分叫系统空间(system space, S)，不过只用到一半。受保护的操作系统代码和数据就住在这里，操作系统由此在各进程之间共享。

VMS 设计师的一大顾虑，是 VAX 硬件里页小得离谱（512 字节）。这个大小是出于历史原因选的，却有个根本毛病：它会让简单的线性页表大得不像话。因此，VMS 设计师的头号目标之一，就是确保 VMS 不会让页表把内存撑爆。

系统从两方面减轻了页表给内存带来的压力。第一，把用户地址空间一分为二后，VAX-11 就为每进程的每个区域（P0 和 P1）各提供一张页表(page table)；

!!! note "边栏：通用性的诅咒"
    操作系统常常碰到一个叫"通用性的诅咒(the curse of generality)"的麻烦：它的任务是为一整大类应用和系统提供通用支持。这个诅咒的根本结果是，操作系统往往没法把任何一种具体安装伺候得特别好。就 VMS 而言，这个诅咒真实得很，因为 VAX-11 架构被实现成了好几种不同的型号。今天它也一样真实：人们指望 Linux 能跑好你的手机、电视顶置盒、笔记本电脑、台式机，以及云端数据中心里跑着成千上万进程的高端服务器。

于是，栈和堆之间那片没用到的地址空间，就完全不需要页表空间了。基址和界限寄存器按你预期的方式使用：基址寄存器存放该段页表的地址，界限寄存器存放它的大小（也就是页表项的数量）。

第二，操作系统把用户页表（P0 和 P1 各一张，因此每进程两张）放进内核虚拟内存，进一步减轻内存压力。这样，在分配或扩大页表时，内核就从自己的虚拟内存里、在段 S 中分配空间。一旦内存压力吃紧，内核可以把这些页表的页交换到磁盘，从而把物理内存腾出来另作他用。

把页表放进内核虚拟内存，意味着地址转换变得更加复杂。比如，要转换 P0 或 P1 里的一个虚拟地址，硬件得先去页表里查那一页的页表项（即该进程的 P0 或 P1 页表）；可这么一查，硬件可能又得先查系统页表（它住在物理内存里）；这次转换完成后，硬件才知道页表所在页的地址，最后才能知道想要的这次内存访问的地址。所幸，VAX 的硬件管理 TLB 让这一切变快了——它通常（但愿）能绕过这番繁琐的查找。

### 一个真实的地址空间

研究 VMS 有个妙处：我们能亲眼看到真实的地址空间是怎么构造的（图 23.1）。在此之前，我们假设的地址空间很简单，只有用户代码、用户数据和用户堆；可从上面可以看到，真实的地址空间明显复杂得多。

比如，代码段从不从 0 号页开始。0 号页反而被标记为不可访问，以便对空指针(null pointer) 访问提供一些检测支持。所以，设计地址空间时的一个考量就是支持调试——这里那个不可访问的 0 号页就以某种形式提供了这种支持。

```text
0x00000000  +---------------------------+
            |  Page 0: Invalid          |  ← 0 号页：无效
            +---------------------------+
            |  User Code                |
            +---------------------------+
            |  User Heap                |
            |                           |
            |                           |  ← User (P0)
0x40000000  +---------------------------+  (2^30)
            |                           |
            |  User Stack               |  ← User (P1)
0x80000000  +---------------------------+  (2^31)
            |  Trap Tables              |
            +---------------------------+
            |  Kernel Data              |
            +---------------------------+
            |  Kernel Code              |
            +---------------------------+
            |  Kernel Heap              |  ← System (S)
            +---------------------------+
            |  Unused                   |
0xFFFFFFFF  +---------------------------+  (2^32)
```

*图 23.1：VAX/VMS 地址空间。*

更重要的是，内核虚拟地址空间（也就是它的数据结构和代码）是每个用户地址空间的一部分。上下文切换时，操作系统会修改 P0 和 P1 寄存器，让它们指向即将运行的进程对应的页表；但它不会修改 S 的基址和界限寄存器，结果就是"同一份"内核结构被映射进了每个用户地址空间。

内核之所以被映射进每个地址空间，原因有若干。这种构造让内核的日子更好过：比如，当操作系统收到来自用户程序的一个指针时（例如在某次 `write()` 系统调用里），从那个指针往自己的结构里拷贝数据就很方便。操作系统自然地编写、编译，完全不用操心它访问的数据究竟来自哪里。反过来，如果内核整个待在物理内存里，那像把页表的页交换到磁盘这类事情就很难办；如果给内核单独一个地址空间，

!!! note "边栏：为什么空指针访问会导致段错误"
    你现在应该已经清楚空指针解引用时到底发生了什么。进程通过类似下面的操作生成一个虚拟地址 0：

    ```c
    int *p = NULL; // 令 p = 0
    // 试图把 10 写入虚拟地址 0
    *p = 10;
    ```

    硬件试着在 TLB 里查这个 VPN（这里也是 0），遭遇一次 TLB 缺失。接着去查页表，发现 VPN 0 对应的页表项被标记为无效。于是这是一次非法访问，控制权转交给操作系统，而操作系统多半会终止这个进程（在 UNIX 系统上，进程会收到一个信号，允许它对这种错误作出反应；但如果没有捕获这个信号，进程就会被杀掉）。

那么在用户应用程序和内核之间搬数据，又会变得既复杂又痛苦。有了这种构造（如今被广泛采用），内核在应用程序眼里几乎就像个库，只不过是有保护的那种。

关于这个地址空间，最后一点跟保护有关。显然，操作系统不希望用户应用程序读写操作系统的数据或代码。因此，硬件必须支持对页施加不同的保护级别。VAX 的做法是：在页表的保护位里指明 CPU 必须处于哪个特权级，才能访问某个特定的页。这样，系统数据和代码被设成比用户数据和代码更高的保护级别；用户代码若试图访问这类信息，就会触发一次陷入、进入操作系统，然后（你猜到了）这个惹事的进程多半会被终止。

### 页替换

VAX 的页表项（page table entry, PTE）包含这些位：一个有效位、一个保护字段（4 位）、一个修改（也叫脏）位、一个留给操作系统使用的字段（5 位），最后是一个物理帧号(physical frame number, PFN)，用来记录该页在物理内存中的位置。眼尖的读者可能会发现：居然没有引用位(reference bit)！因此，VMS 的替换算法必须在没有硬件支持的情况下，设法判断哪些页是活跃的。

开发人员还担心"内存饕餮(memory hog)"，也就是那些占用大量内存、让其他程序难以运行的程序。我们目前见过的多数策略都容易被这类饕餮钻空子；比如，LRU 是一种全局策略，并不会在进程之间公平地分配内存。

为了解决这两个问题，开发人员提出了**分段 FIFO 替换策略(segmented FIFO replacement policy)** [RL81]。思路很简单：每个进程有一个它能保留在内存里的最大页数，称为它的常驻集大小(resident set size, RSS)。这些页各自放在一条 FIFO 链表上；当

!!! note "边栏：模拟引用位"
    事实证明，你并不需要硬件的引用位，也能对系统里哪些页正在被使用有个大致的判断。实际上，早在 20 世纪 80 年代初，Babaoglu 和 Joy 就表明，VAX 上的保护位可以用来模拟引用位 [BJ81]。基本思路是：如果你想了解系统里哪些页正在被积极使用，就把页表里所有页都标记为不可访问（但要保留"进程其实能访问哪些页"这一信息，也许放在页表项里"保留给操作系统"的那部分字段里）。当进程访问某一页时，它会触发一次陷入、进入操作系统；操作系统随后检查这一页是否真的应该可访问，如果是，就把这一页恢复成它正常的保护属性（比如只读，或可读可写）。在替换发生时，操作系统可以检查哪些页仍然被标记为不可访问，从而大致了解哪些页近期没被用到。

    这种引用位"模拟"的关键，是在仍能较好地掌握页使用情况的同时降低开销。操作系统在把页标记为不可访问时不能太激进，否则开销会太高。操作系统也不能太被动，否则所有页最后都会变成被引用过，操作系统同样无从判断该逐出哪一页。

进程超出它的 RSS 时，就把"最先进入"的那一页逐出。FIFO 显然不需要硬件的任何支持，因此容易实现。

当然，纯 FIFO 的表现并不特别好，如我们前面所见。为了改进 FIFO 的性能，VMS 引入了两条"二次机会(second-chance)"链表，页在被逐出内存之前会先放进去，具体来说是一条全局干净页空闲链表(clean-page free list)和一条脏页链表(dirty-page list)。当进程 P 超出它的 RSS 时，就从它的每进程 FIFO 里移除一页；如果这页是干净的（未被修改），就放到干净页链表的末尾；如果是脏的（被修改过），就放到脏页链表的末尾。

如果另一个进程 Q 需要一个空闲页，它就从全局干净链表上取走第一个空闲页。不过，如果原来那个进程 P 在这页被回收之前又访问它而缺页，P 就把它从空闲（或脏）链表里收回，从而避免一次昂贵的磁盘访问。这些全局二次机会链表越大，分段 FIFO 算法的表现就越接近 LRU [RL81]。

VMS 用到的另一项优化，也有助于克服 VMS 页太小的问题。具体来说，页这么小，交换期间的磁盘 I/O 可能效率极低，因为磁盘更擅长大的传输。为了让交换 I/O 更高效，VMS 加了不少优化，但最重要的是**成簇(clustering)**。有了成簇，VMS 把全局脏链表里的大批页聚到一起，一口气写到磁盘（从而把它们变干净）。成簇在大多数现代系统里都有用，因为能自由地把页放到交换空间里的任意位置，操作系统就可以把页聚成群，执行更少、更大的写操作，进而提升性能。

### 其他高明的小把戏

VMS 还有两个如今已成标配的小把戏：按需置零(demand zeroing)和写时复制(copy-on-write)。下面介绍这两项"惰性(lazy)"优化。VMS（以及大多数现代系统）里的一种惰性，就是页的按需置零。为了更好地理解它，我们设想这样一个例子：往你的地址空间里加一页，比如在你的堆里。在朴素的实现里，操作系统响应"往堆里加一页"的请求时，会在物理内存里找一页，把它清零（出于安全考虑，必须清零；否则你就能看到别的进程用这页时留下的内容！），然后把它映射进你的地址空间（也就是设置好页表，让它按需指向那个物理页）。但朴素实现可能很昂贵，尤其是当这一页根本没被进程用上的时候。

有了按需置零，操作系统在页被加进你的地址空间时几乎什么都不用做；它只在页表里放一个条目，把这一页标记为不可访问。如果进程随后读或写这一页，就会触发一次陷入、进入操作系统。处理这次陷入时，操作系统会注意到（通常是通过页表项里"保留给操作系统"那部分的一些标记位）这其实是一个按需置零页(demand-zero page)；这时，操作系统才去做必要的工作：找一个物理页，清零，再映射进进程的地址空间。如果进程从来不访问这一页，所有这些工作就都免了——这就是按需置零的好处。

VMS 里另一个很酷的优化（同样，几乎每个现代操作系统里也有）是写时复制(copy-on-write, COW)。这个想法至少能追溯到 TENEX 操作系统 [BB+72]，很简单：当操作系统需要把一页从一个地址空间复制到另一个地址空间时，它不复制，而是把这页映射进目标地址空间，并在两个地址空间里都标记为只读。如果两个地址空间都只读这一页，那就没有任何后续动作，操作系统于是实现了一次快速复制，却没有真正搬动任何数据。

然而，如果其中一个地址空间确实试图改写这一页，就会陷入操作系统。操作系统随后会注意到这是一页 COW 页，于是（惰性地）分配一个新页，填入数据，再把这个新页映射进出错进程的地址空间。进程接着运行，现在它有了自己私有的这一页副本。

COW 有用的原因有很多。任何形式的共享库显然都可以写时复制地映射进许多进程的地址空间，从而省下宝贵的内存。在 UNIX 系统里，由于 `fork()` 和 `exec()` 的语义，COW 更是至关重要。你可能还记得，`fork()` 会为调用者创建一份地址空间的精确副本；地址空间一大，做这样的副本就又慢又费数据。更糟的是，这份地址空间的大部分很快又会被随后的一次 `exec()` 调用覆盖掉——`exec()` 会用那个即将被执行的程序，盖住调用进程的地址空间。而改成执行写时复制的 `fork()`，操作系统就省掉了大量多余的复制，既保住了正确的语义，又提升了性能。

!!! tip "提示：保持惰性"
    在生活里和在操作系统里一样，懒惰都可以是一种美德。懒惰可以把活儿拖到以后再干，这在操作系统里有若干好处。第一，把活儿往后推可能降低当前操作的延迟，从而提升响应性；比如，操作系统常常先报告对文件的写已经成功，之后才在后台把它真正写到磁盘。第二，而且更重要的是，懒惰有时能干脆免掉这些活儿；比如，把写操作一直拖到文件被删除，就完全没必要写了。懒惰在生活里也不错：比如，把你的操作系统大作业往后拖，说不定会发现项目说明里的 bug 已经被同学解决掉了；不过，课程项目不太可能被取消，所以太懒也可能出问题，导致项目迟交、成绩难看、教授伤心。别让教授伤心！

## 23.2 Linux 虚拟内存系统

下面我们讨论 Linux 虚拟内存系统里一些更有意思的方面。Linux 的发展是被真正的工程师推动的，他们在解决生产环境里遇到的真实问题；于是一大堆特性慢慢被纳入进来，形成如今这套功能完整、特性丰富的虚拟内存系统。

我们没法把 Linux 虚拟内存的每个方面都讲到，只谈最重要的那些，尤其是它超越 VAX/VMS 这类经典虚拟内存系统的地方。我们也会尽量点出 Linux 和老系统之间的共同点。

这次的讨论，我们聚焦运行在 Intel x86 上的 Linux。Linux 能、也确实运行在许多不同的处理器架构上，但 x86 上的 Linux 是它最重要、占据主导地位的部署场景，因此也是我们注意力的焦点。

### Linux 的地址空间

跟其他现代操作系统很像，也跟 VAX/VMS 很像，Linux 的虚拟地址空间[^1]由用户部分（用户程序的代码、栈、堆以及其他部分所在之处）和内核部分（内核的代码、栈、堆以及其他部分所在之处）组成。跟那些系统一样，上下文切换时，当前运行地址空间的用户部分会变；内核部分则各进程相同。也跟那些系统一样，用户态运行的程序无法访问内核虚拟页；只有陷入内核、切换到特权态，才能访问这类内存。

[^1]: 那是指最近因安全威胁而做出改变之前。关于这一改动，详见下面讲 Linux 安全的那几小节。

在经典的 32 位 Linux（也就是拥有 32 位虚拟地址空间的 Linux）里，地址空间的用户部分和内核部分在地址 0xC0000000 处分界，也就是地址空间的四分之三处。因此，虚拟地址 0 到 0xBFFFFFFF 是用户虚拟地址；余下的虚拟地址（0xC0000000 到 0xFFFFFFFF）位于内核虚拟地址空间。64 位 Linux 有类似的分界，只是位置略有不同。图 23.2 描绘了一个典型的（简化过的）地址空间。

```text
0x00000000  +---------------------------+
            |  Page 0: Invalid          |  ← 0 号页：无效
            +---------------------------+
            |  User Code                |
            +---------------------------+
            |  User Heap                |
            |                           |
            |  ...                      |  ← 用户部分（User）
            |                           |
            |  User Stack               |
0xC0000000  +---------------------------+
            |  Kernel (Logical)         |
            |                           |
            |  ...                      |  ← 内核部分（Kernel）
            |                           |
            |  Kernel (Virtual)         |
0xFFFFFFFF  +---------------------------+
```

*图 23.2：Linux 的地址空间。*

Linux 稍有意思的一点是，它包含两种类型的内核虚拟地址。第一种叫内核逻辑地址(kernel logical address) [O16]。这就是你会认为的内核常规虚拟地址空间；要拿到更多这类内存，内核代码只需调用 `kmalloc`。大多数内核数据结构都住在这里，比如页表、每进程内核栈等等。跟系统里大多数其他内存不同，内核逻辑内存不能被交换到磁盘。

内核逻辑地址最有趣的方面，是它跟物理内存的关系。具体来说，内核逻辑地址和物理内存的前一部分之间存在直接映射。于是，内核逻辑地址 0xC0000000 转换成物理地址 0x00000000，0xC0000FFF 转换成 0x00000FFF，以此类推。这种直接映射有两个含义。第一，在内核逻辑地址和物理地址之间来回转换很简单；因此，这些地址常常被当作它们真的就是物理地址来对待。第二，如果一块内存在内核逻辑地址空间里是连续的，那它在物理内存里也连续。这就使得内核地址空间这部分里分配的内存，适合那些需要连续物理内存才能正确工作的操作，比如通过直接内存访问(direct memory access, DMA) 在设备之间来回传输 I/O（这点我们会在本书第三部分学到）。

另一种内核地址叫内核虚拟地址(kernel virtual address)。要拿到这类内存，内核代码调用另一个分配器 `vmalloc`，它返回一个指向所需大小的、虚拟上连续区域的指针。跟内核逻辑内存不同，内核虚拟内存通常不连续；每个内核虚拟页可能映射到不连续的物理页（因此不适合 DMA）。但正因如此，这类内存更容易分配，于是被用于大缓冲区——因为要给大缓冲区找一块连续的大物理内存，是很有挑战的。

在 32 位 Linux 里，内核虚拟地址存在的另一个原因，是它们让内核能够寻址超过（大约）1GB 的内存。多年前，机器的内存比这少得多，能访问超过 1GB 根本不是问题。可技术在进步，很快就有了让内核用上更大内存的需求。内核虚拟地址，以及它们与物理内存之间那种严格一对一映射的脱钩，让这件事成为可能。不过，随着转向 64 位 Linux，这个需求不再那么紧迫，因为内核不再被局限在虚拟地址空间的最后 1GB 里。

### 页表结构

因为我们聚焦 x86 上的 Linux，讨论就围绕 x86 提供的这类页表结构，因为它决定了 Linux 能做和不能做什么。如前所述，x86 提供一种硬件管理的多级页表结构，每进程一张页表；操作系统只需在自己的内存里建立好映射，把一个特权寄存器指向页目录的起始位置，剩下的交给硬件。操作系统如你所料，会在进程创建、删除以及上下文切换时介入，确保每种情况下硬件 MMU 都用对了页表来做转换。

近年来最大的变化，大概是从 32 位 x86 转向 64 位 x86，前面简略提过。正如在 VAX/VMS 系统里所见，32 位地址空间已经存在了很久，随着技术变化，它们终于开始成为程序的真正限制。虚拟内存让系统编程变得容易，可现代系统动辄好几个 GB 的内存，32 位已不足以指代其中每一个字节。于是，下一次飞跃成了必要。

转向 64 位地址，对 x86 页表结构的影响不出所料。因为 x86 用的是多级页表，当前的 64 位系统用四级表。不过，虚拟地址空间完整的 64 位特性还没用上，只用到低 48 位。于是，一个虚拟地址可以这样看：

```text
 63                              47                      15      0
 +--------------------------------+-----------------------+-------+
 |             Unused             |   P1 | P2 | P3 | P4  |Offset |
 +--------------------------------+-----------------------+-------+
```

正如你在图里看到的，虚拟地址的高 16 位未使用（因而在转换中不起任何作用），低 12 位（因为页大小是 4KB）用作偏移（从而直接使用、不经转换），中间 36 位虚拟地址用于参与转换。地址里的 P1 部分用来索引最顶层的页目录，转换从那里开始，一次一级往下走，直到由 P4 索引到页表里真正的那一页，得到想要的页表项。

随着系统内存变得更大，这片浩瀚地址空间里会有更多部分被启用，从而走向五级、最终六级的页表树结构。想象一下吧：一次简单的页表查找，竟需要六级转换，只为了搞清某个数据到底住在内存的哪里。

### 大页支持

Intel x86 允许使用多种页大小，而不只是标准的 4KB 页。具体来说，近期的设计在硬件上支持 2MB 乃至 1GB 的页。于是随着时间推移，Linux 逐渐演化，允许应用程序使用这些"巨页(huge page)"（在 Linux 的世界里就是这么叫的）。

使用巨页，如前面所暗示的，带来许多好处。正如在 VAX/VMS 里所见，这么做能减少页表里所需的映射数量；页越大，映射越少。不过，页表项更少并不是巨页背后的驱动力；真正的驱动力是更好的 TLB 行为和相关的性能提升。

当一个进程积极地使用大量内存时，它会迅速用转换塞满 TLB。如果这些转换都是针对 4KB 页的，那在引发 TLB 缺失之前，只能访问总内存里很小的一部分。对运行在许多 GB 内存机器上的现代"大内存"负载来说，结果就是可观的性能代价；近期研究表明，有些应用会把 10% 的周期花在处理 TLB 缺失上 [B+13]。

巨页让进程能够在 TLB 里占用更少的槽位，从而访问一大片内存而不引发 TLB 缺失，这就是它主要的好处。不过巨页还有其他好处：TLB 缺失的处理路径更短，意味着一旦真的发生 TLB 缺失，处理起来更快。此外，分配可以相当快（在某些场景下），这是一个不大、但有时很重要的好处。

Linux 对巨页的支持有一个有意思之处：它是渐进式地做成的。一开始，Linux 的开发者知道这种支持只对少数应用重要，比如对性能要求苛刻的大型数据库。于是他们决定，允许应用程序显式地申请使用大页的内存分配（通过 `mmap()` 或 `shmget()` 调用）。这样一来，大多数应用不受影响（继续只用 4KB 页），少数要求苛刻的应用则需要改一改、用上这些接口，但对它们来说，这点麻烦是值得的。

!!! tip "提示：拥抱渐进主义"
    生活里，你常常被鼓励去当个革命者。"要有大格局！"，他们说。"改变世界！"，他们喊。你也能明白这为什么吸引人；在某些情况下，大变革确实必要，为它使劲推一把也就很有道理。而且，你要是这么干，至少他们兴许就不冲你嚷嚷了。

    然而在许多情况下，一种更缓慢、更渐进的做法可能才是对的。本章里 Linux 的巨页就是个"工程渐进主义"的例子；开发者没有摆出原教旨主义者的姿态、一口咬定大页就是未来，而是采取了审慎的做法：先为它引入专门的支持，多了解它的好处和坏处，只到真有充分理由时，才为所有应用加上更通用的支持。

    渐进主义虽然有时被鄙视，却常常带来缓慢、深思熟虑而明智的进步。构建系统时，这种做法或许正是你需要的。事实上，在生活里大概也是如此。

最近，由于许多应用都更普遍地需要更好的 TLB 行为，Linux 的开发者又加入了透明巨页(transparent huge page)支持。启用这个特性后，操作系统会自动寻找机会分配巨页（通常是 2MB，但有些系统上是 1GB），无需应用程序改任何代码。

巨页也不是没有代价。最大的潜在代价是内部碎片(internal fragmentation)，也就是一页很大却稀疏地使用。这种浪费会让内存里塞满大而很少用的页。交换（如果启用）跟巨页也配合不好，有时会大幅放大系统所做的 I/O 量。分配开销有时也会很糟（在另一些情况下）。总的来说，有一点很清楚：4KB 页大小服务了系统这么多年、这么出色，可它已不再是过去那种万能的方案；不断增长的内存规模，要求我们把大页以及其他方案视为虚拟内存系统必要演进的一部分。Linux 对这项基于硬件的技术采纳得如此缓慢，正说明变化即将到来。

### 页缓存

为了降低访问持久化存储的成本（本书第三部分的重点），大多数系统都用激进的缓存子系统，把热门数据留在内存里。在这方面，Linux 跟传统操作系统没什么不同。

Linux 的页缓存(page cache)是统一的，把来自三个主要来源的页留在内存里：内存映射文件(memory-mapped file)、来自设备的文件数据和元数据（通常通过把 `read()` 和 `write()` 调用导向文件系统来访问），以及构成每个进程的堆和栈页（有时叫匿名内存(anonymous memory)，因为它底下没有具名的文件，而是交换空间）。

!!! note "边栏：内存映射无处不在"
    内存映射(memory mapping)比 Linux 还要早几年，在 Linux 和其他现代系统里被用在许多地方。想法很简单：对一个已经打开的文件描述符调用 `mmap()`，进程就会得到一个指针，指向一段虚拟内存的起始处，文件内容看起来就位于那里。随后用那个指针，进程只要简单解引用一次，就能访问文件的任何部分。访问一个尚未被载入内存的映射文件部分，会触发缺页(page fault)，此时操作系统会把相关数据调页进来，并相应地更新进程的页表，让它变得可访问（也就是按需分页）。

    每个常规的 Linux 进程都会用到内存映射文件，哪怕 `main()` 里的代码并没有直接调用 `mmap()`，因为 Linux 是这样把可执行文件和共享库里的代码载入内存的。下面是 `pmap` 命令行工具输出的（高度删节过的）结果，它展示了运行中程序（这个例子里是 shell，`tcsh`）的虚拟地址空间由哪些不同的映射构成。输出有四列：映射的虚拟地址、它的大小、这段区域的保护位，以及映射的来源：

    ```text
    0000000000400000    372K r-x--  tcsh
    00000000019d5000   1780K rw---  [ anon ]
    00007f4e7cf06000   1792K r-x--  libc-2.23.so
    00007f4e7d2d0000     36K r-x--  libcrypt-2.23.so
    00007f4e7d508000    148K r-x--  libtinfo.so.5.9
    00007f4e7d731000    152K r-x--  ld-2.23.so
    00007f4e7d932000     16K rw---  [ stack ]
    ```

    从这份输出可以看到，来自 `tcsh` 二进制的代码，以及来自 `libc`、`libcrypt`、`libtinfo` 的代码，还有动态链接器本身（`ld.so`）的代码，全都被映射进了地址空间。此外还有两个匿名区域：堆（第二项，标为 `anon`）和栈（标为 `stack`）。内存映射文件为操作系统提供了一种直接而高效的方式来构建现代地址空间。

这些实体保存在一张页缓存哈希表里，需要这些数据时就能快速查找。

页缓存会跟踪条目是干净的（读过但未更新）还是脏的(dirty)（也就是被修改过）。脏数据由后台线程（叫 `pdflush`）定期写回后备存储（对文件数据是写回某个特定文件，对匿名区域是写回交换空间），从而确保被修改的数据最终被写回持久化存储。这种后台活动要么在某个时间段之后发生，要么在过多页被视为脏页时发生（两者都是可配置参数）。

有时系统内存吃紧，Linux 必须决定把哪些页踢出内存、腾出空间。为此，Linux 使用 2Q 替换算法的一个修改版本 [JS94]，我们在此描述它。基本思路很简单：标准的 LRU 替换虽然有效，却可能被某些常见的访问模式给带偏。比如，如果一个进程反复访问一个大文件（尤其是一个大小接近内存、甚至更大的文件），LRU 会把其他所有文件都踢出内存。更糟的是：把这个文件的一部分留在内存里其实没用，因为它们在被踢出内存之前根本不会被再次引用。

Linux 版的 2Q 替换算法用两条链表、并把内存在这两者之间划分，来解决这个问题。一页第一次被访问时，被放进其中一条队列（在原论文里叫 A1，在 Linux 里叫非活跃链表(inactive list)）；当它再次被引用时，这页被提升到另一条队列（原论文里叫 Aq，在 Linux 里叫活跃链表(active list)）。需要替换时，替换的候选从非活跃链表里取。Linux 还会定期把页从活跃链表底部移到非活跃链表，让活跃链表大约占整个页缓存大小的三分之二 [G04]。

Linux 理想情况下会按完美的 LRU 顺序管理这些链表，但如前面几章所讨论的，这么做代价高昂。因此，和许多操作系统一样，用的是 LRU 的一种近似（类似时钟替换）。这种 2Q 方法总体行为和 LRU 相当像，但有一个显著之处：它通过把循环式大文件访问的那些页限制在非活跃链表里，妥善处理了这种情况。因为那些页在被踢出内存之前永远不会被再次引用，它们就不会把活跃链表里有用的页冲走。

### 安全与缓冲区溢出

现代虚拟内存系统（Linux、Solaris 或某个 BSD 变种）与古老系统（VAX/VMS）之间最大的差别，大概就是现代对安全的重视。保护一直是操作系统严肃关心的问题，但如今机器比以往任何时候都更互联，开发者们实现出各种各样的防御性对策，来阻止那些狡猾的黑客控制系统，也就不足为奇了。

一大威胁来自**缓冲区溢出(buffer overflow)** 攻击 [W18]，它可能被用来对付普通用户程序，甚至内核本身。这类攻击的思路是：在目标系统里找出一个 bug，让攻击者能把任意数据注入目标的地址空间。这类漏洞有时是因为开发者（错误地）假定某个输入不会太长，于是（轻信地）把输入拷进一个缓冲区；而输入实际上太长，就溢出了缓冲区，从而改写目标的内存。像下面这样看似无辜的代码就可能是问题之源：

```c
int some_function(char *input) {
    char dest_buffer[100];
    strcpy(dest_buffer, input); // 糟糕，无界拷贝！
}
```

在很多情况下，这样的溢出并不致命——比如，误喂给用户程序、甚至操作系统的坏输入，多半会让它崩溃，但也就到此为止。然而，恶意的程序员可以精心构造溢出缓冲区的输入，把他们的代码注入目标系统，这实际上就让他们接管了系统、为所欲为。如果是针对一个联网的用户程序得手，攻击者就能运行任意计算，甚至把被攻陷系统上的算力租出去；如果是对操作系统本身得手，攻击就能访问更多资源，而且这属于所谓**特权提升(privilege escalation)**（也就是用户代码获得了内核访问权限）。你就算猜不到，也该明白这些都是"坏事"。

对付缓冲区溢出，第一个也是最简单的防御，是禁止执行地址空间里某些区域（比如栈里）的任何代码。AMD 引入它的 x86 版本里的 NX 位（No-eXecute，即不可执行；Intel 上现在有类似的 XD 位），就是这样一种防御；它只是禁止执行任何在对应页表项里设置了这一位的页。这个办法阻止攻击者注入目标栈里的代码被执行，从而缓解问题。

可是，聪明的攻击者……很聪明，即便攻击者不能显式地加入注入代码，恶意代码也能执行任意的代码序列。这个想法最一般的形式，叫做**面向返回的编程(return-oriented programming, ROP)** [S07]，说实话相当精彩。ROP 背后的观察是：任何程序的地址空间里都有大量代码碎片（ROP 术语里叫 gadget），尤其是链接了庞大 C 库的 C 程序。于是，攻击者可以改写栈，让当前执行函数的返回地址指向一段想要的恶意指令（或指令序列），后面跟着一条返回指令。通过把大量 gadget 串起来（也就是确保每次返回都跳到下一个 gadget），攻击者就能执行任意代码。太惊人了！

为了防御 ROP（包括它更早的形式，return-to-libc 攻击 [S+04]），Linux（以及其他系统）又加了一层防御，叫做**地址空间布局随机化(address space layout randomization, ASLR)**。操作系统不再把代码、栈和堆放在虚拟地址空间里固定的位置，而是把它们的摆放随机化，从而让构造这类攻击所需的精巧代码序列变得相当困难。这样，针对易受攻击用户程序的大多数攻击都会导致崩溃，却无法取得对运行中程序的控制权。

有意思的是，你其实很容易在实践中观察到这种随机性。下面是一段在现代 Linux 系统上演示它的代码：

```c
int main(int argc, char *argv[]) {
    int stack = 0;
    printf("%p\n", &stack);
    return 0;
}
```

这段代码只是打印出栈上一个变量的（虚拟）地址。在较老的、没有 ASLR 的系统上，这个值每次都会一样。但如你在下面所见，这个值每次运行都会变：

```console
prompt> ./random
0x7ffd3e55d2b4
prompt> ./random
0x7ffe1033b8f4
prompt> ./random
0x7ffe45522e94
```

ASLR 对用户级程序来说是一种如此有用的防御，以至于它也被并入了内核，这个特性的名字起得毫无想象力，叫做**内核地址空间布局随机化(kernel address space layout randomization, KASLR)**。不过，内核可能要处理更大的麻烦，我们接下来就讨论这个。

### 其他安全问题：Meltdown 与 Spectre

在我们写下这些文字之时（2018 年 8 月），系统安全的世界被两个新的、彼此相关的攻击搅得天翻地覆。第一个叫 Meltdown（熔毁），第二个叫 Spectre（幽灵）。它们大约同时被四组不同的研究者/工程师发现，并引发了对计算机硬件及其上层操作系统所提供的基本保护的深刻质疑。关于详细描述这两个攻击的论文，见 meltdownattack.com 和 spectreattack.com。Spectre 被认为是两者中更棘手的一个。

这两个攻击所利用的普遍弱点在于：现代系统里的 CPU 会做各种疯狂的幕后把戏来提升性能。问题的核心有一类技术，叫做**推测执行(speculative execution)**，CPU 在其中猜测未来不久将要执行的指令，并提前开始执行它们。如果猜对了，程序跑得更快；如果猜错了，CPU 就撤销它们对架构状态（比如寄存器）的影响，重来一次，这次走正确的路径。

推测的问题在于，它往往会在系统的各个部位留下执行的痕迹，比如处理器缓存、分支预测器等等。问题就此来了：正如攻击作者们所展示的，这类状态可能让内存内容变得可被攻击，哪怕是我们以为受 MMU 保护的内存。

因此，增强内核保护的一条途径，就是把尽可能多的内核地址空间从每个用户进程里移走，改为给大多数内核数据单独一张内核页表（称为**内核页表隔离(kernel page-table isolation, KPTI)** [G+17]）。这样，就不再是把内核的代码和数据结构映射进每个进程，而只在其中保留最低限度的东西；当切入内核时，就需要切换到内核页表了。这么做提升了安全性、避开了一些攻击途径，但代价是：性能。切换页表很昂贵。唉，安全的代价：便利和性能。

遗憾的是，KPTI 并不能解决上面列出的所有安全问题，只能解决其中一部分。而像关掉推测这样的简单方案又没什么意义，因为系统会慢上几千倍。所以，如果你对系统安全感兴趣，现在是个有意思的时代。

要真正理解这些攻击，你（很可能）得先学更多东西。先从中级进阶书里的现代计算机架构入手，重点关注推测以及实现它所需要的一切机制。一定要读上面提到的网站上关于 Meltdown 和 Spectre 攻击的内容；它们其实还附带了一份有用的推测入门，所以也许不算太差的起点。然后再研究操作系统里还有哪些漏洞。谁知道还剩下些什么问题呢？

## 23.3 小结

你现在已经自上而下地看完两套虚拟内存系统。但愿大部分细节都容易跟上，因为你应该已经对基本的机制和策略有了不错的理解。关于 VAX/VMS 的更多细节，可以在 Levy 和 Lipman 那篇出色（且简短）的论文 [LL82] 里找到。我们鼓励你去读一读，因为这是了解这些章节背后原始素材长什么样的好办法。

你还对 Linux 有了一点了解。它虽然是个庞大而复杂的系统，却从过去继承了许多好想法，其中许多我们没篇幅展开细讲。比如，Linux 在 `fork()` 时对页执行惰性的写时复制，通过避免不必要的复制来降低开销。Linux 也会按需置零页（利用对 `/dev/zero` 设备的内存映射），还有一个后台交换守护进程（`swapd`），把页交换到磁盘以减轻内存压力。的确，这套虚拟内存系统里满是取自过去的好想法，也包含许多它自己的创新。

想学更多的话，可以看看这两本还算不错（可惜有些过时）的书 [BC05, G04]。我们鼓励你自己去读，因为我们能给出的，不过是那片复杂汪洋里的区区一滴。可你总得从某处开始。所谓汪洋，不就是无数滴水吗？[M04]

## 参考文献

[B+13] "Efficient Virtual Memory for Big Memory Servers" by A. Basu, J. Gandhi, J. Chang, M. D. Hill, M. M. Swift. ISCA '13, June 2013, Tel-Aviv, Israel. 近期的一项工作，表明 TLB 很重要，在大内存负载下会吃掉 10% 的周期。解决办法：用一个巨大的段来装大数据集。我们后退一步，是为了前进两步！

[BB+72] "TENEX, A Paged Time Sharing System for the PDP-10" by D. G. Bobrow, J. D. Burchfiel, D. L. Murphy, R. S. Tomlinson. CACM, Volume 15, March 1972. 一套早期的分时操作系统，许多好想法都源自于它。写时复制只是其中之一；它还启发了现代系统的其他方面，包括进程管理、虚拟内存和文件系统。

[BJ81] "Converting a Swap-Based System to do Paging in an Architecture Lacking Page-Reference Bits" by O. Babaoglu, W. N. Joy. SOSP '81, Pacific Grove, California, December 1981. 如何利用现有的保护机制来模拟引用位——出自伯克利一个开发自己 UNIX 版本的团队：伯克利软件发行版(Berkeley Systems Distribution, BSD)。这个团队在虚拟内存、文件系统和网络的发展中很有影响力。

[BC05] "Understanding the Linux Kernel" by D. P. Bovet, M. Cesati. O'Reilly Media, November 2005. 你能找到的众多 Linux 书籍之一，虽然过时，但依然值得一读。

[C03] "The Innovator's Dilemma" by Clayton M. Christenson. Harper Paperbacks, January 2003. 一本精彩的书，讲的是磁盘驱动器行业，以及新创新如何颠覆既有者。无论你是商科生还是计算机科学学生，都值得一读。它提供了对庞大而成功的公司如何彻底失败的洞见。

[C93] "Inside Windows NT" by H. Custer, D. Solomon. Microsoft Press, 1993. 这本讲 Windows NT 的书自上而下地解释了这套系统，详细到你可能觉得过了头。但说真的，是本相当不错的书。

[G04] "Understanding the Linux Virtual Memory Manager" by M. Gorman. Prentice Hall, 2004. 深入剖析 Linux 虚拟内存，可惜有点过时了。

[G+17] "KASLR is Dead: Long Live KASLR" by D. Gruss, M. Lipp, M. Schwarz, R. Fellner, C. Maurice, S. Mangard. Engineering Secure Software and Systems, 2017. Available: https://gruss.cc/files/kaiser.pdf 关于 KASLR、KPTI 以及更多的极佳资料。

[JS94] "2Q: A Low Overhead High Performance Buffer Management Replacement Algorithm" by T. Johnson, D. Shasha. VLDB '94, Santiago, Chile. 一种构建页替换的简单却有效的方法。

[LL82] "Virtual Memory Management in the VAX/VMS Operating System" by H. Levy, P. Lipman. IEEE Computer, Volume 15:3, March 1982. 本章大部分内容的原始出处，去读吧。如果你打算读研究生，这篇尤为重要——读研就是整天读论文、干活，再读一堆论文、再干活，最后写一篇论文，然后接着干活。
