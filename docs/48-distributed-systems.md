# 第 48 章 分布式系统

> 英文原题：*Distributed Systems*

分布式系统改变了世界的面貌。当浏览器连接到地球另一端的 Web 服务器时，它正在参与一种看似简单的客户端/服务器分布式系统。可当你访问 Google、Facebook 之类的现代 Web 服务时，交互对象并非单独一台机器；幕后是成千上万台机器协同工作，共同提供网站的服务。因此，分布式系统值得研究——它足够单开一门课；这里我们只介绍几个主要主题。

构建分布式系统会遇到许多新挑战。本章最关注的是**故障(failure)**：机器、磁盘、网络和软件都会不时出错，因为我们不会——而且很可能永远不会——制造出“完美”的部件和系统。然而，现代 Web 服务又希望在客户端眼里永不失败。怎么办？

!!! danger "问题核心：怎样用会坏的部件构建能工作的系统"
    怎样用并非始终正确工作的部件构建可用系统？这和 RAID 存储阵列中的一些问题颇为相似，只是这里的问题和解法通常都更复杂。

有趣的是，故障既是挑战，也是机会。机器会坏，并不意味着整个系统必须跟着陪葬。把一组机器组织起来，即使其中的部件经常故障，也能建出一个看起来极少失败的系统。这正是分布式系统的美丽与价值所在，也是你使用的几乎所有现代 Web 服务的基础。

!!! tip "通信天生不可靠"
    几乎在任何情况下，都应该把通信看作一种从根上就不可靠的活动。位损坏、链路或机器宕机、接收端没有足够缓冲区，都会得到同一结果：数据包偶尔到不了目的地。要在不可靠网络之上构建可靠服务，就必须有办法应对丢包。

此外还有性能和安全问题。网络把系统连接起来，设计者就得减少消息数量，并让通信尽可能低延迟、高带宽。连接远程站点时，还要确认对方真是它自称的那个家伙，并防止第三方监听或篡改通信。

本章从分布式系统最基本的新东西——**通信**——讲起：系统内的机器应怎样彼此交流？我们从消息这种基本原语出发，在其上构建更高级的原语，并始终盯着一个问题：通信层怎样处理故障？

## 48.1 通信基础

现代网络的核心信条是：通信从根本上不可靠。无论广域互联网，还是 InfiniBand 一类高速局域网，数据包都会经常丢失、损坏，或以其他方式没能抵达目的地。

原因很多。传输途中，电气问题可能翻转某些位；链路、路由器乃至远端主机可能损坏或工作异常——网线确实会被人不小心剪断，至少偶尔如此。

更根本的原因，是交换机、路由器或端点的缓冲空间不足。即便所有链路和部件都完美运行，丢包仍然可能发生。一个包到达路由器后，必须先放进内存；若同时到达的包太多，内存装不下，路由器只能丢弃一个或多个包。终端主机也一样：向一台机器狂发消息，很容易耗尽它的资源，于是包又丢了。

所以丢包是网络的基本事实。问题变成：怎样对付它？

下面是一个 UDP/IP 客户端与服务器：

```c
// client code
int main(int argc, char *argv[]) {
    int sd = UDP_Open(20000);
    struct sockaddr_in addrSnd, addrRcv;
    int rc = UDP_FillSockAddr(&addrSnd, "machine.cs.wisc.edu", 10000);
    char message[BUFFER_SIZE];
    sprintf(message, "hello world");
    rc = UDP_Write(sd, &addrSnd, message, BUFFER_SIZE);
    if (rc > 0) {
        int rc = UDP_Read(sd, &addrRcv, message, BUFFER_SIZE);
    }
    return 0;
}

// server code
int main(int argc, char *argv[]) {
    int sd = UDP_Open(10000);
    assert(sd > -1);
    while (1) {
        struct sockaddr_in addr;
        char message[BUFFER_SIZE];
        int rc = UDP_Read(sd, &addr, message, BUFFER_SIZE);
        if (rc > 0) {
            char reply[BUFFER_SIZE];
            sprintf(reply, "goodbye world");
            rc = UDP_Write(sd, &addr, reply, BUFFER_SIZE);
        }
    }
    return 0;
}
```

*图 48.1：UDP/IP 客户端/服务器示例代码。*

## 48.2 不可靠通信层

对付丢包的一种简单方法是：不对付。有些应用本身知道怎样处理丢包，让它们直接使用基本的不可靠消息层有时反而合适；这是本章末尾“端到端原则”的一个例子。几乎所有现代系统都有的 UDP/IP 协议栈，就是优秀的不可靠层。

进程通过套接字 API 建立通信端点，其他机器或同一机器上的进程向它发送 UDP **数据报(datagram)**；数据报是大小不超过某个上限的定长消息。下面是示例使用的简易 UDP 库：

```c
int UDP_Open(int port) {
    int sd;
    if ((sd = socket(AF_INET, SOCK_DGRAM, 0)) == -1) return -1;
    struct sockaddr_in myaddr;
    bzero(&myaddr, sizeof(myaddr));
    myaddr.sin_family = AF_INET;
    myaddr.sin_port = htons(port);
    myaddr.sin_addr.s_addr = INADDR_ANY;
    if (bind(sd, (struct sockaddr *)&myaddr, sizeof(myaddr)) == -1) {
        close(sd);
        return -1;
    }
    return sd;
}

int UDP_FillSockAddr(struct sockaddr_in *addr, char *hostName, int port) {
    bzero(addr, sizeof(struct sockaddr_in));
    addr->sin_family = AF_INET;
    addr->sin_port = htons(port);
    struct in_addr *inAddr;
    struct hostent *hostEntry;
    if ((hostEntry = gethostbyname(hostName)) == NULL) return -1;
    inAddr = (struct in_addr *)hostEntry->h_addr;
    addr->sin_addr = *inAddr;
    return 0;
}

int UDP_Write(int sd, struct sockaddr_in *addr, char *buffer, int n) {
    int addrLen = sizeof(struct sockaddr_in);
    return sendto(sd, buffer, n, 0, (struct sockaddr *)addr, addrLen);
}

int UDP_Read(int sd, struct sockaddr_in *addr, char *buffer, int n) {
    int len = sizeof(struct sockaddr_in);
    return recvfrom(sd, buffer, n, 0, (struct sockaddr *)addr,
                    (socklen_t *)&len);
}
```

*图 48.2：一个简易 UDP 库。*

客户端发消息，服务器回消息；这么一点代码，已经足够迈出构建分布式系统的第一步。

UDP 很好地体现了不可靠通信：包可能丢失且发送方不会收到通知。不过 UDP 并非什么故障都不管；例如，它用校验和检测某些数据包损坏。只是许多应用希望把数据发到目的地而不操心丢包，因此还需要在不可靠网络上构建可靠通信。

!!! tip "用校验和保护完整性"
    校验和是现代系统快速检测损坏的常用办法。最简单的校验和可以只是把一段数据的字节相加；更复杂的还有 CRC、Fletcher 校验和等 [MK09]。

    发送前计算消息字节的校验和，把消息与校验和一起发出；接收方重新计算并比较。二者匹配，就有一定把握认为传输途中没有损坏。评价校验和主要看两点：数据变化是否会使校验和变化，以及计算成本有多高。遗憾的是，效果和性能常常互相较劲：质量高的校验和通常也更贵。生活再次证明自己并不完美。

## 48.3 可靠通信层

要构建可靠通信层，需要用新机制处理丢包。假设客户端通过不可靠连接向服务器发消息，第一个问题是：发送方怎样知道接收方确实收到了？

答案是**确认(acknowledgment，简称 ack)**：发送方发出消息，接收方回一个短消息确认收讫。

```text
发送方                         接收方
  | -------- 发送消息 --------> |
  | <---------- ack ----------- |
```

*图 48.3：消息加确认。*

收到 ack 后，发送方可以放心。但若没收到呢？这就需要**超时(timeout)**。发送消息时启动计时器；到期仍无 ack，便认为消息丢了，再次发送。发送方必须保留消息副本以备重试。于是有了“超时/重试(timeout/retry)”——网络专家给它起了个惊人地直白的名字，不是吗？

```text
发送方                         接收方
发送消息、保留副本、启动计时器
  | -------- 消息（丢失） ----X
  |       ……等待 ack……          |
计时器到期，重新计时并重试
  | -------- 发送消息 --------> | 接收消息
  | <---------- ack ----------- | 发送 ack
收到 ack，删除副本并关闭计时器
```

*图 48.4：消息加确认——请求丢失。*

可惜，仅有超时/重试还不够。如果丢的不是请求而是回复，发送方看见的仍是“没有 ack”，于是重试；接收方却会收到同一条消息两次。下载文件时若凭空插入重复数据，场面不会很好看。因此可靠消息层通常还要保证每条消息**恰好一次(exactly once)**交给接收应用。

发送方必须唯一标识消息，接收方要追踪消息是否见过。遇到重复消息时，接收方仍回 ack，但绝不能再次把它交给应用。可以给每条消息生成全局唯一 ID，但接收方永久保存所有 ID 的内存成本没有上限。

更简单的办法是**序列计数器(sequence counter)**。双方约定起始值（如 1）。发送方在消息中带上当前计数器值 $N$，随后自增到 $N+1$。接收方也保存期望值：若收到的 ID 正是 $N$，就确认、交给应用并自增；若 ack 丢失，发送方重发 $N$，而接收方已经期待 $N+1$，便知道这是重复消息，只确认而不再次交付。

```text
发送方                         接收方
  | -------- 消息 N ----------> | 接收并交付 N
  | <------ ack（丢失） -------X
计时器到期，重发 N
  | -------- 消息 N ----------> | 识别为重复，不再交付
  | <---------- ack ----------- |
```

*图 48.5：消息加确认——回复丢失。*

最常用的可靠通信层是 TCP/IP，简称 TCP。它远比上述方案复杂，还要处理网络拥塞 [VJ88]、多个未完成请求，以及几百处细小调整和优化。好奇就继续读；更好的是去上一门网络课，把它学扎实。

!!! tip "谨慎设置超时值"
    超时太短，会无谓重发，浪费发送方 CPU 与网络资源；太长，又会迟迟不重试，让性能显得磨磨蹭蹭。对单个客户端和服务器而言，理想值应刚好足以判断丢包。

    多客户端同时访问一个服务器时，丢包也许意味着服务器过载。客户端可采用**指数退避(exponential back-off)**：第一次超时后把等待时间加倍，之后继续增长。这种方案发端于早期 ALOHA 网络，后来用于以太网 [A70]，可避免重发洪水把已经过载的资源再踩上一脚。健壮系统会尽力躲开这种“大家一起急，结果谁也走不了”的场面。

## 48.4 通信抽象

有了基本消息层，下一个问题是：构建分布式系统时应该采用什么通信抽象？

系统界提出过许多方案，其中一类把操作系统抽象扩展到分布式环境。例如**分布式共享内存(distributed shared memory, DSM)**让不同机器上的进程共享一个很大的虚拟地址空间 [LH89]，把分布式计算伪装成多线程程序，只不过线程跑在不同机器上。

多数 DSM 依靠虚拟内存系统工作。访问页面时，若页面已经在本机，读取很快；若在别的机器上，就触发缺页，处理程序发消息取回页面，装入请求进程的页表，再继续执行。

它没有广泛流行，主要原因之一是故障难处理。一台机器坏了，那台机器上的页面怎么办？若分布式数据结构散布在整个地址空间，部分结构会突然消失。想象链表的 `next` 指针指向已经蒸发的地址空间——哎呀。

性能也是问题。程序员通常假设内存访问便宜；DSM 中有些访问便宜，有些却触发缺页并从远程机器昂贵地取回数据。程序员不得不精心安排计算，让通信几乎不发生，这多少把使用 DSM 的意义也一起安排没了。尽管研究不少，实际影响有限；如今没人用 DSM 构建可靠分布式系统。

## 48.5 远程过程调用（RPC）

操作系统抽象不太合适，编程语言抽象却更顺手。最主流的是**远程过程调用(remote procedure call, RPC)** [BN84]。它的目标很简单：让远程机器执行代码，尽量像调用本地函数一样自然。客户端发起过程调用，稍后得到结果；服务器定义要导出的例程；剩下的魔法由 RPC 系统完成。

RPC 通常由两部分组成：**存根生成器(stub generator，也称协议编译器)**和**运行时库(run-time library)**。

> 在现代编程语言里，也可称为远程方法调用(RMI)。不过，谁喜欢那些满身“对象”的花哨语言呢？

### 存根生成器

存根生成器自动把函数参数和结果打包进消息，免去手工编码的痛苦和常见错误，还有机会生成更高效的代码。输入只是服务器希望导出的调用集合，例如：

```c
interface {
    int func1(int arg1);
    int func2(int arg1, int arg2);
};
```

它为客户端生成包含这些函数的**客户端存根(client stub)**。客户端链接存根后，看起来只是调用 `func1(x)`；内部则会：

1. 创建消息缓冲区，通常是一段连续字节数组。
2. 把函数标识和全部参数装入缓冲区。这个过程叫**编组(marshaling)**或**序列化(serialization)**。
3. 通过 RPC 运行时库把消息发给目标服务器。
4. 等待回复；普通函数调用是同步的，因此通常要等完成。
5. 解出返回码和其他结果，即**解组(unmarshaling)**或**反序列化(deserialization)**。
6. 从客户端存根返回调用者。

服务器端也会生成代码：

1. 解组消息，取出函数标识和参数。
2. 调用真正的函数——终于到正戏了！
3. 编组返回结果，装进回复缓冲区。
4. 把回复发给调用者。

复杂参数需要额外信息。例如 `write()` 接收文件描述符、缓冲区指针和字节数；远端不能直接理解本机指针。通常使用编译器认识的约定类型（如带长度的 `buffer_t`），或给数据结构加注解，说明哪些字节需要序列化。

服务器还要处理并发。单线程循环一次处理一个请求很低效：一个 RPC 阻塞于 I/O，整台服务器都闲着。常见做法是**线程池(thread pool)**：启动时创建有限数量的工作线程，主线程持续接收请求并分派给它们。利用率提高了，但熟悉的代价也回来报到：并发 RPC 可能需要锁和其他同步原语。

### 运行时库

运行时库承担 RPC 的重活，尤其是性能与可靠性。

第一个挑战是定位远程服务，即**命名(naming)**。简单方案利用现有主机名/IP 地址和端口号；客户端必须知道服务所在机器及端口，网络协议再负责把包路由过去。深入讨论可参阅 DNS、互联网名称解析，或 Saltzer 与 Kaashoek 的书 [SK09]。

接着要选择传输协议：可靠的 TCP，还是不可靠的 UDP？直觉说当然选 TCP——请求和回复都该可靠送达。可 TCP 的可靠性本身依赖确认和超时/重试：客户端请求后服务器回一个确认，服务器回复后客户端再回一个确认。在这种可靠层上再构建请求/响应协议，会多出两个消息。

因此许多 RPC 包直接建在 UDP 等不可靠层上，自己用超时/重试、确认与序列号提供可靠性。这样可保证无故障时每个 RPC 恰好执行一次；发生故障时，则通常只能保证**至多一次(at most once)**。

### 其他问题

远程调用可能执行很久，客户端的超时机制会误以为它失败并重试。一个方案是：服务器无法立即回复时先明确确认已收到请求；客户端随后定期询问“还在干活吗？”，服务器只要继续回答“是”，客户端便安心等下去——有些过程调用确实需要很久。

参数若大于单包容量，还需要发送端分片(fragmentation)和接收端重组(reassembly)。底层协议若不提供，RPC 运行时就得自己实现。细节可参阅 Birrell 与 Nelson 的经典论文 [BN84]。

不同机器还可能使用不同的**字节序(byte ordering)**。大端把高有效字节放前面，像我们书写阿拉伯数字；小端反过来。RPC 消息通常规定统一字节序。Sun RPC 的 XDR（eXternal Data Representation，外部数据表示）层就负责此事：机器字节序与 XDR 相同便直接收发，不同则转换每项数据，因此有一点性能成本。

最后，RPC 是否向客户端暴露通信的异步性？典型 RPC 是同步的，客户端发起调用后必须等待。**异步 RPC(asynchronous RPC)**则发出请求后立即返回，客户端可继续计算或发起其他 RPC，稍后再调用运行时等待未完成的 RPC 并取得结果。

!!! note "边栏：端到端原则"
    **端到端原则(end-to-end argument)**指出，在分层系统中，某些功能最终只有最高层——通常是“端点”处的应用——才能真正实现。Saltzer 等人用可靠文件传输说明这一点 [SRC84]：要确保机器 B 上最终得到的字节与机器 A 上最初的字节完全相同，必须进行端到端检查；网络或磁盘底层的可靠机制无法给出这个最终保证。

    即使通信协议通过超时/重试、确认和序列号保证所有字节按序送达，发送前内存中的数据可能已损坏，接收后写磁盘也可能出错。可靠网络并不会自动变出可靠文件传输。真正的做法是传输完成后从接收方磁盘读回文件，计算校验和，并与发送方文件比较。

    推论并不是“底层可靠性没用”。底层功能确实能改善性能或优化系统；只是应根据整个系统和应用的最终用途，仔细判断它是否值得存在。

## 48.6 总结

本章引入了分布式系统及其核心问题：处理已经成为家常便饭的故障。Google 内部有句话：只有一台桌面机时，故障很少见；身处拥有几千台机器的数据中心时，故障每时每刻都在发生。分布式系统的关键，就是你怎样对付它。

通信是任何分布式系统的心脏。RPC 是常见的通信抽象，让客户端调用服务器上的远程过程；RPC 包把超时/重试、确认等脏活累活藏起来，提供一个很像本地过程调用的服务。

真正理解 RPC 的最佳办法当然是亲自用一个。Sun RPC 和存根编译器 `rpcgen` 已经有些年头；Google gRPC 与 Apache Thrift 是更现代的版本。挑一个试试，看看大家到底在兴奋什么。

## 参考资料

- **[A70]** Norman Abramson, “The ALOHA System — Another Alternative for Computer Communications,” *1970 Fall Joint Computer Conference*. ALOHA 开创了指数退避和重传等基本概念，后来多年构成共享总线以太网通信的基础。
- **[BN84]** Andrew D. Birrell, Bruce Jay Nelson, “Implementing Remote Procedure Calls,” *ACM TOCS*, 2(1), 1984. 奠定后续 RPC 系统基础的经典工作；又一次来自 Xerox PARC 朋友们的开创性成果。
- **[MK09]** Theresa C. Maxino, Philip J. Koopman, “The Effectiveness of Checksums for Embedded Control Networks,” *IEEE TDSC*, 6(1), 2009. 校验和机制及性能、健壮性比较的优秀综述。
- **[LH89]** Kai Li, Paul Hudak, “Memory Coherence in Shared Virtual Memory Systems,” *ACM TOCS*, 7(4), 1989. 通过虚拟内存实现软件共享内存的开山工作。想法很诱人，只是最终既没长寿，也算不上好用。
- **[SK09]** Jerome H. Saltzer, M. Frans Kaashoek, *Principles of Computer System Design*, Morgan-Kaufmann, 2009. 优秀的系统教材，书架必备；其中关于命名的讨论尤其难得。
- **[SRC84]** Jerome H. Saltzer, David P. Reed, David D. Clark, “End-To-End Arguments in System Design,” *ACM TOCS*, 2(4), 1984. 对分层、抽象以及功能最终应落在哪里的精彩讨论。
- **[VJ88]** Van Jacobson, “Congestion Avoidance and Control,” *SIGCOMM ’88*. 客户端怎样适应网络拥塞的开创性论文，是互联网关键技术之一。严肃对待系统的人必读；Van Jacobson 的亲戚也该读——毕竟亲戚写的论文，总得捧场。

## 作业（编程）

这一节会写一些简单通信代码，帮助你熟悉这项工作。玩得开心！

1. 使用本章代码构建简单的 UDP 服务器和客户端。服务器接收客户端消息并回复确认。第一次先不加重传或健壮性机制，假设通信完美。先在一台机器测试，再在两台机器上运行。
2. 把代码改造成通信库。设计自己的 API，包括发送、接收及其他必要调用；让客户端和服务器使用你的库，而不是直接调用套接字。
3. 用超时/重试为逐渐长大的通信库加入可靠性。库必须保留待发消息副本并启动计时器；接收端确认收到的消息。客户端 `send` 应阻塞到消息获确认，并能无限重试。最大消息大小取 UDP 单个消息的上限。要高效休眠到 ack 到达或超时，别自旋着把 CPU 烤热。
4. 提高效率并增加功能：支持超大消息。网络虽然限制单包大小，你的库应接受任意长度消息；客户端分片发送，服务器端重组成连续整体，再把一个大缓冲区交给等待中的服务器代码。
5. 再做一次，但追求高性能。不要一次只发一个分片，而要快速发送多个分片以充分利用网络；仔细标记每片，确保接收端重组时不会把消息洗牌。
6. 最后的实现挑战：支持按序交付的异步消息发送。客户端可连续调用 `send`，接收端调用 `receive` 时仍可靠地按序获得消息；多个消息可同时在途。再增加一个发送端调用，让客户端等待所有未完成消息均获确认。
7. 最后一个痛点：测量。分别测量各方案在两台机器间的带宽；再测单包发送并收到确认的延迟。结果合理吗？原本预期是多少？怎样建立更好的预期，从而判断代码有问题还是运行正常？
