# 第 34 章 并发总结对话

> 英文原题：*Summary Dialogue on Concurrency*

<div class="dialogue" markdown>
**教授：** 所以，现在脑袋疼了吗？

**学生：** （吞下两片布洛芬）有一点。要把线程所有可能的交错方式都想明白，太难了。

**教授：** 确实如此。每次碰到并发执行，我都很惊讶：区区几行代码，竟然能变得几乎无法理解。

**学生：** 我也一样！身为计算机科学家，连五行代码都看不明白，多少有点丢人。

**教授：** 别太难过。去翻翻最早那批并发算法论文，有些也是错的！而且作者往往还是教授！

**学生：** （倒吸一口凉气）教授也会……呃……犯错？

**教授：** 千真万确。不过别告诉别人——这是我们这一行的商业机密。

**学生：** 我发誓保密。可并发代码这么难想、又这么难写对，我们到底怎样才能写出正确的并发代码？

**教授：** 这才是真问题，不是吗？我想可以从几件简单的事做起。第一，保持简单！避免线程之间复杂的交互，使用广为人知、久经考验的方式来管理线程协作。

**学生：** 比如简单加锁，再来一个生产者—消费者队列？

**教授：** 正是！这些都是常见模式。学完前面的内容，你应该已经能写出可用方案。第二，只有绝对必要时才使用并发；能不用就别用。没有什么比过早优化程序更糟糕。

**学生：** 明白了——既然不需要，何必硬塞几条线程进去？

**教授：** 正是。第三，如果确实需要并行性，就去寻找其他更简化的形式。例如，编写并行数据分析代码的 MapReduce 方法非常出色：它能实现并行，却不用你亲手应付锁、条件变量，以及我们讨论过的其他那些吓人玩意儿。

**学生：** MapReduce，是吧？听起来挺有意思——我得自己再多读一点。

**教授：** 很好！确实应该。说到底，你必须大量自学；我们一起学到的，只能算浩瀚知识海洋最粗浅的导论。读，读，再多读！然后动手试，写代码，再多写一些。Gladwell 在《异类》里谈过：要成为真正的专家，得在一件事上投入大约一万小时。课堂时间可塞不下这么多！

**学生：** 哇，我说不好这到底让人泄气，还是让人振奋。不过我就当它是后者，开工吧！该再写点并发代码了……
</div>
