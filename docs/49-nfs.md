# 第 49 章 Sun 网络文件系统（NFS）

> 英文原题：*Sun’s Network File System (NFS)*

分布式客户端/服务器计算最早的一类用途，就是分布式文件系统。这样的环境有多台客户端和一台（或少数几台）服务器；服务器把数据放在自己的磁盘上，客户端通过格式明确的协议消息请求数据。

```text
客户端 0 ─┐
客户端 1 ─┼── 网络 ── 服务器 ── RAID
客户端 2 ─┤
客户端 3 ─┘
```

*图 49.1：通用客户端/服务器系统。*

为何不让客户端只用本地磁盘？首要原因是便于共享：先在客户端 0 访问某文件，后来换到客户端 2，看到的仍是同一个文件系统。其次是集中管理，例如只需备份少数服务器，而不是浩浩荡荡的一群客户端。安全性也可能更好：把服务器锁进机房，至少能挡住某些麻烦。

!!! danger "问题核心：怎样构建分布式文件系统"
    分布式文件系统要怎样构建？哪些方面最值得思考？什么最容易弄错？现有系统能教给我们什么？

## 49.1 基本的分布式文件系统

简单的客户端/服务器分布式文件系统，比此前研究的本地文件系统多出一些部件。客户端应用通过**客户端文件系统(client-side file system)**访问目录和文件，仍调用 `open()`、`read()`、`write()`、`close()`、`mkdir()` 等系统调用。除性能可能不同外，它在应用看来与本地磁盘文件系统无异；这就是**透明访问(transparent access)**。毕竟，谁会喜欢一套另起炉灶、处处添堵的 API？

客户端文件系统负责完成系统调用。例如应用发出 `read()`，客户端文件系统可向**文件服务器(file server)**发送消息，请它读取某个块；服务器从磁盘或内存缓存取出数据并回复；客户端再把数据复制到 `read()` 的用户缓冲区。以后再次读同一块时，数据也许已缓存在客户端内存甚至本地磁盘中，最好情况下完全不产生网络流量。

```text
客户端应用
    │
客户端文件系统                 文件服务器
    │                              │
网络层  ════════ 网络 ════════  网络层
                                   │
                                  磁盘
```

*图 49.2：分布式文件系统体系结构。*

所以，客户端文件系统和文件服务器是两块关键软件，它们共同决定整个系统的行为。下面研究一个具体系统：Sun 网络文件系统 NFS。

!!! note "边栏：服务器为什么会崩溃"
    原因多得很。服务器可能暂时停电；几百万行代码里总会有 bug，迟早会踩中；小小的内存泄漏积累久了也能耗尽内存。分布式系统中，客户端与服务器之间还有网络；若网络分区，双方都活着却无法通信，看起来就和远端机器崩了一模一样。

## 49.2 走进 NFS

Sun Microsystems 开发了最早且非常成功的一批分布式系统之一：Sun Network File System，即 NFS [S86]。Sun 采取了不同寻常的路线：不造封闭的专有系统，而是发布开放协议，精确规定客户端和服务器通信所用的消息格式。不同团队可以开发自己的 NFS 服务器，在保持互操作性的同时竞争。

事实证明这招奏效了。Oracle/Sun、NetApp [HLM94]、EMC、IBM 等许多公司都销售过 NFS 服务器。NFS 的广泛成功，很可能正得益于这种“开放市场”方式。

## 49.3 目标：简单而快速地从服务器崩溃中恢复

本章讨论经典 NFS 第 2 版，即 NFSv2。它多年都是标准；NFSv3 只做了较小改动，NFSv4 才进行了更大规模的协议变化。NFSv2 既精彩又令人抓狂，因此正适合拿来研究。

它的主要设计目标是：**服务器崩溃后的恢复必须简单而快速**。多客户端、单服务器环境里，服务器每停一分钟，所有客户端及其用户就多一分钟不开心、不产出。服务器倒下，整个系统便跟着倒下。

## 49.4 快速崩溃恢复的关键：无状态

NFSv2 用**无状态协议(stateless protocol)**实现目标。服务器刻意不追踪每个客户端正在做什么：不知道谁缓存了哪些块、谁打开了哪些文件，也不知道文件的当前偏移。每个协议请求必须自带完成操作所需的一切信息。

先看有状态的反例。`open()` 接收路径名并返回文件描述符，后续 `read()`、`write()` 都靠它访问文件：

```c
char buffer[MAX];
int fd = open("foo", O_RDONLY); // 获得描述符 fd
read(fd, buffer, MAX);          // 从 foo 读取 MAX 字节
read(fd, buffer, MAX);
// ...
read(fd, buffer, MAX);
close(fd);
```

*图 49.3：客户端代码——读取文件。*

假设客户端向服务器发送“打开 `foo`，给我一个描述符”，服务器在本地打开文件，再把描述符返回。后续客户端传这个描述符，请服务器读取它所指的文件。此时文件描述符成为客户端与服务器之间的**共享状态(shared state)**；Ousterhout 称之为**分布式状态(distributed state)** [O91]。

共享状态使崩溃恢复复杂化。若服务器在第一次 `read()` 后、第二次之前崩溃，重启后收到第二次读取时，它已经不知道 `fd` 指向什么，因为内存里的临时信息全丢了。客户端与服务器不得不执行恢复协议，由客户端保存足够信息，再告诉服务器“这个 `fd` 原来指 `foo`”。

客户端崩溃更麻烦。客户端打开文件后宕机，占用的服务器描述符由谁关闭？正常客户端最终会调用 `close()`，崩掉的客户端却永远不会。服务器还得发现它死了，才能清理资源。

所以 NFS 选择无状态：每次操作都携带完成请求的全部信息。服务器重启后直接继续服务；最坏也不过是客户端重试。

## 49.5 NFSv2 协议

!!! danger "问题核心：怎样定义无状态文件协议"
    怎样让网络协议保持无状态，同时支持 POSIX 的 `open()`、`read()`、`write()`、`close()` 等文件 API？显然，要求服务器追踪已打开文件的有状态 `open()` 不能直接成为协议操作。

理解 NFS 协议的关键是**文件句柄(file handle)**。它唯一描述操作目标文件或目录，因此许多请求都携带文件句柄。

文件句柄可看成由三部分组成：

- **卷标识符(volume identifier)**：请求属于服务器导出的哪个文件系统；
- **inode 号**：访问该分区中的哪个文件；
- **世代号(generation number)**：inode 号每次重用时递增，防止持有旧句柄的客户端误访问新分配文件。

下面列出协议的重要部分，完整细节可参阅 Callaghan 的著作 [C00]：

| 协议过程 | 参数 | 返回 |
|---|---|---|
| `NFSPROC_GETATTR` | 文件句柄 | 属性 |
| `NFSPROC_SETATTR` | 文件句柄、属性 | 无 |
| `NFSPROC_LOOKUP` | 目录句柄、待查文件/目录名 | 文件句柄 |
| `NFSPROC_READ` | 文件句柄、偏移、计数 | 数据、属性 |
| `NFSPROC_WRITE` | 文件句柄、偏移、计数、数据 | 属性 |
| `NFSPROC_CREATE` | 目录句柄、文件名、属性 | 无 |
| `NFSPROC_REMOVE` | 目录句柄、待删文件名 | 无 |
| `NFSPROC_MKDIR` | 目录句柄、目录名、属性 | 文件句柄 |
| `NFSPROC_RMDIR` | 目录句柄、待删目录名 | 无 |
| `NFSPROC_READDIR` | 目录句柄、读取字节数、cookie | 目录项、用于继续读取的 cookie |

*图 49.4：NFS 协议示例。*

`LOOKUP` 用于取得后续访问数据所需的文件句柄。客户端传目录句柄与待查名称，服务器返回目标文件或目录的句柄及属性。例如客户端通过挂载协议拿到根目录 `/` 的句柄后，应用打开 `/foo.txt`，客户端文件系统便发送根句柄和名字 `foo.txt`；成功后得到它的句柄与属性。

属性就是文件系统保存的元数据，包括创建时间、最后修改时间、大小、所有者、权限等，与对文件调用 `stat()` 得到的信息同类。

拿到句柄后，客户端用 `READ` 和 `WRITE` 读写。`READ` 带文件句柄、文件内偏移和字节数；服务器据此确定卷、inode 与所需字节，返回数据或错误。`WRITE` 类似，只是数据从客户端传给服务器。

`GETATTR` 根据句柄取得文件属性，尤其是最后修改时间。等谈到缓存，你就会看出它为何重要——也许现在已经猜到了。

## 49.6 从协议到分布式文件系统

客户端文件系统追踪已打开文件，并把应用请求翻译成协议消息；服务器只回应自带完整信息的请求。

下例展示应用读取 `/foo` 时双方的动作：

| 客户端 | 服务器 |
|---|---|
| `fd = open("/foo", ...)`；发送 `LOOKUP(rootdir_FH, "foo")` | 接收请求，在根目录找 `foo`，返回其句柄与属性 |
| 收到回复；在打开文件表分配描述符，保存句柄和当前位置 0；把 `fd` 返回应用 | — |
| `read(fd, buffer, MAX)`；由 `fd` 找到句柄，以当前位置为偏移；发送 `READ(FH, offset=0, count=MAX)` | 由句柄找卷与 inode，读 inode，按偏移计算块位置，从磁盘或缓存读数据并返回 |
| 收到回复；把当前位置更新为 `MAX`，向应用返回数据或错误 | — |
| 再次 `read()`：偏移为 `MAX`，完成后位置变为 `2*MAX` | 同上 |
| 再次 `read()`：偏移为 `2*MAX`，完成后位置变为 `3*MAX` | 同上 |
| `close(fd)`：只清理本地打开文件表，无需联系服务器 | — |

*图 49.5：读取文件时客户端与文件服务器的动作。*

几点值得注意。第一，客户端保存文件描述符到 NFS 句柄的映射及当前文件指针，所以即使应用的 `read()` 没显式传偏移，客户端也能构造完整的 NFS 请求；成功读取后再推进文件位置。

第二，首次打开文件会触发 `LOOKUP`。若路径很长，例如 `/home/remzi/foo.txt`，客户端需要三次查找：先在 `/` 找 `home`，再在 `home` 找 `remzi`，最后在 `remzi` 找 `foo.txt`。

第三，每个服务器请求都有独立完成操作所需的一切。这是优雅恢复服务器故障的关键：服务器无需保存状态也能回应。

## 49.7 用幂等操作处理服务器故障

!!! tip "幂等性很强大"
    **幂等(idempotent)**操作可安全执行多次，处理失败时直接重试即可；非幂等操作则会让生活陡然复杂。

客户端发出请求后，有时收不到回复：请求或回复可能被网络丢掉，服务器也可能已经崩溃。它稍后或许会重启，但当前请求已经无影无踪。NFSv2 用统一而优雅的办法处理这些情况：**重试**。

发送请求后，客户端启动计时器。回复先到，一切安好；计时器先响，就假定请求未处理并重发。之所以敢这么做，是因为多数 NFS 请求都具有幂等性：执行多次的效果与执行一次相同。

向同一内存位置存同一个值三次，与存一次效果相同；它是幂等的。把计数器递增三次，与递增一次当然不同；它不是幂等的。纯读取天然幂等，更新操作则须仔细判断。

`LOOKUP` 和 `READ` 只读取服务器信息，显然幂等。更有意思的是 `WRITE`：消息包含数据、计数以及精确偏移，重复写同一位置与写一次结果相同。

```text
情形 1：请求丢失       客户端 --请求--X 服务器
情形 2：服务器宕机     客户端 --请求--> [服务器宕机]
情形 3：回复丢失       客户端 --请求--> 服务器处理 --回复--X
```

*图 49.6：三种丢失。*

若请求丢失，重试后服务器执行写入；若服务器当时宕机，重启后重试成功；若服务器其实完成了写入但回复丢失，重试只会把同样数据再写到同一位置。三种故障被同一机制处理，漂亮！

当然，某些操作很难幂等。例如第一次 `MKDIR` 成功但回复丢失，客户端重试时会因目录已存在而收到失败，尽管原操作其实成功了。生活毕竟不完美。

!!! tip "完美是优秀之敌（伏尔泰定律）"
    即使设计出漂亮系统，边角情况也未必处处称心。可以重新定义 `mkdir` 使之幂等，但值得吗？NFS 已覆盖大多数重要情况，并让故障处理整体保持干净简单。接受世界不完美、仍把系统造出来，正是优秀工程的标志。伏尔泰曾转述：“一位睿智的意大利人说，最好是好的敌人。”[V72]

## 49.8 提升性能：客户端缓存

每次读写都穿过网络，性能会很糟，因为网络通常远慢于本地内存或磁盘。标题已经用粗体把答案喊出来了：**客户端缓存(client-side caching)**。

NFS 客户端文件系统把从服务器读取的文件数据和元数据缓存在本机内存。第一次访问需要网络，后续访问可直接由内存快速满足。

缓存也是写入的临时缓冲。应用调用 `write()` 时，客户端先把数据放入内存缓存，立即向应用报告成功，稍后再写回服务器。这样，应用看到的写延迟与真正写入性能解耦。

于是性能很好，故事结束？没那么轻松。多个客户端各有缓存，会引出巨大而有趣的**缓存一致性问题(cache consistency problem)**。

## 49.9 缓存一致性问题

设客户端 C1 读取文件 F，并缓存旧版本 `F[v1]`；C2 覆盖 F，在缓存中得到新版本 `F[v2]`；C3 尚未访问 F；服务器最初仍有 `F[v1]`，最终才会变成 `F[v2]`。

```text
C1 缓存：F[v1]    C2 缓存：F[v2]    C3 缓存：空
                         │
服务器磁盘：起初 F[v1]，最终 F[v2]
```

*图 49.7：缓存一致性问题。*

它包含两个子问题。

第一是**更新可见性(update visibility)**。C2 可能把写入在本地缓存一阵子才发给服务器；在此期间 C3 访问 F，只能取得旧版。想象你在 C2 更新文件，转身登录 C3，却读到旧内容，多少有点让人想和电脑谈谈人生。问题是：一个客户端的更新何时对其他客户端可见？

第二是**陈旧缓存(stale cache)**。即使 C2 已把 `F[v2]` 刷到服务器，C1 仍缓存着 `F[v1]`，在 C1 上读取就会得到旧版。

NFSv2 用两种办法处理：

1. 对更新可见性采用**关闭时刷新(flush-on-close)**，也叫**关闭到打开(close-to-open)一致性**。客户端写过文件并关闭时，把所有脏页刷到服务器，保证另一节点随后打开时看见最新版。
2. 对陈旧缓存，客户端使用缓存块前先发 `GETATTR`，取回服务器上的最后修改时间。若它晚于该文件进入客户端缓存的时间，便使本地副本失效，之后重新从服务器获取；否则继续使用缓存。

Sun 的原始团队很快发现了新问题：服务器被 `GETATTR` 淹没。常见情况是文件只由一个客户端反复访问，却仍不断问服务器：“有人改过它吗？现在呢？现在呢？”大多数时候答案都是“没有”。

于是每个客户端又加了**属性缓存(attribute cache)**。访问文件时仍要验证，但通常只查本地属性缓存。文件首次访问时放入属性，过一段时间（如 3 秒）才过期；在这 3 秒里都直接使用缓存文件，不联系服务器。

## 49.10 评估 NFS 缓存一致性

关闭时刷新“讲得通”，却带来性能问题：客户端创建一个短命临时文件后立刻删除，仍必须先把它送到服务器。更理想的实现也许能一直留在内存，到删除时直接消失，完全省掉服务器交互。

更重要的是，属性缓存使“这次读到哪个版本”变得难以推理。有时是最新版；有时只是因为属性缓存尚未超时，客户端便愉快地交出内存里的旧版。多数时候没事，但它偶尔会——而且至今仍会——产生古怪行为。

这就是 NFS 客户端缓存的奇特之处：不是先定义用户可见语义再实现，而是实现细节反过来塑造了用户可见语义。

## 49.11 对服务器端写缓冲的影响

NFS 服务器通常也有大量内存。磁盘读出的数据和元数据会保留在内存，后续读取不必再次访问磁盘，带来一点性能提升。

写缓冲却更棘手：NFS 服务器在把写入强制送达**稳定存储(stable storage)**之前，绝不能对 `WRITE` 返回成功。服务器可以在内存留副本，但不能提前报喜。

假设客户端依次覆盖文件的三个块：

```c
write(fd, a_buffer, size); // 第一块填 a
write(fd, b_buffer, size); // 第二块填 b
write(fd, c_buffer, size); // 第三块填 c
```

初始文件是三块 `x`、`y`、`z`，预期最终成为 `a`、`b`、`c`：

```text
xxxxxxxx...        aaaaaaaa...
yyyyyyyy...   →    bbbbbbbb...
zzzzzzzz...        cccccccc...
```

若第一块已落盘并成功回复，第二块只在服务器内存中却也回复成功，随后服务器崩溃；重启后第三块又成功，那么客户端以为三个写入全成功，文件却成了：

```text
aaaaaaaa...
yyyyyyyy...  <--- 糟糕
cccccccc...
```

哎呀！第二次写入的旧内容留了下来，对应用可能是灾难。因此，服务器必须先把每次写入提交到持久介质，再告知客户端成功。若中途崩溃，客户端检测到失败并重试，直至真正成功。

代价是写性能可能成为 NFS 服务器的主要瓶颈。Network Appliance 等公司正是为打造快速 NFS 服务器而生。一个技巧是先把写入放进电池供电内存，既能快速回复，又不怕掉电丢数据；另一个技巧是使用需要落盘时能迅速写入的专门文件系统 [HLM94, RO91]。

!!! note "边栏：创新催生创新"
    NFS 要成功，也需要其他基础创新。其中最持久的也许是 Sun 引入的**虚拟文件系统/虚拟节点(VFS/vnode)**接口，它让不同文件系统能方便地插入操作系统 [K86]。

    VFS 层包含作用于整个文件系统的操作，如挂载、卸载、取得全局统计和把全部脏数据刷盘；vnode 层包含对单个文件的 `open`、`close`、读写等操作。新文件系统只需定义这些“方法”，框架负责把系统调用连接到具体实现，并集中完成缓存等通用功能，使多种文件系统能在同一系统里并存。

    细节虽已演变，Linux、BSD、macOS，甚至 Windows（可安装文件系统）都仍有某种 VFS/vnode 层。即使 NFS 有朝一日淡出，它打下的地基还会继续服役。

## 49.12 总结

NFS 围绕服务器故障后的简单、快速恢复设计，并通过谨慎的协议设计达到目标。操作幂等至关重要：客户端可安全重放失败操作，无论服务器此前是否已经执行过它。

!!! note "边栏：NFS 关键术语"
    - **无状态协议**使服务器崩溃后可以快速重启并继续服务；客户端只需重试到成功。
    - **幂等请求**让同一操作执行多次仍等同于一次，统一处理消息丢失与服务器崩溃。
    - 客户端缓存和写缓冲改善性能，也引入缓存一致性问题。
    - **关闭时刷新**让文件关闭时把内容送到服务器；**属性缓存**则减少通过 `GETATTR` 检查文件变化的频率。
    - 服务器必须先把写入提交到持久介质，才能返回成功。
    - Sun 为把 NFS 集成进操作系统而引入 VFS/vnode 接口，使多种文件系统实现能够共存。

多个客户端缓存让系统更复杂。NFS 以稍显临时拼凑的办法处理一致性，偶尔产生用户可观察到的古怪行为；服务器缓存也不简单，写入必须先落到稳定存储才能确认。

本章没有展开安全问题。早期 NFS 安全性松得惊人，客户端上的用户很容易冒充他人，进而访问几乎任意文件。后来与 Kerberos [NT94] 等严肃认证服务集成，才修补了这些显眼的缺口。
