# 第 2 章 操作系统导论

> 英文原题：*Introduction to Operating Systems*

如果你正在上一门本科操作系统课程，那么你应该已经对计算机程序运行时会做什么有些概念。要是没有，这本书（以及配套课程）恐怕会很难——所以你最好先停下来，冲进最近的书店，把必要的背景材料迅速啃完再继续（Patt 与 Patel 的书 [PP03]，以及 Bryant 与 O’Hallaron 的书 [BOH10] 都相当不错）。

那么，程序运行时究竟会发生什么？

运行中的程序其实只做一件非常简单的事：**执行指令**。处理器每秒要重复几百万次（如今甚至几十亿次）这样的循环：从内存中**取出(fetch)** 一条指令，**解码(decode)** 它（也就是弄清这是什么指令），再**执行(execute)** 它（也就是做它该做的事，例如把两个数相加、访问内存、检查条件、跳转到函数，等等）。执行完这条指令，处理器就转向下一条，如此反复，直到程序最终结束[^1]。

刚才描述的，就是**冯·诺依曼计算模型(Von Neumann model of computing)** 的基础[^2]。听起来很简单，对吧？但这门课会告诉你：程序运行时，背后还有一大堆疯狂的事情同时发生，而它们的首要目标，是让系统容易使用。

事实上，有一整套软件负责让程序能够轻松运行（甚至让你觉得许多程序在同时运行）、让程序共享内存、让程序与设备交互，以及完成其他诸如此类的有趣工作。这套软件就叫作**操作系统(operating system, OS)**[^3]，因为它负责确保系统以一种正确、高效而又易用的方式运转。

!!! danger "问题核心"
    **如何虚拟化资源？**

    本书要回答的一个核心问题非常简单：操作系统如何**虚拟化资源**？这就是问题的关键。操作系统为什么要这样做并不是重点，因为答案显而易见：这让系统更容易使用。因此，我们关注的是「如何」：操作系统实现了哪些机制和策略来达成虚拟化？怎样才能高效地做到这一点？需要哪些硬件支持？

    本书会用这种带底色的「问题核心」框，点出构建操作系统时需要解决的具体问题。因此，在讨论某个主题的章节中，你可能会看到一个或多个问题核心；它们负责突出问题，而章节里的细节则会给出解决方案，或者至少划定解决方案的基本轮廓。

操作系统完成这些工作的主要手段，是一种称为**虚拟化(virtualization)** 的通用技术。也就是说，操作系统拿到一种物理资源（比如处理器、内存或磁盘），把它变成一种更通用、更强大、更易用的虚拟形式。因此，我们有时也把操作系统称作**虚拟机(virtual machine)**。

当然，为了让用户能够告诉操作系统该做什么，进而使用虚拟机的功能（例如运行程序、分配内存或访问文件），操作系统还会提供一些可供调用的**接口(API)**。事实上，一个典型的操作系统会向应用程序开放几百个**系统调用(system call)**。操作系统通过这些调用提供运行程序、访问内存和设备等功能，所以我们有时也说，操作系统为应用程序提供了一套**标准库(standard library)**。

最后，虚拟化让许多程序都能运行（因而共享 CPU），让许多程序可以并发访问各自的指令和数据（因而共享内存），也让许多程序能够访问设备（因而共享磁盘等资源），所以操作系统有时又被称作**资源管理器(resource manager)**。CPU、内存和磁盘都是系统资源；操作系统的职责就是管理这些资源，可能追求效率、公平，或者其他许许多多的目标。为了更好地理解操作系统扮演的角色，我们来看几个例子。

## 2.1 虚拟化 CPU

下面是我们的第一个程序。它没做多少事：只调用 `Spin()`。这个函数会反复检查时间，运行一秒后返回；随后程序打印用户从命令行传入的字符串，再从头重复，永不停歇。

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/time.h>
#include <assert.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "usage: cpu <string>\n");
        exit(1);
    }
    char *str = argv[1];
    while (1) {
        Spin(1);
        printf("%s\n", str);
    }
    return 0;
}
```

*图 2.1：一个不断循环并打印内容的简单程序（`cpu.c`）。*

假设我们把这个文件保存为 `cpu.c`，然后在一台只有一个处理器（也就是我们常说的 CPU）的机器上编译并运行它，会看到：

```console
prompt> gcc -o cpu cpu.c -Wall
prompt> ./cpu "A"
A
A
A
A
^C
prompt>
```

这次运行没什么意思——系统开始运行程序；程序反复查看时间，直到一秒过去，然后打印用户传入的字符串（这里是字母 `A`），再继续循环。注意，这个程序会永远运行下去；只有按下 `Control-c`（在基于 UNIX 的系统上，这会终止前台运行的程序）才能停掉它。

现在再做一次同样的事，不过这回同时运行这个程序的多个实例。结果稍微有趣了一点：

```console
prompt> ./cpu A & ; ./cpu B & ; ./cpu C & ; ./cpu D &
[1] 7353
[2] 7354
[3] 7355
[4] 7356
A
B
D
C
A
B
D
C
A
C
B
D
...
```

*图 2.2：同时运行多个程序。*

现在事情变得有意思了。明明只有一个处理器，不知怎么地，四个程序看起来竟然同时在运行！这场魔法是怎么变出来的[^4]？

原来，操作系统会在硬件的帮助下营造这种幻象——让系统看起来拥有数量庞大的虚拟 CPU。把一颗 CPU（或一小组 CPU）变成看似无限多颗 CPU，让许多程序看起来可以同时运行，这就是所谓的**虚拟化 CPU**，也是本书第一大部分关注的主题。

当然，要想运行和停止程序，或者用其他方式告诉操作系统该运行哪些程序，就必须有一些接口(API)，让你可以把自己的意图传达给操作系统。整本书都会讨论这些 API；事实上，大多数用户主要就是通过它们与操作系统交互。

你可能也注意到了，同时运行多个程序会引出各种新问题。例如，假如两个程序此刻都想运行，究竟该运行哪一个？这个问题由操作系统的某项**策略(policy)** 回答。操作系统会在许多地方使用策略来回答这类问题。因此，在学习操作系统实现的基本**机制(mechanism)**（例如同时运行多个程序的能力）时，我们也会研究这些策略。这又体现了操作系统作为资源管理器的角色。

## 2.2 虚拟化内存

接下来考虑内存。现代机器呈现出来的**物理内存(physical memory)** 模型非常简单：内存就是一个字节数组。要读取内存，必须给出一个**地址(address)**，才能访问其中存放的数据；要写入（或更新）内存，则既要给出地址，也要给出准备写到该地址的数据。

程序运行时会不停地访问内存。程序把所有数据结构放在内存里，并通过各种指令来访问它们，例如加载、存储指令，或者其他在工作过程中显式访问内存的指令。别忘了，程序的每条指令本身也在内存中，因此每次取指令同样要访问内存。

来看一个调用 `malloc()` 分配内存的程序：

```c
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <assert.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    int *p = malloc(sizeof(int));                         // a1
    assert(p != NULL);
    printf("(%d) address pointed to by p: %p\n",
           getpid(), p);                                 // a2
    *p = 0;                                              // a3
    while (1) {
        Spin(1);
        *p = *p + 1;
        printf("(%d) p: %d\n", getpid(), *p);           // a4
    }
    return 0;
}
```

*图 2.3：一个访问内存的程序（`mem.c`）。*

程序的输出如下：

```console
prompt> ./mem
(2134) address pointed to by p: 0x200000
(2134) p: 1
(2134) p: 2
(2134) p: 3
(2134) p: 4
(2134) p: 5
^C
```

这个程序做了几件事。首先，它分配了一些内存（a1）；然后打印这块内存的地址（a2），并把数字 0 放进刚分配内存的第一个位置（a3）。最后，它进入循环：每次延迟一秒，再把 `p` 所保存地址里的值加一。每次打印时，它还会输出正在运行的程序的**进程标识符(process identifier, PID)**。每个运行中的进程都有一个唯一的 PID。

第一次运行没什么意外。新分配的内存位于地址 `0x200000`；程序运行时缓慢更新里面的值，并打印结果。

现在再次同时运行这个程序的多个实例，看看会发生什么：

```console
prompt> ./mem &; ./mem &
[1] 24113
[2] 24114
(24113) address pointed to by p: 0x200000
(24114) address pointed to by p: 0x200000
(24113) p: 1
(24114) p: 1
(24114) p: 2
(24113) p: 2
(24113) p: 3
(24114) p: 3
(24113) p: 4
(24114) p: 4
...
```

*图 2.4：多次运行内存程序。*

从例子中可以看到，每个运行中的程序都在同一个地址 `0x200000` 分配了内存，可它们似乎又在彼此独立地更新 `0x200000` 中的值！仿佛每个运行中的程序都拥有自己的私有内存，而不是和其他程序共享同一块物理内存[^5]。

事实正是如此，因为操作系统正在虚拟化内存。每个进程访问的，都是它自己的私有**虚拟地址空间(virtual address space)**（有时简称**地址空间(address space)**），操作系统会设法把它映射到机器的物理内存上。一个运行中的程序所发出的内存引用，不会影响其他进程（或操作系统本身）的地址空间；在这个程序看来，整块物理内存都归它独享。然而实际上，物理内存是一种由操作系统管理的共享资源。这一切究竟如何实现，同样是本书第一部分「虚拟化」的主题。

## 2.3 并发

本书的另一个主要主题是**并发(concurrency)**。这个概念涵盖了这样一大类问题：同一个程序同时（也就是并发地）处理许多事情时，会出现哪些问题，又该如何解决？并发问题最早出现在操作系统内部。正如前面的虚拟化例子所展示的，操作系统同时周旋于许多事情之间：先运行一个进程，再运行另一个，如此往复。事实证明，这会带来一些深刻而有趣的问题。

遗憾的是，并发问题早已不再局限于操作系统本身。现代多线程程序也会遇到同样的问题。下面用一个**多线程(multi-threaded)** 程序演示：

```c
#include <stdio.h>
#include <stdlib.h>
#include "common.h"

volatile int counter = 0;
int loops;

void *worker(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}

int
main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "usage: threads <value>\n");
        exit(1);
    }
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);

    Pthread_create(&p1, NULL, worker, NULL);
    Pthread_create(&p2, NULL, worker, NULL);
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("Final value   : %d\n", counter);
    return 0;
}
```

*图 2.5：一个多线程程序（`threads.c`）。*

你现在可能还不能完全理解这个例子（本书并发部分的后续章节会讲得更多），但基本思路很简单。主程序用 `Pthread_create()`[^6] 创建两个**线程(thread)**。你可以把线程想成一个和其他函数在同一内存空间里运行的函数，只不过同一时间可以有多个线程处于活动状态。在这个例子中，每个线程都从名为 `worker()` 的例程开始运行，只做一件事：在循环中把计数器递增 `loops` 次。

下面是把变量 `loops` 的输入值设为 1000 时，程序运行的记录。`loops` 决定两个工作线程分别要把共享计数器递增多少次。你觉得两个线程各递增 1000 次后，`counter` 的最终值会是多少？

```console
prompt> gcc -o thread thread.c -Wall -pthread
prompt> ./thread 1000
Initial value : 0
Final value   : 2000
```

正如你可能猜到的，两个线程都结束后，计数器的最终值是 2000，因为每个线程各把它递增了 1000 次。一般来说，当 `loops` 的输入值是 $N$ 时，我们预期程序最后输出 $2N$。然而事实证明，生活并没有这么简单。把 `loops` 调大，再运行同一个程序：

```console
prompt> ./thread 100000
Initial value : 0
Final value   : 143012    // 啥？？
prompt> ./thread 100000
Initial value : 0
Final value   : 137298    // 什么鬼？？
```

这次输入 100,000，最终得到的不是 200,000，而是 143,012。再运行一遍，不但答案还是错的，甚至和上一次的错法都不一样，变成了 137,298。事实上，如果反复用较大的 `loops` 值运行程序，有时你甚至会得到正确答案！这到底是怎么回事？

!!! danger "问题核心"
    **如何构建正确的并发程序？**

    当同一内存空间里有许多线程并发执行时，怎样才能构建一个正确工作的程序？操作系统需要提供哪些原语？硬件应该提供哪些机制？我们又该如何利用它们解决并发问题？

这些古怪结果的原因，与指令每次只执行一条的方式有关。上面程序中递增共享计数器的关键部分，实际上需要三条指令：先把计数器的值从内存加载到寄存器，再将其递增，最后写回内存。因为这三条指令不是**原子地(atomically)**（一次全部）执行的，奇怪的事情便可能发生。这正是本书第二部分将详细解决的并发问题。

## 2.4 持久化

课程的第三大主题是**持久化(persistence)**。系统内存中的数据很容易丢失，因为 DRAM 等设备以**易失性(volatile)** 方式保存数值；一旦断电或系统崩溃，内存里的数据就没了。因此，我们需要硬件和软件把数据**持久地(persistently)** 保存下来。用户非常在乎自己的数据，所以持久存储对任何系统都至关重要。

硬件以某种**输入/输出(input/output, I/O)设备**的形式出现。在现代系统中，硬盘通常用来保存长期信息；不过**固态硬盘(solid-state drive, SSD)** 也正在这个领域攻城略地。

操作系统中通常负责管理磁盘的软件叫作**文件系统(file system)**。它负责把用户创建的文件可靠、高效地存放到系统磁盘上。

与操作系统为 CPU 和内存提供的抽象不同，操作系统不会为每个应用创建一块私有的虚拟磁盘。相反，我们假定用户常常需要共享文件中的信息。例如，编写 C 程序时，你可能先用编辑器（比如 Emacs[^7]）创建并编辑 C 文件（`emacs -nw main.c`）；完成后，再用编译器把源代码变成可执行文件（比如 `gcc -o main main.c`）；最后运行这个新程序（比如 `./main`）。由此可见，文件会在不同进程之间共享：Emacs 先创建一个文件作为编译器的输入；编译器拿这个输入文件，经过许多步骤生成新的可执行文件（细节请去上编译原理课）；最后，新生的可执行程序开始运行。于是，一个新程序诞生了！

为了看得更清楚，下面的代码会创建文件 `/tmp/file`，其中包含字符串 `hello world`。

```c
#include <stdio.h>
#include <unistd.h>
#include <assert.h>
#include <fcntl.h>
#include <sys/types.h>

int
main(int argc, char *argv[])
{
    int fd = open("/tmp/file", O_WRONLY | O_CREAT | O_TRUNC, S_IRWXU);
    assert(fd > -1);
    int rc = write(fd, "hello world\n", 13);
    assert(rc == 13);
    close(fd);
    return 0;
}
```

*图 2.6：一个执行 I/O 的程序（`io.c`）。*

程序为了完成任务，三次调用操作系统。第一次调用 `open()`，打开并创建文件；第二次调用 `write()`，向文件写入一些数据；第三次调用 `close()`，关闭文件，表示程序不会再向它写入数据。这些系统调用被转交给操作系统中称为文件系统的部分；文件系统处理请求，再向用户返回某种错误码。

!!! danger "问题核心"
    **如何持久地存储数据？**

    文件系统是操作系统中负责管理持久数据的部分。怎样才能正确地完成这项工作？要实现高性能，需要哪些机制和策略？面对硬件与软件故障，又该如何保证可靠性？

你可能会好奇，操作系统实际写磁盘时究竟做了什么。我们倒是可以展示给你看，不过你得先答应闭上眼睛；场面就是这么不堪。文件系统要做相当多的工作：先确定新数据应该放在磁盘的什么位置，再用自己维护的各种结构把位置记录下来。这要求向底层存储设备发出 I/O 请求，以读取已有结构或更新（写入）它们。任何写过设备驱动程序[^8]的人都知道，让设备替你办事是一套错综复杂、细节繁多的流程；你必须透彻理解底层设备接口及其确切语义。幸运的是，操作系统通过系统调用提供了一套标准而简单的设备访问方式。因此，操作系统有时也被看作一套标准库。

当然，如何访问设备、文件系统如何在设备之上持久管理数据，还有大量细节。出于性能考虑，大多数文件系统会先把写操作推迟一阵，希望将它们攒成更大的批次。为了应对写入过程中系统崩溃的问题，大多数文件系统会采用某种精巧的写入协议，比如**日志(journaling)** 或**写时复制(copy-on-write)**，仔细安排写磁盘的顺序，确保即使在写入序列中途发生故障，系统之后仍能恢复到合理状态。为了高效执行各种常见操作，文件系统还会使用许多数据结构和访问方法，从简单的链表到复杂的 B 树，应有尽有。如果这些现在还让你一头雾水，那就对了！本书第三部分「持久化」还会大谈这些内容：先讨论一般意义上的设备和 I/O，再详细研究磁盘、RAID 和文件系统。

## 2.5 设计目标

现在，你应该多少了解操作系统究竟在做什么了：它拿到 CPU、内存或磁盘等物理资源，并把它们虚拟化；它处理与并发有关的棘手问题；它还持久地保存文件，让它们长期安然无恙。既然要构建这样的系统，我们就需要先确定一些目标，以便聚焦设计和实现，并在必要时作出取舍。找到正确的一组取舍，是构建系统的关键。

最基本的目标之一，是建立一组**抽象(abstraction)**，让系统方便而易用。抽象是我们在计算机科学中所做一切的根基。有了抽象，我们才能把大型程序拆成小而易懂的部件；才能用 C[^9] 这样的高级语言编程而不用考虑汇编；才能写汇编而不用考虑逻辑门；也才能用逻辑门构造处理器而不必时刻惦记晶体管。抽象如此基础，以至于我们有时会忘掉它的重要性——但本书不会。每一部分都会讨论一些经过长期发展形成的重要抽象，为你提供思考操作系统各个部件的方式。

设计和实现操作系统的另一个目标是提供**高性能(high performance)**；换句话说，就是尽量降低操作系统的**开销(overhead)**。虚拟化以及让系统易用当然值得，但不能不计代价。因此，我们必须努力在不产生过多开销的情况下提供虚拟化及其他操作系统功能。开销有多种形式，包括额外的时间（更多指令）和额外的空间（内存或磁盘）。只要可能，我们会寻找能减少其中一种、或同时减少两种开销的方案。然而完美并非总能企及；我们会学着发现这一点，并在适当的时候容忍它。

另一个目标，是在应用程序之间，以及操作系统与应用程序之间提供**保护(protection)**。既然要允许许多程序同时运行，就必须确保某个程序的恶意行为或意外错误不会伤害其他程序；当然更不能让应用程序伤害操作系统本身，否则系统上的所有程序都会受到影响。保护是操作系统一项基本原则——**隔离(isolation)**——的核心。让进程彼此隔离，是实现保护的关键，也构成了操作系统许多工作的基础。

操作系统还必须不间断运行；一旦它出故障，系统上运行的所有应用程序也会跟着失败。由于存在这种依赖，操作系统通常力求提供高度的**可靠性(reliability)**。随着操作系统日益复杂（有时包含数百万行代码），构建可靠的操作系统相当困难——事实上，这个领域仍有大量研究（包括我们自己的工作 [BS+09, SS+10]）专门解决这一问题。

其他目标也同样合理：在日益重视环保的世界里，能源效率很重要；尤其是在高度联网的时代，防范恶意应用的安全性（其实是保护的延伸）至关重要；随着操作系统被放进越来越小的设备，移动性也变得越来越重要。系统用途不同，操作系统的目标也不同，实现方式多半也会有些差异。不过我们会看到，本书介绍的许多操作系统构建原则都适用于形形色色的设备。

## 2.6 一点历史

结束导论之前，我们简单回顾一下操作系统的发展史。和人类构建的所有系统一样，工程师在实践中不断认识到设计中什么最重要，好的想法也随时间逐渐积累。这里只谈几个重大进展；想读更丰富的介绍，可以参考 Brinch Hansen 那篇精彩的操作系统史 [BH00]。

### 早期操作系统：只是一些库

最初，操作系统没做多少事情。它基本上只是一组常用函数库。例如，不必让系统上的每个程序员都自己编写底层 I/O 处理代码，「操作系统」会提供这样的 API，让开发者轻松一些。

在那些古老的大型机系统上，通常一次只运行一个程序，由人类操作员控制。今天你以为操作系统该做的许多事情（比如决定作业的运行顺序），当时都由操作员完成。如果你是个机灵的开发者，最好对这位操作员客气一点，说不定他会把你的作业挪到队首。

这种计算方式叫作**批处理(batch processing)**：操作员准备好许多作业，再把它们作为一个「批次」运行。当时，计算机并不以交互方式使用，原因是成本：让一个用户坐在计算机前操作，机器大部分时间会闲在那里，每小时却要耗掉设施数十万美元，实在太贵了 [BH00]。

### 超越函数库：保护

操作系统不再只是常用服务的简单函数库后，便开始在机器管理中扮演更加核心的角色。其中一个重要进展，是人们意识到：代表操作系统运行的代码具有特殊地位；它控制着设备，因此应该和普通应用程序代码区别对待。为什么？想象一下，要是允许任何应用读取磁盘上的任意位置，隐私观念就可以直接扔出窗外了——因为任何程序都能读取任何文件。所以，把管理文件的文件系统实现成普通函数库并不合理；我们需要别的办法。

于是，**系统调用(system call)** 的概念诞生了，Atlas 计算系统在这方面做了开创性工作 [K+61, L78]。操作系统例程不再作为普通函数库提供（也就是不能只通过过程调用访问）；新思路是在硬件中加入一对特殊指令和相应状态，让进入操作系统变成一套更加正式、受控的过程。

系统调用与过程调用的关键区别在于：系统调用把控制权转移（也就是跳转）到操作系统，同时提升硬件的**特权级(privilege level)**。用户应用运行在所谓的**用户态(user mode)**，硬件会限制应用程序能做的事情。例如，在用户态运行的应用通常不能向磁盘发起 I/O 请求，不能访问任意物理内存页，也不能在网络上发送数据包。发起系统调用时（通常通过一条叫作**陷入(trap)** 的特殊硬件指令），硬件会把控制权交给一个预先指定的陷阱处理程序（由操作系统事先设置），同时把特权级提升到**内核态(kernel mode)**。在内核态下，操作系统可以完全访问系统硬件，于是能够发起 I/O 请求，或者为程序提供更多内存。操作系统处理完请求后，会通过一条特殊的**从陷入返回(return-from-trap)** 指令把控制权交还用户；这条指令在恢复用户态的同时，也让应用从离开的地方继续执行。

### 多道程序设计时代

操作系统真正腾飞，是在计算机从大型机迈向**小型机(minicomputer)** 的时代。Digital Equipment 的 PDP 系列等经典机器让计算机价格大幅降低；过去，一个大型组织才拥有一台大型机，如今，组织中的一个小团队也有望拥有自己的计算机。不出所料，成本下降带来的主要影响之一，是开发者活动迅速增加：更多聪明人接触到计算机，于是计算机系统开始做更多有趣而漂亮的事情。

尤其是，为了更充分地利用机器资源，**多道程序设计(multiprogramming)** 变得普遍。操作系统不再一次只运行一个作业，而是把多个作业载入内存，并在它们之间快速切换，从而提高 CPU 利用率。由于 I/O 设备很慢，这种切换格外重要：程序等待 I/O 服务时还占着 CPU，只会浪费 CPU 时间。何不切换到另一个作业，让它先跑一阵？

在 I/O 和中断存在的情况下支持多道程序设计与任务重叠，迫使操作系统在多个概念方向上创新。内存保护等问题变得重要——我们当然不希望一个程序能访问另一个程序的内存。理解如何处理多道程序设计引入的并发问题也至关重要；即便存在中断，也要保证操作系统行为正确，这是一项巨大的挑战。本书稍后会研究这些问题及相关主题。

当时一项重大的实践进展，是 **UNIX** 操作系统问世。这主要归功于贝尔实验室（没错，就是那家电话公司的实验室）的 Ken Thompson（以及 Dennis Ritchie）。UNIX 从不同操作系统中吸收了许多好想法——尤其是 Multics [O72]，以及 TENEX [B+72]、Berkeley 分时系统 [S68] 等——但把它们做得更简单、更易用。很快，这个团队开始把装有 UNIX 源代码的磁带寄给世界各地的人；许多收到代码的人参与进来，亲手扩展系统。详情见下面的边栏[^10]。

!!! note "边栏：UNIX 的重要性"
    UNIX 在操作系统史上的重要性怎么强调都不为过。UNIX 受到早期系统（尤其是 MIT 著名的 Multics 系统）的影响，把许多伟大思想汇聚到一起，做成了一个既简单又强大的系统。

    最初的「贝尔实验室版」UNIX 背后有一条统一原则：构建小巧而强大的程序，再把它们连接起来，组成更大的工作流。用户输入命令的 shell 提供了管道等原语，从而支持这种元层次的编程，让程序可以轻松串联起来完成更大的任务。例如，要找出文本文件中包含单词 `foo` 的行，再统计一共有多少行，可以输入 `grep foo file.txt | wc -l`，把 `grep` 和 `wc`（字数统计）程序组合起来完成任务。

    UNIX 环境对程序员和开发者都很友好，还为新生的 C 编程语言提供了编译器。它让程序员很容易编写和分享自己的程序，因此大受欢迎。作者把副本免费送给任何索取的人——这是一种早期的开源软件形式——大概也帮了很大的忙。

    代码易于获得和阅读，同样至关重要。一个用 C 编写、漂亮而小巧的内核，吸引其他人摆弄它，不断加入新奇功能。例如，Bill Joy 领导的 Berkeley 团队制作了一个出色的发行版——**Berkeley Systems Distribution(BSD)**，其中包含先进的虚拟内存、文件系统和网络子系统。Joy 后来参与创办了 Sun Microsystems。

    遗憾的是，随着公司试图主张所有权并从 UNIX 中获利，它的传播稍稍慢了下来——律师介入后，这是一种令人遗憾（却很常见）的结果。许多公司都有自己的变体：Sun Microsystems 的 SunOS、IBM 的 AIX、HP 的 HPUX（又叫「H-Pucks」），以及 SGI 的 IRIX。AT&T/贝尔实验室与其他参与者之间的法律争斗，在 UNIX 上空投下阴影；尤其是在 Windows 问世并占据大部分 PC 市场以后，许多人都怀疑 UNIX 能否生存下去……

### 现代

小型机之后，又出现了一种更便宜、更快、面向大众的新机器：个人计算机，也就是今天所说的 PC。在 Apple 的早期机器（如 Apple II）和 IBM PC 带领下，这类新机器很快成为计算领域的主导力量。它们成本低廉，于是每张办公桌都能拥有一台机器，而不必让整个工作组共享一台小型机。

遗憾的是，对操作系统而言，PC 最初代表着一次大倒退：早期系统忘记了（或者压根儿不知道）小型机时代总结的教训。例如，DOS（微软的磁盘操作系统）等早期操作系统认为内存保护并不重要；于是，恶意的（或者只是写得很差的）应用程序可以在内存里四处乱写。第一代 Mac OS（第 9 版及以前）采用协作式作业调度；因此，一个意外卡在死循环里的线程就能霸占整个系统，逼得用户重启。那一代系统缺失的重要操作系统功能还有一长串，长得没法在这里完整讨论。

幸好，在忍受多年折磨后，小型机操作系统的老功能开始走上桌面。例如，Mac OS X/macOS 的核心是 UNIX，具备成熟系统应有的全部功能。Windows 也吸收了计算机历史上的许多伟大思想，尤其是从 Windows NT 开始，微软的操作系统技术迈出了一大步。就连今天的手机，也运行着更像 20 世纪 70 年代小型机系统、而不是 80 年代 PC 系统的操作系统（例如 Linux）——谢天谢地。看到操作系统发展黄金时期诞生的好想法进入现代世界，实在令人欣慰。更妙的是，这些想法还在继续发展，为现代系统增添功能，让用户和应用的体验越来越好。

!!! note "边栏：然后 Linux 来了"
    UNIX 很幸运：一位名叫 Linus Torvalds 的芬兰年轻黑客决定编写自己的 UNIX 版本。它大量借鉴原系统背后的原则和思想，却没有借用其代码库，因此避开了法律问题。Torvalds 邀请世界各地的许多人帮忙，并充分利用已经存在的成熟 GNU 工具 [G85]；不久，Linux（以及现代开源软件运动）诞生了。

    互联网时代到来后，大多数公司（如 Google、Amazon、Facebook 等）都选择运行 Linux，因为它免费，而且很容易按自身需求修改。事实上，如果没有这样的系统，很难想象这些新公司能取得如此成功。智能手机成为主流的用户平台后，出于许多同样的理由，Linux 也通过 Android 在那里站稳了脚跟。Steve Jobs 则把基于 UNIX 的 NeXTStep 操作环境带去了 Apple，让 UNIX 在桌面上流行起来（尽管许多 Apple 技术的用户可能根本不知道这件事）。于是，UNIX 延续至今，而且比以往任何时候都更重要。如果你相信世上有计算之神，就该为这个美妙的结果感谢他们。

## 2.7 小结

至此，我们初步认识了操作系统。现代操作系统让系统相对容易使用，而你今天使用的几乎每一种操作系统，都受到本书将要讨论的那些历史进展的影响。

遗憾的是，时间有限，本书不会涉及操作系统的所有组成部分。例如，操作系统中有大量网络代码；想深入了解，请去上网络课程。图形设备同样格外重要；可以通过图形学课程扩展这方面的知识。最后，有些操作系统教材会大谈安全；本书会讨论操作系统如何保护运行中的程序彼此不受伤害，以及如何让用户保护自己的文件，但不会深入安全课程中那些更深层的问题。

不过，本书仍会覆盖许多重要主题，包括 CPU 与内存虚拟化的基础、并发，以及通过设备和文件系统实现的持久化。别担心！虽说要走的路很长，但大部分内容都相当酷；走到终点时，你会以全新的眼光欣赏计算机系统真正的工作方式。

现在，干活吧！

## 作业

本书大多数章节（最终会是全部章节）末尾都有作业。完成这些作业很重要，因为每一份作业都能让你对本章介绍的概念获得更多实际经验。

作业分为两类。第一类基于**模拟(simulation)**。计算机系统模拟器只是一个简单程序：它假装完成真实系统中某些有趣的工作，再报告一些输出指标，展示系统的行为。例如，硬盘模拟器可以接收一系列请求，模拟具有特定性能特征的硬盘要花多久处理它们，然后报告这些请求的平均延迟。

模拟的妙处在于，不必面对运行真实系统的困难，就能轻松探索系统行为。事实上，它甚至让你可以创造现实世界中不存在的系统（比如性能快得不可思议的硬盘），从而观察未来技术可能带来的影响。

当然，模拟也有缺点。从本质上说，模拟只是对真实系统行为的近似。如果遗漏了真实行为的某个重要方面，模拟就会给出糟糕的结果。因此，对模拟结果始终应该抱有一点怀疑。归根结底，真正重要的是系统在现实世界中的表现。

第二类作业要求你与真实代码打交道。有些作业侧重测量，另一些则要求进行小规模开发与实验。两者都只是带你初探那个更广阔的世界：如何在基于 UNIX 的系统上用 C 编写系统代码。要真正把你推向这个方向，还需要规模超出这些作业的项目。因此，除了完成作业，我们强烈建议你再做一些项目来巩固系统编程能力；项目见 [`ostep-projects`](https://github.com/remzi-arpacidusseau/ostep-projects)。

要完成这些作业，你很可能需要一台基于 UNIX 的机器，运行 Linux、macOS 或类似系统。机器上还应该装有 C 编译器（例如 `gcc`）和 Python；你也应该知道如何使用某种真正的代码编辑器来编辑代码。
