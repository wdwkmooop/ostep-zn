# 附录 B 虚拟机监控器

> 英文原题：*Virtual Machine Monitors*

## B.1 引言

许多年前，IBM 向大型组织出售昂贵的大型机，由此冒出一个问题：如果一个组织想同时在机器上运行不同操作系统，该怎么办？有些应用为一种操作系统开发，另一些又依赖别的系统，麻烦就这样来了。

IBM 的解决办法是再加一层间接性：**虚拟机监控器(virtual machine monitor, VMM)**，也叫**管理程序(hypervisor)** [G74]。监控器位于一个或多个操作系统与硬件之间，让每个运行中的操作系统都以为机器归自己控制。幕后真正掌控硬件的却是监控器，它把多个操作系统复用到机器的物理资源上。

VMM 实际上是“操作系统的操作系统”，但层次低得多；上面的操作系统仍必须相信自己正在与真实物理硬件打交道。因此，**透明性(transparency)**是 VMM 的主要目标。

局面颇为有趣：此前，操作系统一直扮演幻术大师，哄着毫无戒心的应用相信自己独占 CPU 和巨大虚拟内存，暗中却在应用间来回切换、共享内存。现在同一套把戏要再演一次，只不过舞台搬到了操作系统下面，而操作系统早已习惯当老大。VMM 怎样为每个操作系统制造这种幻觉？

!!! danger "问题核心：怎样虚拟化操作系统下面的机器"
    虚拟机监控器必须透明地虚拟化操作系统下面的机器。为此需要哪些技术？

## B.2 动机：为什么需要 VMM？

如今 VMM 再次流行，原因很多。

第一是**服务器整合(server consolidation)**。很多环境把服务分散到运行不同操作系统甚至不同版本的多台机器，每台机器利用率却很低。虚拟化让管理员把多个操作系统整合到较少的硬件平台上，降低成本，也简化管理。

第二是桌面功能。许多用户主要使用一个操作系统，例如 Linux 或 macOS，却仍需要另一个平台（例如 Windows）上的原生应用。虚拟化可以两全其美。

第三是测试与调试。开发者通常在一个主平台上写代码，却要在软件部署到的各种平台上调试测试。虚拟化让一台机器同时运行许多操作系统类型和版本，省心得多。

这场虚拟化复兴在 20 世纪 90 年代中后期真正起步，由斯坦福大学 Mendel Rosenblum 教授带领的研究组推动。该组为 MIPS 处理器开发的 VMM Disco [B+97] 是早期复兴工作，后来还促成 VMware [V98] 的创立；VMware 如今已成为虚拟化技术市场的领导者。本附录以 Disco 的核心技术为窗口，理解虚拟化怎样工作。

## B.3 虚拟化 CPU

要在 VMM 上运行一台虚拟机（一个操作系统及其应用），基本技术仍是前文操作系统虚拟化 CPU 时见过的**受限制的直接执行(limited direct execution)**。想在 VMM 上“启动”新操作系统，只需跳到它的第一条指令，让它开始运行。就是这么简单——嗯，几乎。

假设机器只有一个处理器，要在两台虚拟机，也就是两套操作系统及各自应用之间复用。就像操作系统用上下文切换在进程间切换，VMM 要在虚拟机之间执行**机器切换(machine switch)**：保存一套操作系统的完整机器状态，包括寄存器、PC，以及普通上下文切换不需保存的特权硬件状态；恢复下一台虚拟机的状态；最后跳到它的 PC。这个 PC 可能位于操作系统内部（当时正在执行系统调用），也可能位于该系统上的用户进程。

### 截获特权操作

当应用或操作系统尝试执行特权操作时，事情开始棘手。例如，在软件管理 TLB 的系统上，操作系统会用特权指令把地址转换写进 TLB，再重新执行触发 TLB 未命中的指令。虚拟化环境不能允许操作系统直接执行特权指令，否则控制机器的就不再是下面的 VMM。VMM 必须截获这些尝试，保住控制权。

以系统调用为例。进程可能调用 `open()`、`read()` 或 `fork()`。没有虚拟化时，系统调用通过特殊指令进入内核：MIPS 使用 trap，x86 使用参数为 `0x80` 的 `int` 指令。FreeBSD 的 `open()` 库调用大致如下 [B00]：

```asm
open:
    push dword mode
    push dword flags
    push dword path
    mov  eax, 5
    push eax
    int  80h
```

UNIX 系统中，`open()` 的三个参数是 `int open(char *path, int flags, mode_t mode)`。代码先把 `mode`、`flags`、`path` 压栈，再放入数字 5，最后执行 `int 80h` 转移到内核。数字 5 是 FreeBSD 用户程序与内核预先约定的 `open()` 系统调用号；其他系统调用会在同一位置放入不同编号。

> 为了让事情更混乱，Intel 把几乎任何理智的人都会称作 trap 的指令叫作“interrupt”。Patterson 评价 Intel 指令集：“这是一套只有亲妈才会爱的 ISA。”不过说真的，我们多少也挺喜欢它，而我们不是它妈。

trap 指令首先把 PC 改到操作系统预先向硬件注册的 trap 处理程序，同时把处理器从用户模式切到内核模式。用户模式不能执行特权操作，违规会再次 trap，通常还会把肇事进程干掉；内核模式则拥有机器的全部权力。

| 步骤 | 进程 | 硬件 | 操作系统 |
|---:|---|---|---|
| 1 | 执行加法、加载等普通指令 | — | — |
| 2 | 发起系统调用，trap 到 OS | — | — |
| 3 | — | 切入内核模式，跳到 trap 处理程序 | — |
| 4 | — | — | 在内核模式处理系统调用，执行返回 trap |
| 5 | — | 切回用户模式，返回用户代码 | — |
| 6 | 从 trap 后的 PC 恢复执行 | — | — |

*表 B.1：执行系统调用。*

有虚拟化时，应用仍执行同一条 trap 指令，参数仍放在栈或寄存器里；但机器真正归 VMM 控制，内核模式下最先运行的是 VMM 安装的处理程序。

VMM 本身并不知道怎样完成每套操作系统的每个调用，却知道该操作系统的 trap 处理程序在哪里。操作系统启动时曾尝试安装处理程序；安装是特权操作，因此陷入 VMM，VMM 当时就把地址记了下来。

收到某操作系统用户进程的 trap 后，VMM 跳到该系统的处理程序，让它照常处理。操作系统完成后执行返回 trap 的特权指令（MIPS 的 `rett`、x86 的 `iret`），再次陷入 VMM；VMM 识别其意图，执行真正的返回，切回用户模式。

| 无虚拟化的系统调用 | 动作 |
|---:|---|
| 1 | 进程发起系统调用，trap 到操作系统 |
| 2 | OS 解码 trap，执行系统调用例程，完成后从 trap 返回 |
| 3 | 进程从 trap 后的 PC 恢复执行 |

*表 B.2：没有虚拟化时的系统调用流程。*

| 有虚拟化的系统调用 | 动作 |
|---:|---|
| 1 | 进程发起系统调用 |
| 2 | VMM 捕获 trap，以降低后的特权级调用 OS 处理程序 |
| 3 | OS 解码并执行系统调用，然后尝试返回 trap |
| 4 | VMM 截获返回请求，执行真正的返回 trap |
| 5 | 进程恢复执行 |

*表 B.3：有虚拟化时的系统调用流程。*

虚拟化显然增加了许多跳转，可能拖慢系统调用、损害性能。

还剩一个问题：操作系统应该运行在哪种模式？不能是内核模式，否则它可无限制访问硬件；但它又必须比用户应用更有权力，能访问自己的数据结构并阻止用户进程访问。

Disco 利用 MIPS 的**监督者模式(supervisor mode)**漂亮地解决了问题。该模式不能执行特权指令，却比用户模式能访问更多内存，足够存放 OS 数据结构。没有这种模式的硬件只能让 OS 跑在用户模式，再用页表与 TLB 保护其数据：进入 OS 时开放内核数据结构的映射，返回应用时撤销读写权限。

## B.4 虚拟化内存

CPU 的思路已经清楚：VMM 像操作系统一样调度虚拟机，在特权级变化时插手。可内存怎么办？

操作系统通常把物理内存看成线性页面数组，把页面分配给自身或用户进程；同时它已经为每个进程虚拟化内存，让进程以为自己拥有私有地址空间。现在还要透明地再加一层，让多个操作系统共享机器真正的物理内存。

于是操作系统眼里的“物理内存”也成了虚拟物；VMM 把真实物理内存称为**机器内存(machine memory)**。地址转换增加一层间接性：OS 的每进程页表把虚拟地址映射到“物理”地址，VMM 的每操作系统页表再把物理页框映射到底层机器页框。

```text
OS 页表                    VMM 页表
VPN 0 -> PFN 10            PFN 03 -> MFN 06
VPN 2 -> PFN 03            PFN 08 -> MFN 10
VPN 3 -> PFN 08            PFN 10 -> MFN 05

虚拟地址空间          “物理内存”           机器内存
页 0  ----------------> PFN 10 -----------> MFN 5
页 2  ----------------> PFN 3  -----------> MFN 6
页 3  ----------------> PFN 8  -----------> MFN 10
```

*图 B.1：VMM 内存虚拟化。*

图中只有一个含 4 页的虚拟地址空间，其中 0、2、3 有效。OS 把它们映射到物理页框 10、3、8；下面的 VMM 又把 PFN 3、8、10 映射到机器页框 6、10、5。真实系统会有 $V$ 个操作系统及 $V$ 张 VMM 页表；每个 $OS_i$ 上还有几十乃至几百个进程 $P_i$，因而又有 $P_i$ 张每进程页表。

### 软件管理 TLB 下的流程

回忆 32 位地址空间、4 KB 页面：虚拟地址由 20 位虚拟页号 VPN 和 12 位偏移组成。OS 借助硬件 TLB 把 VPN 转换成物理页框号 PFN。常见情况由 TLB 直接完成；未命中时，软件管理 TLB 的操作系统介入。

| 无虚拟化的 TLB 未命中 | 动作 |
|---:|---|
| 1 | 进程从内存加载，TLB 未命中并 trap |
| 2 | OS 处理程序从虚拟地址提取 VPN，查页表；若存在且有效，取得 PFN 并更新 TLB，然后返回 |
| 3 | 进程重试原指令，这次 TLB 命中 |

*表 B.4：没有虚拟化时的 TLB 未命中流程。*

有 VMM 后，TLB 未命中首先进入真正拥有特权的 VMM，而非 OS。VMM 通常不知道 OS 页表语义，于是跳入 OS 的 TLB 未命中处理程序。OS 查到 VPN 对应 PFN，并尝试更新 TLB；更新属于特权操作，又陷回 VMM。此时 VMM 施展把戏：不安装 OS 想要的 VPN→PFN，而安装自己需要的 VPN→MFN。随后层层返回用户代码，重试指令并命中 TLB，从真正的机器页框取数据。

| 有虚拟化的 TLB 未命中 | 动作 |
|---:|---|
| 1 | 进程访问内存，TLB 未命中并 trap |
| 2 | VMM 处理程序以降低后的特权级调用 OS 的 TLB 处理程序 |
| 3 | OS 提取 VPN、查页表，取得 PFN，并尝试更新 TLB |
| 4 | VMM 截获这次特权更新，将 VPN→PFN 改成 VPN→MFN 写入 TLB，再返回 OS |
| 5 | OS 尝试从 trap 返回 |
| 6 | VMM 再次截获，执行真正的返回 trap |
| 7 | 进程重试指令，TLB 命中 |

*表 B.5：有虚拟化时的 TLB 未命中流程。*

这也说明 VMM 怎样管理每个 OS 的“物理内存”：像 OS 为每个进程保存页表一样，VMM 为每台虚拟机追踪物理页到机器页的映射。处理 TLB 未命中时要查询这些表，甚至判断某“物理”页当前是否在机器内存中——VMM 也可能把它换到磁盘。

!!! note "边栏：管理程序与硬件管理的 TLB"
    硬件管理 TLB 的系统在未命中时由硬件遍历页表，VMM 没机会每次跳出来偷换转换。它必须密切监视 OS 对页表的修改，并维护一张**影子页表(shadow page table)**，直接把进程虚拟地址映射到 VMM 想要的机器页 [AA06]。

    OS 尝试安装自己的页表时，VMM 改为安装对应影子页表。硬件随后照常工作，用影子表把虚拟地址翻译成机器地址，OS 全程浑然不觉。

虚拟化让 TLB 未命中贵了不少。Disco 因而增加 VMM 级“软件 TLB”：记录每个 OS 试图安装的虚拟到物理映射及其对应的虚拟到机器映射。再次未命中时，VMM 先查软件 TLB；若找到，便直接把 VPN→MFN 装入硬件 TLB，跳过上述来回折腾 [B+97]。

## B.5 信息鸿沟

就像操作系统不知道应用真正想做什么，只能制定希望对大家都好用的通用策略，VMM 也不了解上层操作系统的意图。这种知识缺失称为 VMM 与 OS 之间的**信息鸿沟(information gap)**，会造成低效 [B+97]。

例如 OS 无事可做时，可能进入空闲自旋，等待下一次中断：

```c
while (1)
    ; // 空闲循环
```

若 OS 独占整台机器，这很合理。但 VMM 同时运行两个 OS，一个空转，另一个有用户进程认真干活；若 VMM 知道前者空闲，就能把更多 CPU 时间给后者。

另一个例子是页面的按需清零。多数 OS 把物理页框映射给进程前会清零，防止前一个进程的敏感数据泄漏给后一个进程。VMM 出于同样原因，也会在把页面交给 OS 前清零。结果一个页面经常被清两次：VMM 清一次，OS 再清一次。Disco 作者没有神奇解法，只好修改 IRIX，让它别再清理由底层 VMM 已经清过的页面 [B+97]。

类似问题还有很多。一种方案是让 VMM 通过**推断(inference)**，也就是隐式信息，跨越鸿沟；例如观察 OS 进入低功耗模式，推断它正处于空闲循环。另一种是修改 OS，明确告诉 VMM 自己在做什么；这就是半虚拟化的路线。显式方案部署较难，却很有效。

!!! note "边栏：半虚拟化"
    很多时候必须假设不能修改 OS，例如 VMM 上跑的是不太友好的竞争对手系统。但若允许修改，OS 可以更高效地运行在 VMM 上，就像避免重复清零那样。

    这种为 VMM 修改操作系统的方式称为**半虚拟化(para-virtualization)** [WSG02]：VMM 提供的不是完整虚拟化，而是需要 OS 配合的部分虚拟化。研究表明，只做恰到好处的修改，半虚拟化系统可以接近没有 VMM 的效率 [BD+03]。

## B.6 总结

虚拟化正在复兴。出于服务器整合、兼容、测试等原因，用户和管理员希望在一台机器上同时运行多个操作系统。VMM 通常透明地提供服务，上层 OS 几乎不知道硬件其实不归自己控制。

核心机制是扩展受限制的直接执行：让硬件允许 VMM 截获 trap 等关键事件，VMM 便能完全控制机器资源分配，同时维持 OS 所需的幻觉。

VMM 对操作系统所做的事情，与 OS 对进程所做的事情颇为相似：两者都虚拟化硬件。但存在关键差别。OS 虚拟化会提供新的抽象和友好接口；VMM 的抽象却必须与原硬件相同——所以谈不上友好。VMM 的目标不是让硬件更容易使用，而是把硬件原样复制成幻觉。

还有许多主题尚未讨论。例如虚拟平台上的 I/O 有自己的新问题；VMM 也可在所谓**宿主式(hosted)**配置中“依附”现有 OS 运行 [SVL01]；多个 OS 一起用掉过多内存时又该怎么办，都值得继续研究。

硬件支持也改变了虚拟化。Intel、AMD 等公司如今直接支持额外虚拟化层，使本附录许多纯软件技巧不再必要。也许作者会在某篇尚未写出的章节里详谈——经典的“未来工作”，永远不会迟到。

!!! tip "使用隐式信息"
    分层系统的接口难以改变，但一层又需要了解另一层时，隐式信息非常强大。例如块设备想知道上层文件系统如何使用它，应用想知道哪些页面位于文件系统页缓存，可操作系统没有相应 API。

    研究者已经设计出推断技术，无需显式跨层接口也能取得这些信息 [AD+01, S+03]。VMM 尤其适合这样做：它想了解上面的 OS，却不愿要求两层之间新增专用 API。

- **[SVL01]** Jeremy Sugerman, Ganesh Venkitachalam, Beng-Hong Lim, “Virtualizing I/O Devices on VMware Workstation’s Hosted Virtual Machine Monitor,” *USENIX ’01*. 介绍 VMware 宿主式架构怎样利用原生 OS 功能完成 I/O，避免在 VMM 中重新实现。
- **[V98]** VMware Corporation, 1998. 也许是本书最没用的参考资料，毕竟你显然可以自己查到。总之，该公司创立于 1998 年，是虚拟化领域的领导者。
- **[S+03]** Muthian Sivathanu et al., “Semantically-Smart Disk Systems,” *FAST ’03*. 作者团队展示“愚笨”的块设备怎样推断上层文件系统正在删除文件等行为，进而提供安全删除或更可靠存储等新功能。
- **[WSG02]** Andrew Whitaker, Marianne Shaw, Steven D. Gribble, “Scale and Performance in the Denali Isolation Kernel,” *OSDI ’02*. 提出“半虚拟化”一词。Disco 或许已经引入思想，但 Denali 把它推进得更远、更一般化。
