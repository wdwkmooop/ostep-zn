# 第 50 章 Andrew 文件系统（AFS）

> 英文原题：*The Andrew File System (AFS)*

Andrew 文件系统由卡内基—梅隆大学（CMU）在 20 世纪 80 年代引入 [H+88]，项目由著名的 M. Satyanarayanan 教授（简称 Satya）领导。它的主要目标很简单：**可扩展性(scale)**。具体说，怎样设计分布式文件系统，让一台服务器支持尽可能多的客户端？

设计与实现的许多方面都会影响扩展性，其中最重要的是客户端与服务器之间的协议。NFS 要求客户端定期询问服务器缓存内容是否变化；每次检查都消耗服务器 CPU 与网络带宽，所以频繁检查会限制一台服务器能服务的客户端数量。

AFS 与 NFS 还有一个差别：它从一开始就把合理的用户可见行为当成头等大事。NFS 的缓存一致性很难说清，因为它直接取决于客户端缓存超时等底层实现细节；AFS 的一致性则简单易懂：客户端打开文件时，通常会从服务器得到最新的一致副本。

## 50.1 AFS 第 1 版

本章讨论 AFS 的两个版本 [H+88, S+85]。第一版在这里称作 AFSv1，实际原名为 ITC 分布式文件系统 [S+85]。它已有基本设计，但未达到扩展目标，于是团队重新设计出最终协议 AFSv2，后文简称 AFS [H+88]。

> 当时校名写作“Carnegie-Mellon University”，后来 CMU 去掉了连字符，才有今天的“Carnegie Mellon University”。AFS 源于 20 世纪 80 年代初的工作，所以原书保留全连字符写法。若你偏爱这种无聊到令人肃然起敬的琐事，可以继续深挖校名史。

AFSv1 的主要协议消息如下：

| 消息 | 作用 |
|---|---|
| `TestAuth` | 检查文件是否变化，用于验证缓存项 |
| `GetFileStat` | 取得文件的 `stat` 信息 |
| `Fetch` | 获取整个文件内容 |
| `Store` | 把整个文件存到服务器 |
| `SetFileStat` | 设置文件的 `stat` 信息 |
| `ListDir` | 列出目录内容 |

*图 50.1：AFSv1 协议要点。*

所有 AFS 版本的基本原则之一，都是在访问文件的客户端**本地磁盘上缓存整个文件(whole-file caching)**。调用 `open()` 时，若文件存在，就从服务器获取整个文件并写入本地磁盘；之后应用的 `read()` 与 `write()` 被重定向到本地文件系统，不需要网络通信，因此很快；`close()` 时，若文件已修改，再把整个文件刷回服务器。

这与 NFS 对比鲜明：NFS 缓存块而非整个文件，并把它们放在客户端内存而非本地磁盘。当然，NFS 也可能碰巧缓存一个文件的全部块，但协议粒度仍是块。

详细一点：客户端首次 `open()` 时，AFS 客户端代码 **Venus** 向服务器发送 `Fetch`，其中携带完整路径，如 `/home/remzi/notes.txt`。文件服务器群称为 **Vice**；它遍历路径，找到文件，将整个文件发给客户端。Venus 把文件写入本地磁盘缓存。后续读写都是本地操作；本地文件系统还可能把访问过的块缓存在客户端内存中。因此 AFS 同时利用本地磁盘和内存缓存。关闭时，若文件被修改，客户端用 `Store` 将整个文件及路径发回服务器永久保存。

下次访问会高效得多。客户端先用 `TestAuth` 问服务器文件是否变化；若没有，就直接使用本地磁盘副本，省去网络传输。早期协议只缓存文件内容，目录仍只留在服务器。

## 50.2 第 1 版的问题

!!! tip "先测量，再构建（Patterson 定律）"
    作者们的导师 David Patterson（因 RISC 与 RAID 闻名）总是鼓励大家：先测量系统、证明问题存在，再造新系统解决它。实验数据能把系统构建变得更科学，也迫使你在改进版完成之前就想清楚如何测量。

    这样最终会得到两项好处：第一，有证据表明你解决的是真问题；第二，已有方法证明新系统确实超越现状。这便是 Patterson 定律。

AFS 团队花大量时间测量原型，找到两个主要问题：

- **路径遍历成本太高。** `Fetch` 或 `Store` 携带完整路径，例如 `/home/remzi/notes.txt`。服务器必须从根目录起逐级查找 `home`、`remzi`，最后才到文件。大量客户端并发时，服务器许多 CPU 时间都耗在目录树里徒步旅行。
- **客户端发出太多 `TestAuth`。** 就像 NFS 的 `GETATTR` 泛滥，AFSv1 不断询问本地文件或其属性是否仍有效。服务器忙着告诉客户端“缓存还能用”，而绝大多数时候文件根本没变。

还有两个问题：服务器负载不均，以及每个客户端对应一个独立服务器进程，造成上下文切换等开销。团队引入可在服务器间迁移的**卷(volume)**来平衡负载，并在 AFSv2 中用线程而非进程构建服务器。受篇幅所限，本章主要关注限制扩展性的前两个协议问题。

## 50.3 改进协议

上述问题让服务器 CPU 成为瓶颈，一台服务器过载前只能服务约 20 个客户端：`TestAuth` 太多，`Fetch`/`Store` 又把时间耗在路径遍历。

!!! danger "问题核心：怎样设计可扩展的文件协议"
    怎样重新设计协议，尽量减少服务器交互，特别是 `TestAuth`？又怎样让不可避免的交互更高效？同时解决两点，才能得到扩展性高得多的 AFS。

## 50.4 AFS 第 2 版

AFSv2 引入**回调(callback)**来减少客户端/服务器交互。回调是服务器给客户端的承诺：若客户端缓存的文件被修改，服务器会通知它。加入这份状态后，客户端不必主动询问缓存是否有效；在服务器通知前，它都假定文件有效。这恰似轮询与中断的区别。

AFSv2 还用**文件标识符(file identifier, FID)**代替路径名指定目标文件，类似 NFS 文件句柄。FID 由卷标识符、文件标识符和一个**唯一化值(uniquifier)**组成；文件删除后卷 ID 与文件 ID 可以重用，唯一化值则防止旧标识误中招。

客户端不再把完整路径扔给服务器遍历，而是自己逐段遍历并缓存结果，从而减轻服务器负载。

例如访问 `/home/remzi/notes.txt`，假设本地根目录为 `/`，AFS 的 `home` 挂载在其下：客户端先 `Fetch` 目录 `home` 的内容，写入本地磁盘缓存并建立回调；再取 `remzi` 目录并建立回调；最后取 `notes.txt`、缓存并建立回调，才把文件描述符返回应用。

| 客户端 C1 | 服务器 |
|---|---|
| `open("/home/remzi/notes.txt", ...)`；发送 `Fetch(home_FID, "remzi")` | 在 `home` 中找 `remzi`，建立 `callback(C1)`，返回目录内容与 FID |
| 把 `remzi` 写入本地磁盘，记录回调；发送 `Fetch(remzi_FID, "notes.txt")` | 在目录中找 `notes.txt`，建立回调，返回文件内容与 FID |
| 缓存 `notes.txt`，记录回调；本地 `open()` 并向应用返回描述符 | — |
| `read()`：读取本地缓存副本 | — |
| `close()`：本地关闭；若文件变化，则刷回服务器 | 接收需要存储的新版本 |
| 再次 `open()`：逐目录检查回调；仍为 `VALID` 就用本地副本，否则重新 `Fetch` | 仅在回调失效时参与 |

*图 50.2：读取文件时客户端与文件服务器的动作。*

关键区别是：每次获取目录或文件时，AFS 客户端都会在服务器建立回调，确保缓存状态变化时收到通知。第一次访问路径会产生许多消息，但同时为全部目录及文件建立回调；后续访问完全在本地，无需服务器交互。在文件已缓存的常见情况下，AFS 几乎与本地磁盘文件系统一样。

!!! note "边栏：缓存一致性不是万能药"
    分布式文件系统的缓存一致性经常被郑重讨论，但基础一致性并不能解决多客户端访问的一切问题。比如构建代码仓库，多个客户端签入、签出代码，不能只靠底层文件系统；还要用显式的文件级锁，保证并发访问产生“正确”结果。

    真正在意并发更新的应用都会额外处理冲突。本章与上一章的一致性主要适合日常使用：用户换一台客户端登录时，希望看到一个合理版本。若指望协议包办更多，便是在为失败、失望和泪流满面提前订座。

## 50.5 缓存一致性

NFS 中有两个一致性问题：**更新可见性**——服务器何时得到新版本；**缓存陈旧性**——服务器已有新版本后，客户端还会看旧缓存多久。

AFS 依靠回调与整文件缓存，规则简单得多。需要分别考虑不同机器上的进程，以及同一机器上的进程。

对不同机器，AFS 在同一时刻让更新对服务器可见，并让其他缓存副本失效：**更新文件被关闭时**。客户端打开文件并反复写入；关闭时把新文件刷给服务器。服务器随即“打破”所有缓存该文件的客户端回调，也就是联系它们，告知回调不再有效。之后这些客户端再次打开文件，必须从服务器重新获取新版本，同时建立新回调。

同一机器上的进程是例外。一个进程的写入会立即对本机其他进程可见，无需等到关闭。这符合典型 UNIX 语义，让单机使用完全如人所料；只有换到另一台机器才看得出 AFS 的一般一致性机制。

还有一个值得讨论的跨机器情况：不同机器同时修改同一文件。AFS 采用**最后写者胜(last writer wins)**，更准确地说是**最后关闭者胜(last closer wins)**。最后调用 `close()` 的客户端最后更新整个服务器文件，因此它的完整版本留下来。

这与块协议 NFS 不同：NFS 的客户端可逐块把写入送给服务器，最终文件可能混合双方更新。若两个客户端分块修改 JPEG，混出来的东西大概率既不是艺术，也不是合法 JPEG。

下面的时间线概括这些情形。`A`、`B`、`C`、`D` 表示文件 F 的完整内容，“失效”表示回调被打破：

| 操作 | 客户端 1 缓存 | 客户端 2 缓存 | 服务器 | 说明 |
|---|---|---|---|---|
| P1 `open(F); write(A)` | A | — | — | 创建文件，尚未关闭 |
| P1 `close()` | A | — | A | A 对远端可见 |
| 本机 P2 `open/read` | A | — | A | 本地进程立即看见 A |
| P1 `open; write(B)`，P2 同时读 | B | — | A | 本地 P2 立即读到 B；远端仍看 A |
| P3 在客户端 2 `open/read/close` | B | A | A | 远端尚看不到 B |
| P1 `close()` | B | 失效 | B | 服务器收到 B，并打破 P3 的回调 |
| P3 再次 `open/read/close` | B | B | B | 重新获取后读到 B |
| P1 写 D；P3 写 C 并先关闭 | D | C | C | 服务器暂时为 C，客户端 1 回调失效 |
| P1 最后关闭 | D | 失效 | D | 最后关闭者胜；P3 下次读到 D |

*图 50.3：缓存一致性时间线。*

## 50.6 崩溃恢复

AFS 的崩溃恢复比 NFS 复杂——你的直觉没骗你。

假设服务器 S 暂时联系不上正在重启的客户端 C1。此时另一客户端 C2 更新文件 F，S 尝试通知所有缓存 F 的客户端撤销回调，但 C1 错过消息。C1 重新加入系统后，必须把全部缓存内容视为可疑。下次访问 F 时，先用 `TestAuth` 询问副本是否仍有效；有效才使用，否则获取新版。

服务器崩溃后恢复也更复杂。回调保存在内存，重启后服务器不知道哪些客户端缓存了哪些文件。因此每个客户端都必须意识到服务器崩过，并把缓存视为可疑，使用前重新确认。

服务器崩溃是件大事：必须及时让每个客户端知道，否则可能访问陈旧文件。实现办法很多，例如服务器恢复后逐一通知客户端“别信你的缓存！”，或客户端定期发送**心跳(heartbeat)**检查服务器是否仍活着。更可扩展、更合理的缓存模型不是免费的；NFS 客户端则几乎觉察不到服务器崩溃。

## 50.7 AFSv2 的扩展性与性能

采用新协议后，一台 AFSv2 服务器可支持约 50 个客户端，而非原来的 20 个。客户端性能也常接近本地系统：常见情况下访问全在本机，读请求命中本地磁盘缓存，甚至内存缓存；只有新建或修改文件时才需 `Store` 到服务器。

下面定性比较 AFS 与 NFS。小、中、大文件分别含 $N_s$、$N_m$、$N_L$ 个块；小和中文件能装入客户端内存，大文件能装入本地磁盘但装不进内存。远程访问一个块用时 $L_{net}$，本地内存为 $L_{mem}$，本地磁盘为 $L_{disk}$，通常 $L_{net}>L_{disk}>L_{mem}$。假设首次访问均不命中缓存，后续重读只要容量足够就命中。

| 工作负载 | NFS | AFS | AFS/NFS |
|---|---:|---:|---:|
| 1. 小文件，顺序读 | $N_sL_{net}$ | $N_sL_{net}$ | 1 |
| 2. 小文件，顺序重读 | $N_sL_{mem}$ | $N_sL_{mem}$ | 1 |
| 3. 中文件，顺序读 | $N_mL_{net}$ | $N_mL_{net}$ | 1 |
| 4. 中文件，顺序重读 | $N_mL_{mem}$ | $N_mL_{mem}$ | 1 |
| 5. 大文件，顺序读 | $N_LL_{net}$ | $N_LL_{net}$ | 1 |
| 6. 大文件，顺序重读 | $N_LL_{net}$ | $N_LL_{disk}$ | $L_{disk}/L_{net}$ |
| 7. 大文件，单次读一个块 | $L_{net}$ | $N_LL_{net}$ | $N_L$ |
| 8. 小文件，顺序写 | $N_sL_{net}$ | $N_sL_{net}$ | 1 |
| 9. 大文件，顺序写 | $N_LL_{net}$ | $N_LL_{net}$ | 1 |
| 10. 大文件，顺序覆盖 | $N_LL_{net}$ | $2N_LL_{net}$ | 2 |
| 11. 大文件，单次写一个块 | $L_{net}$ | $2N_LL_{net}$ | $2N_L$ |

*图 50.4：AFS 与 NFS 比较。*

可以得到几点观察。

第一，许多情况性能大致相同。首次读取任意大小文件时，耗时由从服务器取文件主导。AFS 还要把文件写到本地磁盘，看似更慢，但本地文件系统先把写入缓存在内存，成本通常被隐藏。读取本地缓存副本也往往命中客户端页缓存，因此与 NFS 相似。

第二，大文件顺序重读（工作负载 6）产生差异。AFS 可从本地磁盘缓存读取；NFS 只在客户端内存中缓存块，文件大于内存时必须从服务器重新获取。若远程访问确实慢于本地磁盘，AFS 快约 $L_{net}/L_{disk}$ 倍，而且 NFS 还会增加服务器负载、影响扩展性。

第三，新文件的顺序写（8、9）大致相同。AFS 先写本地缓存，关闭时再送服务器；NFS 在客户端内存中缓冲，可能因内存压力提前写部分块，但关闭时肯定刷到服务器。AFS 的本地磁盘写先进入页缓存、稍后才由后台落盘，也享受客户端操作系统的内存缓存。

第四，AFS 在大文件顺序覆盖（10）上较差。它先完整取回旧文件，随后又把它覆盖，白读了一遍；NFS 可直接按块覆盖，避开初次无用读取。

第五，只访问大文件中一小部分（7、11）时，NFS 远胜 AFS。AFS 在打开时取整个文件，即使只读或写一小块；若修改，还要把整个文件写回，冲击翻倍。NFS 的块协议只产生与实际读写大小成比例的 I/O。

这里假设 NFS 写入按块大小且块对齐，否则它也得先读块；还假设文件未以 `O_TRUNC` 打开，否则 AFS 不会先取即将被截断的旧内容。

总之，NFS 与 AFS 作出不同假设，得到不同性能结果。差异是否要紧，一如既往取决于工作负载。

!!! note "边栏：工作负载的重要性"
    评价系统的一大挑战是选择工作负载。计算机用途千差万别，存储设计者该依据哪些负载做决定？

    AFS 设计者根据测量经验假设：多数文件不常共享，而且会被完整、顺序访问。在这些假设下，AFS 设计非常合理。但它们不总成立。例如应用定期往大日志尾部追加少量数据，对 AFS 就很不友好；事务数据库中的随机更新也是难缠负载。

    可从已有研究了解常见工作负载，参阅 [B+91, H+11, R+00, V99] 以及 AFS 回顾 [H+88]。

## 50.8 AFS 的其他改进

就像 Berkeley FFS 借机加入符号链接等功能，AFS 团队也在造系统时增加了许多便于使用与管理的特性。

- AFS 为客户端提供真正的**全局命名空间(global namespace)**，所有客户端上的文件名都相同。NFS 允许客户端随意挂载服务器，只有靠约定和大量管理工作才能保持一致命名。
- AFS 严肃对待安全，包含用户认证机制，用户希望私有的文件可以真正保持私有。NFS 多年来的安全支持则相当原始。
- AFS 提供灵活的、由用户管理的**访问控制列表(access-control list, ACL)**，让用户细致决定谁能访问哪些文件；NFS 和多数 UNIX 文件系统在这种共享控制上弱得多。
- AFS 提供简化服务器管理的工具。在系统管理意识上，它领先同行好几个光年。

## 50.9 总结

AFS 展示了与 NFS 大不相同的分布式文件系统构建方式。它的协议设计尤其重要：整文件缓存与回调把服务器交互降到最低，让每台服务器支持更多客户端，也减少整个站点所需的服务器数量。统一命名空间、安全和 ACL 等功能让 AFS 很好用；它的一致性模型清楚易懂，不像 NFS 那样偶尔冒出难以解释的怪现象。

也许遗憾的是，AFS 很可能正在衰落。NFS 是开放标准，得到众多厂商支持；加上 Windows 系的分布式文件系统协议 CIFS，二者主导了市场。AFS 仍偶见于教育机构等场所（包括威斯康星），但长期影响更可能来自其思想，而非系统本身。事实上，NFSv4 已加入服务器状态，例如 `open` 协议消息，越来越像 AFS 的基本协议。

## 参考资料

- **[B+91]** Mary Baker et al., “Measurements of a Distributed File System,” *SOSP ’91*. 早期分布式文件系统工作负载测量，与 AFS 的许多直觉相符。
- **[H+11]** Tyler Harter et al., “A File is Not a File: Understanding the I/O Behavior of Apple Desktop Applications,” *SOSP ’11*. 作者团队研究 Apple 桌面工作负载的论文；事实证明，它们与系统研究界惯常关注的服务器负载颇有不同，也是一篇指向大量相关工作的较新参考。
- **[H+88]** John H. Howard et al., “Scale and Performance in a Distributed File System,” *ACM TOCS*, 6(1), 1988. 著名 AFS 系统的长篇期刊版本；它仍在世界多处使用，也可能是关于如何构建分布式文件系统最早的清晰思考。测量科学与原则性工程的绝妙结合。
- **[R+00]** Drew Roselli, Jacob R. Lorch, Thomas E. Anderson, “A Comparison of File System Workloads,” *USENIX ’00*. 比 Baker 论文更新的一组跟踪记录，并有一些有趣转折。
- **[S+85]** M. Satyanarayanan et al., “The ITC Distributed File System: Principles and Design,” *SOSP ’85*. 较早的分布式文件系统论文；AFS 的基础设计已经就位，但还没有扩展性改进。“Andrew”这个名字向 Andrew Carnegie 与 Andrew Mellon 致敬；两位富豪创立的机构最终合并，成为今天的 Carnegie Mellon University。
- **[V99]** Werner Vogels, “File system usage in Windows NT 4.0,” *SOSP ’99*. 一项很酷的 Windows 工作负载研究；它与此前许多基于 UNIX 的研究本来就不一样。

## 作业（模拟）

本节使用 `afs.py` 这个简单 AFS 模拟器巩固知识。更多细节见 `README`。

1. 运行一些简单案例，确认能预测客户端读到的值。改变随机种子 `-s`，预测中间值和文件最终值；再改变文件数 `-f`、客户端数 `-C`、读比例 `-r`（0 到 1）增加难度。也可用 `-n 2` 或更高生成更长、更有趣的跟踪。
2. 预测 AFS 服务器发起的每次回调。尝试不同随机种子，并使用高详细级别，如 `-d 3`；再用 `-c` 让程序给出答案。能准确猜出每次回调何时发生吗？触发它的精确条件是什么？
3. 同样改变随机种子，预测每一步的准确缓存状态。使用 `-c -d 7` 可观察缓存状态。
4. 构造特定工作负载：用 `-A oa1:w1:c1,oa1:r1:c1` 运行。随机调度下，客户端 1 读取文件 `a` 可能看到哪些值？尝试不同种子。两个客户端操作的全部调度交错中，有多少让客户端 1 读到 1，又有多少读到 0？
5. 构造特定调度。继续使用上述 `-A`，分别加 `-S 01`、`-S 100011`、`-S 011100`，以及你想到的其他调度。客户端 1 会读到什么？
6. 运行工作负载 `-A oa1:w1:c1,oa1:w1:c1` 并改变调度。`-S 011100` 会发生什么？`-S 010011` 呢？决定文件最终值的关键是什么？
