# 第 5 章 插曲：进程 API

> 英文原题：*Interlude: Process API*

!!! note "边栏：插曲"
    插曲会讨论系统中更实用的部分，尤其关注操作系统 API 以及如何使用它们。如果你不喜欢实用的东西，大可以跳过这些插曲。不过你理应喜欢实用的东西，因为它们通常在现实生活里派得上用场；比如，公司一般不会因为你擅长不实用的技能而雇用你。

本篇插曲讨论 UNIX 系统中的进程创建。UNIX 用一对系统调用——`fork()` 和 `exec()`——提供了一种最耐人寻味的新进程创建方式。第三个例程 `wait()` 则可供进程等待自己创建的进程完成。下面通过几个简单例子，更详细地介绍这些接口。于是，我们的问题是：

!!! danger "问题核心"
    **如何创建和控制进程？**

    操作系统应该提供哪些接口来创建和控制进程？如何设计这些接口，才能既提供强大功能，又易于使用，并拥有高性能？

## 5.1 `fork()` 系统调用

`fork()` 系统调用用于创建新进程 [C63]。不过先提醒你：它肯定是你这辈子调用过的最古怪的例程[^1]。更具体地说，假设有一个运行中的程序，其代码如图 5.1 所示；请仔细看看代码，最好亲手输入并运行一遍！

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    printf("hello world (pid:%d)\n", (int) getpid());
    int rc = fork();
    if (rc < 0) {
        // fork 失败；退出
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) { // 子进程（新进程）
        printf("hello, I am child (pid:%d)\n", (int) getpid());
    } else {
        // 父进程（主进程）走这条路径
        printf("hello, I am parent of %d (pid:%d)\n",
               rc, (int) getpid());
    }
    return 0;
}
```

*图 5.1：调用 `fork()`（`p1.c`）。*

运行这个名为 `p1.c` 的程序，会看到：

```console
prompt> ./p1
hello world (pid:29146)
hello, I am parent of 29147 (pid:29146)
hello, I am child (pid:29147)
prompt>
```

来仔细看看 `p1.c` 里发生了什么。进程刚开始运行时，先打印一条 `hello world` 消息，其中包含它的进程标识符，也就是 **PID**。这个进程的 PID 是 29146；在 UNIX 系统中，如果想对某个进程做点什么（例如让它停止运行），就用 PID 来指名它。目前为止，一切正常。

接下来，有意思的部分开始了。进程调用 `fork()` 系统调用；这是操作系统提供的一种新进程创建方式。古怪之处在于：新建的进程是调用进程的（几乎）完整副本。也就是说，在操作系统看来，现在有两个 `p1` 程序的副本正在运行，而且两者都即将从 `fork()` 系统调用返回。新创建的进程称为**子进程(child process)**，创建它的进程则称为**父进程(parent process)**。子进程并不像你可能以为的那样从 `main()` 开始运行——注意，`hello world` 只打印了一次；它一出生，就仿佛自己刚刚调用过 `fork()` 一样。

你可能已经注意到：子进程并非完全一样的副本。它确实拥有自己的地址空间副本（也就是自己的私有内存）、自己的寄存器、自己的 PC 等等，但 `fork()` 返回给它的值不同。具体来说，父进程会收到新建子进程的 PID，而子进程收到的返回码是 0。这个差别很有用，因为程序可以像上面那样，轻松编写分别处理两种情况的代码。

还有一点你可能也注意到了：`p1.c` 的输出是**不确定的(nondeterministic)**。创建子进程后，系统中出现了两个我们关心的活动进程：父进程和子进程。为简单起见，假设系统只有一颗 CPU，那么此刻既可能运行子进程，也可能运行父进程。在上面的例子中，父进程先运行，所以先打印了消息；换一次运行，结果可能刚好相反：

```console
prompt> ./p1
hello world (pid:29146)
hello, I am child (pid:29147)
hello, I am parent of 29147 (pid:29146)
prompt>
```

CPU 调度器决定某一时刻运行哪个进程，这个主题很快就会详细讨论。调度器非常复杂，我们通常不能对它将作出什么选择、哪个进程会先运行作出肯定假设。事实证明，这种不确定性会带来一些有趣的问题，在多线程程序中尤其如此；因此，在本书第二部分研究并发时，我们会看到更多不确定性。

## 5.2 `wait()` 系统调用

到目前为止，我们还没做多少事：只是创建一个打印消息后退出的子进程。不过有时，父进程等待子进程完成工作非常有用。这项任务可以用 `wait()` 系统调用（或者功能更完整的近亲 `waitpid()`）完成，详见图 5.2。

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    printf("hello world (pid:%d)\n", (int) getpid());
    int rc = fork();
    if (rc < 0) {
        // fork 失败；退出
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) { // 子进程（新进程）
        printf("hello, I am child (pid:%d)\n", (int) getpid());
    } else {
        // 父进程（主进程）走这条路径
        int rc_wait = wait(NULL);
        printf("hello, I am parent of %d (rc_wait:%d) (pid:%d)\n",
               rc, rc_wait, (int) getpid());
    }
    return 0;
}
```

*图 5.2：调用 `fork()` 和 `wait()`（`p2.c`）。*

在这个例子（`p2.c`）里，父进程调用 `wait()`，暂停自己的执行，直到子进程完成。子进程结束后，`wait()` 才返回父进程。

给前面的代码加上 `wait()` 后，输出就变得确定了。看得出为什么吗？来，想一想。

（等你思考……好了，时间到。）

既然你已经想过了，来看看输出：

```console
prompt> ./p2
hello world (pid:29266)
hello, I am child (pid:29267)
hello, I am parent of 29267 (rc_wait:29267) (pid:29266)
prompt>
```

有了这段代码，我们知道子进程总会先打印。为什么？一种可能是子进程像刚才一样先运行，自然也就先于父进程打印。不过，就算父进程碰巧先运行，它也会立即调用 `wait()`；在子进程运行并退出之前，这个系统调用不会返回[^2]。因此，即使父进程先获得运行机会，它也会彬彬有礼地等待子进程跑完；随后 `wait()` 返回，父进程才打印自己的消息。

## 5.3 最后是 `exec()` 系统调用

进程创建 API 最后一块重要拼图，是 `exec()` 系统调用[^3]。如果想运行一个不同于调用程序的程序，这个系统调用就很有用。例如，只有想继续运行同一个程序的副本时，在 `p2.c` 里调用 `fork()` 才够用；但我们经常想运行另一个程序，而 `exec()` 正好能办到这件事（见图 5.3）。

在这个例子里，子进程调用 `execvp()` 来运行字数统计程序 `wc`。具体来说，它让 `wc` 处理源文件 `p3.c`，告诉我们文件里有多少行、多少个单词和多少字节：

```console
prompt> ./p3
hello world (pid:29383)
hello, I am child (pid:29384)
29  107  1030 p3.c
hello, I am parent of 29384 (rc_wait:29384) (pid:29383)
prompt>
```

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    printf("hello world (pid:%d)\n", (int) getpid());
    int rc = fork();
    if (rc < 0) {
        // fork 失败；退出
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) { // 子进程（新进程）
        printf("hello, I am child (pid:%d)\n", (int) getpid());
        char *myargs[3];
        myargs[0] = strdup("wc");       // 程序："wc"（字数统计）
        myargs[1] = strdup("p3.c");     // 参数：要统计的文件
        myargs[2] = NULL;               // 标记数组末尾
        execvp(myargs[0], myargs);       // 运行字数统计程序
        printf("this shouldn’t print out");
    } else {
        // 父进程（主进程）走这条路径
        int rc_wait = wait(NULL);
        printf("hello, I am parent of %d (rc_wait:%d) (pid:%d)\n",
               rc, rc_wait, (int) getpid());
    }
    return 0;
}
```

*图 5.3：调用 `fork()`、`wait()` 和 `exec()`（`p3.c`）。*

`fork()` 系统调用很古怪；它的同伙 `exec()` 也算不上正常。它会接收一个可执行文件的名称（例如 `wc`）和一些参数（例如 `p3.c`），从该可执行文件中加载代码（和静态数据），用它们覆盖当前代码段（和当前静态数据）；程序内存空间中的堆、栈及其他部分也会重新初始化。随后，操作系统直接运行这个程序，并把参数作为该进程的 `argv` 传进去。因此，`exec()` 并不会创建新进程，而是把当前正在运行的程序（原来的 `p3`）变成另一个正在运行的程序（`wc`）。子进程执行 `exec()` 后，就好像 `p3.c` 从未运行过一样；一次成功的 `exec()` 调用永远不会返回。

## 5.4 为什么？API 背后的动机

你当然可能会问一个大问题：创建新进程理应是一件简单的事，为什么要为它设计这么古怪的接口？事实证明，把 `fork()` 与 `exec()` 分开，对构建 UNIX shell 至关重要。这样一来，shell 就能在调用 `fork()` 之后、调用 `exec()` 之前运行一些代码；这些代码可以改变即将运行的程序所处的环境，从而轻松实现许多有趣的功能。

!!! tip "提示：把事情做对（Lampson 定律）"
    Lampson 在广受推崇的《Hints for Computer Systems Design》[L83] 中说：「把事情做对。抽象和简单都不能替代正确。」有时候，你就是必须做正确的事；一旦做对，效果会远胜其他方案。进程创建 API 有许多设计方法，但 `fork()` 与 `exec()` 的组合既简单又强大得惊人。在这里，UNIX 的设计者就是把事情做对了。由于 Lampson 经常能「把事情做对」，我们用他的名字命名这条定律。

shell 只是一个用户程序[^4]。它显示提示符，然后等你输入内容。你输入一条命令（也就是可执行程序的名称及参数）后，在大多数情况下，shell 会找出该可执行文件在文件系统中的位置，调用 `fork()` 创建一个新子进程来运行命令，调用某个 `exec()` 变体来执行命令，再调用 `wait()` 等待命令结束。子进程结束后，shell 从 `wait()` 返回，再次打印提示符，准备接收下一条命令。

把 `fork()` 与 `exec()` 分开后，shell 可以相当轻松地完成一大堆实用工作。例如：

```console
prompt> wc p3.c > newfile.txt
```

在这个例子中，程序 `wc` 的输出被**重定向(redirection)** 到输出文件 `newfile.txt`（大于号表示这种重定向）。shell 实现它的方法非常简单：创建子进程后、调用 `exec()` 前，shell 关闭标准输出，再打开文件 `newfile.txt`。这样，即将运行的 `wc` 程序所产生的全部输出都会送进文件，而不是显示在屏幕上。

图 5.4 展示了一个恰好完成这项工作的程序。重定向之所以能够工作，是因为我们对操作系统管理**文件描述符(file descriptor)** 的方式作了一项假设。具体来说，UNIX 系统从 0 开始寻找空闲文件描述符。在这里，`STDOUT_FILENO` 会是第一个可用的描述符，因此调用 `open()` 时会把它分配出去。此后，子进程对标准输出文件描述符的写入——例如 `printf()` 等例程发起的写入——就会透明地转到新打开的文件，而不是屏幕。

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <fcntl.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    int rc = fork();
    if (rc < 0) {
        // fork 失败；退出
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) { // 子进程：把标准输出重定向到文件
        close(STDOUT_FILENO);
        open("./p4.output", O_CREAT|O_WRONLY|O_TRUNC, S_IRWXU);

        // 现在执行 "wc"……
        char *myargs[3];
        myargs[0] = strdup("wc");       // 程序："wc"（字数统计）
        myargs[1] = strdup("p4.c");     // 参数：要统计的文件
        myargs[2] = NULL;               // 标记数组末尾
        execvp(myargs[0], myargs);       // 运行字数统计程序
    } else {
        // 父进程（主进程）走这条路径
        int rc_wait = wait(NULL);
    }
    return 0;
}
```

*图 5.4：前述所有内容，再加上重定向（`p4.c`）。*

运行 `p4.c` 的输出如下：

```console
prompt> ./p4
prompt> cat p4.output
32  109  846 p4.c
prompt>
```

关于这份输出，你会注意到（至少）两件有意思的事。第一，运行 `p4` 时看起来什么也没发生；shell 只是打印出命令提示符，立刻准备接收下一条命令。但事实并非如此：`p4` 确实调用了 `fork()` 创建新子进程，随后又调用 `execvp()` 运行 `wc`。屏幕上之所以没有输出，是因为输出已经重定向到 `p4.output`。第二，对输出文件执行 `cat` 后，可以看到运行 `wc` 应有的全部输出。很酷，对吧？

UNIX 的**管道(pipe)** 以类似方式实现，只不过使用 `pipe()` 系统调用。在这种情况下，一个进程的输出连接到内核中的管道（也就是队列），另一个进程的输入也连接到同一条管道；于是，前一个进程的输出无缝成为后一个进程的输入，可以把命令串成又长又实用的链条。举个简单例子：在文件里查找某个单词，再统计它出现了多少次。有了管道以及 `grep`、`wc` 工具，这很容易——只要在命令提示符中输入 `grep -o foo file | wc -l`，然后对结果啧啧称奇就行。

到目前为止，我们只从高层勾勒了进程 API；这些调用还有大量细节值得学习和消化。例如，本书第三部分讨论文件系统时，还会进一步介绍文件描述符。现在只要知道，`fork()`/`exec()` 的组合是创建和操纵进程的一种强大方式，就足够了。

## 5.5 进程控制与用户

除了 `fork()`、`exec()` 和 `wait()`，UNIX 系统还提供许多与进程交互的接口。例如，`kill()` 系统调用用于向进程发送**信号(signal)**，其中包括暂停、终止等实用指令。为了方便，大多数 UNIX shell 会把某些组合键设置成向当前运行的进程发送特定信号。例如，`control-c` 向进程发送 `SIGINT`（中断）信号，通常会终止进程；`control-z` 则发送 `SIGTSTP`（停止）信号，让进程执行到一半时暂停下来（之后可以用命令恢复它，例如许多 shell 中内置的 `fg` 命令）。

整个信号子系统提供了一套丰富的基础设施，用来把外部事件送达进程：既能让单个进程接收并处理信号，也能向单个进程乃至整个**进程组(process group)** 发送信号。要使用这种通信方式，进程应该用 `signal()` 系统调用「捕获」各种信号；这样一来，特定信号到达进程时，进程会暂停正常执行，转而运行一段特定代码来响应信号。关于信号以及其中的种种微妙之处，请阅读其他资料 [SR05]。

这自然引出一个问题：谁可以向进程发送信号，谁不可以？我们使用的系统通常允许多人同时使用；如果其中任何一个人都能随意发送 `SIGINT` 等信号（中断并很可能终止某个进程），系统的可用性和安全性就会受到破坏。因此，现代系统对**用户(user)** 这个概念有严格定义。用户输入密码证明身份后登录，获得系统资源的访问权；随后可以启动一个或多个进程，并完全控制它们（暂停、杀死等等）。用户通常只能控制自己的进程；操作系统负责把 CPU、内存、磁盘等资源分配给每个用户及其进程，以满足系统的整体目标。

!!! note "边栏：超级用户（root）"
    系统通常需要一位能够管理它、不受普通用户那些限制的用户。这个用户应该能够杀死任意进程（例如某进程正在以某种方式滥用系统），即使进程不是由他启动的；也应该能运行 `shutdown` 等威力巨大的命令——顾名思义，它会关闭系统。在基于 UNIX 的系统中，这些特殊能力属于**超级用户(superuser)**，有时也叫 **root**。大多数用户不能杀死其他用户的进程，超级用户却可以。

    成为 root 很像成为蜘蛛侠：能力越大，责任越大 [QI15]。因此，为了提高安全性（也为了避免代价高昂的失误），通常最好以普通用户身份工作；如果确实需要成为 root，请小心行事，因为此刻，计算世界里所有破坏性的力量都在你的指尖。

## 5.6 实用工具

许多命令行工具也很有用。例如，`ps` 命令可以查看正在运行的进程；去读手册页，了解一些传给 `ps` 的实用参数。`top` 工具也相当好用，它会显示系统中的进程，以及它们吞掉了多少 CPU 和其他资源。好笑的是，运行 `top` 时，它经常声称自己才是头号资源大户；这家伙或许有点自恋。`kill` 命令可以向进程发送任意信号，稍微更方便的 `killall` 也可以。使用它们时一定要小心；要是不慎杀掉窗口管理器，你面前这台计算机可能一下子就变得很难用了。

最后，还有许多不同的 CPU 监视器，可以让你迅速了解系统负载。例如，我们总让 Raging Menace software 的 MenuMeters 在 Macintosh 工具栏里运行，以便随时看到 CPU 的利用率。一般来说，对正在发生的事情了解得越多越好。

## 5.7 小结

本章介绍了几个与 UNIX 进程创建有关的 API：`fork()`、`exec()` 和 `wait()`。不过，我们只是浅尝辄止。要了解更多细节，当然应该阅读 Stevens 与 Rago 的著作 [SR05]，尤其是有关进程控制、进程关系和信号的章节。那里的智慧还有太多值得汲取。

!!! note "边栏：进程 API 关键词"
    - 每个进程都有一个名字；在大多数系统中，这个名字是一个称为**进程 ID(PID)** 的数字。
    - UNIX 系统使用 `fork()` 系统调用创建新进程。创建者称为**父进程**，新创建的进程称为**子进程**。就像现实生活中偶尔发生的那样 [J16]，子进程是父进程几乎一模一样的副本。
    - `wait()` 系统调用让父进程可以等待子进程执行完毕。
    - `exec()` 系列系统调用让子进程摆脱与父进程的相似性，执行一个全新的程序。
    - UNIX shell 通常用 `fork()`、`wait()` 和 `exec()` 启动用户命令；把 `fork()` 和 `exec()` 分开后，不用修改正在运行的程序，就能实现输入/输出重定向、管道等酷炫功能。
    - 信号提供了进程控制能力，可以让作业停止、继续，甚至终止。
    - 某个人能控制哪些进程，由用户这个概念封装起来；操作系统允许多位用户进入系统，并确保用户只能控制自己的进程。
    - 超级用户能够控制所有进程（事实上还能做许多其他事情）；出于安全考虑，应该很少承担这个角色，并且始终保持谨慎。

## 参考文献

- `[C63]` “A Multiprocessor System Design” by Melvin E. Conway. AFIPS ’63 Fall Joint Computer Conference. New York, USA, 1963. ——一篇讨论如何设计多处理系统的早期论文；这可能是用 `fork()` 一词讨论产生新进程的最早出处。
- `[DV66]` “Programming Semantics for Multiprogrammed Computations” by Jack B. Dennis and Earl C. Van Horn. *Communications of the ACM*, Volume 9, Number 3, March 1966. ——一篇勾勒多道程序计算机系统基础的经典论文，无疑对 Project MAC、Multics 乃至最终的 UNIX 产生了巨大影响。
- `[J16]` “They could be twins!” by Phoebe Jackson-Edwards. *The Daily Mail*, March 1, 2016. ——这篇掷地有声的新闻报道展示了一堆相似得离谱的子女/父母照片，老实说还挺让人着迷。去吧，花两分钟生命看看，不过别忘了回来！这就是网上冲浪危险之处的一个缩影。
- `[L83]` “Hints for Computer Systems Design” by Butler Lampson. *ACM Operating Systems Review*, Volume 15:5, October 1983. ——Lampson 关于如何设计计算机系统的著名建议。你一生中应该读一次，很可能还应该读很多次。
- `[QI15]` “With Great Power Comes Great Responsibility” by The Quote Investigator. [quoteinvestigator.com](https://quoteinvestigator.com/2015/07/23/great-power/). ——考证者认为，这个观念最早见于 1793 年法国国民公会的一份法令集，大意是「他们必须认识到，重大的责任与巨大的权力不可分割」。直到 1962 年，蜘蛛侠漫画中才出现「能力越大，责任也必定越大！」所以这句话看来应该归功于法国大革命，而不是 Stan Lee。抱歉了，Stan。
- `[SR05]` *Advanced Programming in the UNIX Environment* by W. Richard Stevens, Stephen A. Rago. Addison-Wesley, 2005. ——使用 UNIX API 的一切细微之处都在这里。买下它！读完它！最重要的是，活出它！

## 作业（代码）

!!! note "边栏：代码作业"
    代码作业是一些小练习：你要编写代码并在真实机器上运行，从而积累使用基本操作系统 API 的经验。毕竟，你（大概）是一名计算机科学家，所以应该喜欢写代码，对吧？（如果不喜欢，还有计算机科学理论可选，不过那东西相当难。）当然，要真正成为专家，就必须花上不少时间摆弄机器；事实上，应该抓住一切借口写点代码，看看它如何工作。投入时间，成为你明知自己能够成为的睿智大师。

这份作业会让你熟悉刚读过的进程管理 API。别担心——它比听起来还要好玩！一般来说，尽可能多抽时间编写代码，会让你受益匪浅；那为什么不现在就开始？

### 问题

1. 编写一个调用 `fork()` 的程序。调用 `fork()` 前，让主进程访问一个变量（例如 `x`），并把它设为某个值（例如 100）。子进程中的变量值是多少？子进程和父进程都改变 `x` 的值时，会发生什么？
2. 编写一个程序，先用 `open()` 系统调用打开文件，再调用 `fork()` 创建新进程。子进程和父进程能否访问 `open()` 返回的文件描述符？它们并发（也就是同时）写文件时会发生什么？
3. 再编写一个使用 `fork()` 的程序。子进程应该打印 `hello`，父进程应该打印 `goodbye`。试着确保子进程总是先打印；不在父进程中调用 `wait()`，能做到吗？
4. 编写一个程序，调用 `fork()`，再调用某种形式的 `exec()` 来运行 `/bin/ls`。看看能否尝试 `exec()` 的所有变体，包括 Linux 上的 `execl()`、`execle()`、`execlp()`、`execv()`、`execvp()` 和 `execvpe()`。为什么同一个基本调用会有这么多变体？
5. 现在编写一个使用 `wait()` 的程序，让父进程等待子进程结束。`wait()` 返回什么？在子进程中使用 `wait()` 会发生什么？
6. 稍微修改上一个程序，这次用 `waitpid()` 代替 `wait()`。`waitpid()` 在什么情况下有用？
7. 编写一个程序创建子进程，然后在子进程中关闭标准输出（`STDOUT_FILENO`）。关闭描述符后，如果子进程调用 `printf()` 打印内容，会发生什么？
8. 编写一个程序创建两个子进程，并用 `pipe()` 系统调用，把一个进程的标准输出连接到另一个进程的标准输入。

[^1]: 好吧，我们承认没法肯定；谁知道没人的时候你都调用些什么例程？不过无论你的例程调用习惯有多离谱，`fork()` 都够古怪的。
[^2]: 有少数情况下，`wait()` 会在子进程退出前返回；一如既往，请阅读手册页了解详情。还要警惕本书中任何没有限定条件的绝对说法，比如「子进程总会先打印」，或者「UNIX 是世界上最好的东西，甚至胜过冰激凌」。
[^3]: 在 Linux 上，`exec()` 有六种变体：`execl()`、`execlp()`、`execle()`、`execv()`、`execvp()` 和 `execvpe()`。请阅读手册页了解更多。
[^4]: shell 有很多种，随便举几个：`tcsh`、`bash` 和 `zsh`。你应该选一个，阅读它的手册页，深入了解；所有 UNIX 专家都会这么做。
