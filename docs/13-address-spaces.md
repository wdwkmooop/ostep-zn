# 第 13 章 抽象：地址空间

> 英文原题：*The Abstraction: Address Spaces*

早年那会儿，造计算机系统可轻松了。你问为啥？因为用户没抱多大期望。就是那帮难缠的用户，整天惦记着「易用」「高性能」「可靠」这些个要求，才真真给大家惹来一脑门子官司。下回你要是碰见这么一位计算机用户，记得替我们谢谢他——谢谢你给我们添了这么多麻烦。

## 13.1 早期系统

从内存的角度看，早期的机器并没给用户提供多少抽象。基本上，机器的物理内存就长得像图 13.1 那样。

操作系统不过是一堆例程（说白了就是一个库），安安静静地待在内存里（这个例子里从物理地址 0 开始）；然后有一个正在跑的程序（也就是一个进程），当前也待在物理内存中（这个例子里从物理地址 64k 开始），并用着剩下的内存。这里头没什么障眼法，用户也没对操作系统抱多大指望。那会儿做操作系统的人日子过得是真舒坦，不是吗？

```text
0KB     +---------------------------+
        | Operating System          |
        | (code, data, etc.)        |
64KB    +---------------------------+
        |                           |
        | Current Program           |
        | (code, data, etc.)        |
        |                           |
max     +---------------------------+
```

*图 13.1：操作系统：早期岁月。*

## 13.2 多道程序设计与时间共享

过了一阵子，因为机器太贵，人们开始想办法更高效地共用机器。于是**多道程序设计(multiprogramming)** 的时代诞生了 [DV66]：某一时刻有多个进程都准备就绪待运行，操作系统就在它们之间来回切换，比如某个进程决定去做一次 I/O 的时候。这么做提高了 CPU 的有效利用率。在那个每台机器动辄几十万甚至上百万美元的年头（你还嫌你的 Mac 贵？），这种效率上的提升尤其要紧。

可没过多久，人们又对机器提出更多要求，**时间共享(time sharing)** 的时代随之降临 [S59, L60, M62, M83]。具体说，很多人意识到**批处理(batch computing)** 的局限，尤其是它对程序员本人的折磨 [CV65]——谁受得了又长又没效率的程序调试周期啊。于是「交互性」这个概念变得重要起来：许多用户可以同时用一台机器，每个人都等着（或者盼着）自己当前的任务能及时给点回应。

实现时间共享的一种法子是：先跑一个进程一小会儿，把整块内存都交给它随便用（图 13.1），然后把它停下，把它的全部状态存到某种磁盘上（包括整块物理内存），再加载另一个进程的状态，让它跑一阵子——如此这般，粗放地实现了机器共享 [M+63]。

可惜，这招有个大毛病：太慢，内存越大越慢。保存和恢复寄存器级别的状态（PC、通用寄存器之类）还算快，可把整块内存的内容都倒腾到磁盘上，那性能简直惨不忍睹。所以我们更想做的，是让进程留在内存里、直接在它们之间切换，这样操作系统就能高效地实现时间共享了（图 13.2）。

```text
0KB     +---------------------------+
        | Operating System          |
        | (code, data, etc.)        |
64KB    +---------------------------+
        | (free)                    |
128KB   +---------------------------+
        | Process C                 |
        | (code, data, etc.)        |
192KB   +---------------------------+
        | Process B                 |
        | (code, data, etc.)        |
256KB   +---------------------------+
        | (free)                    |
320KB   +---------------------------+
        | Process A                 |
        | (code, data, etc.)        |
384KB   +---------------------------+
        | (free)                    |
448KB   +---------------------------+
        | (free)                    |
512KB   +---------------------------+
```

*图 13.2：三个进程：共享内存。*

图中有三个进程（A、B 和 C），每个都从 512KB 物理内存里分到了一小块地盘。假设只有一颗 CPU，操作系统选择运行其中某个进程（比如 A），另外两个（B 和 C）则待在就绪队列里等着轮到自己。

随着时间共享越来越流行，你大概能猜到，新的要求也被压到了操作系统头上。尤其是，让多个程序同时待在内存里，使得**保护(protection)** 成了一个重要问题：你总不希望某个进程能读、甚至更糟——能写别的进程的内存吧。

## 13.3 地址空间

不过，我们还得照顾那帮难缠的用户，这就逼着操作系统为物理内存造一个易用的抽象出来。这个抽象我们叫它**地址空间(address space)**，它就是运行中的程序对系统内存的那套视角。吃透这个操作系统里最根本的内存抽象，是理解内存如何被虚拟化的关键。

一个进程的地址空间，包含运行中程序的所有内存状态。比如说，程序的代码（那些指令）总得待在内存的某个地方，所以它们就在地址空间里。程序运行时，用**栈(stack)** 来记录自己在函数调用链里的位置，也用来分配局部变量、在例程之间传递参数和返回值。最后，**堆(heap)** 用于动态分配、由用户管理的内存，比如你在 C 里调用 `malloc()` 得到的那块，或者在 C++、Java 这类面向对象语言里用 `new` 得到的那些。当然，地址空间里还有别的东西（比如静态初始化的变量），不过眼下我们就先认定这三个部件：代码、栈和堆。

在 Figure 13.3 那个例子里，我们有一个小小的地址空间（只有 16KB）[^1]。程序代码住在地址空间的顶部（这个例子里从 0 开始，塞进地址空间头 1K 里）。代码是静态的（所以好摆），我们可以把它放在地址空间顶部，并且清楚它随着程序运行不会再要更多空间。

[^1]: 我们经常用这种小例子，原因有二：(a) 画一个 32 位地址空间实在遭罪，(b) 算起来也更难。我们就喜欢简单的算术。

```text
0KB      +------------------------------------------+
         | Program Code                             |
         |   the code segment:                      |
         |   where instructions live                |
1KB      +------------------------------------------+
         | Heap                                     |
         |   the heap segment:                      |
         |   contains malloc'd data,                |
         |   dynamic data structures                |
         |   (it grows downward)                    |
2KB      +------------------------------------------+
         | (free)                                   |
         |                                          |
15KB     +------------------------------------------+
         | Stack                                    |
         |   (it grows upward)                      |
         |   the stack segment:                     |
         |   contains local variables,              |
         |   arguments to routines,                 |
         |   return values, etc.                    |
16KB     +------------------------------------------+
```

*图 13.3：一个地址空间示例。*

接下来，地址空间里还有两块区域，会在程序运行过程中增长（和收缩）：堆（在上方）和栈（在下方）。我们把它们这么摆，是因为两者都希望有地方长大；把两者放在地址空间的两头，就能给它们留出增长余地——只要朝着相反的方向长就行了。于是堆紧挨着代码之后开始（在 1KB 处），向下增长（比如用户通过 `malloc()` 要更多内存的时候）；栈则从 16KB 开始，向上增长（比如用户做一次过程调用的时候）。不过，栈和堆这么摆放只是一种约定；你爱怎么摆都行（不过后面我们会看到，当一个地址空间里共存着多个线程时，这种把地址空间一劈两半的漂亮分法就再也不管用了，哎）。

当然，我们描述地址空间时，描述的是操作系统提供给运行程序的那个抽象。程序实际上并不在物理地址 0 到 16KB 那一段内存里；它是被加载到某个随意的物理地址上的。看看 Figure 13.2 里的进程 A、B、C，你会发现每个进程都被加载到内存中不同的地址。于是问题就来了：

!!! danger "问题核心"
    **如何虚拟化内存**

    操作系统怎样才能在单块物理内存之上，为多个运行中的进程（它们都共用内存）营造出一个私有的、可能很大的地址空间这层抽象？

操作系统做成这件事时，我们说它正在**虚拟化内存(virtualizing memory)**，因为运行中的程序以为自己被加载到内存里某个特定的地址（比如 0），还拥有一个可能大得多的地址空间（比如 32 位或 64 位）；而现实完全是另一回事。

举个例子，当 Figure 13.2 里的进程 A 想在地址 0 处做一次加载（我们称这个地址为**虚拟地址(virtual address)**），操作系统就得联合某些硬件支持，想办法确保这次加载并不会真的落到物理地址 0，而是落到物理地址 320KB（也就是 A 被加载进内存的地方）。这就是内存虚拟化的关键，它支撑着世界上每一台现代计算机系统。

!!! tip "提示：隔离原则"
    隔离(isolation)是构建可靠系统的一条关键原则。如果两个实体彼此恰当地隔离开，那就意味着其中一个出故障也不会影响到另一个。操作系统致力于把进程彼此隔离，用这种方式防止一个进程祸害另一个。借助内存隔离，操作系统进一步确保运行中的程序无法影响底层操作系统自身的运转。一些现代操作系统把隔离做得更绝，把操作系统的各个部分之间也筑起高墙。这样的**微内核(microkernel)** [BH70, R+89, S+03] 因此可能比典型的宏内核设计提供更高的可靠性。

## 13.4 目标

于是我们就来到了这组讲义里操作系统的活儿：虚拟化内存。不过，操作系统可不只是把内存虚拟化了事，它还得干得漂亮。为了确保它干得漂亮，我们需要一些目标来引路。这些目标之前见过（想想导论那一章），以后还会再见到，但绝对值得再念叨一遍。

**虚拟内存(virtual memory, VM)** 系统的一个主要目标是**透明(transparency)**[^2]。操作系统应该把虚拟内存实现得让运行的程序完全无感。也就是说，程序不该察觉到内存被虚拟化这回事；它表现得就像自己独占了一块私有的物理内存。而在幕后，操作系统（和硬件）忙前忙后，把内存多路复用给许多不同的作业，从而把这层幻觉坐实。

[^2]: 「透明」这个用法有时让人犯迷糊；有些学生以为「透明」意味着什么都摆在明面上，也就是政府该有的样子。这里恰恰相反：操作系统提供的幻觉不该被应用程序看见。所以在通常的用法里，一个透明的系统是指那种不引人注意的系统，而不是一个遵照《信息自由法》对请求有求必应的系统。

VM 的另一个目标是**效率(efficiency)**。操作系统应尽力让虚拟化尽可能高效，无论在时间上（也就是别让程序跑得太慢）还是空间上（也就是别为支持虚拟化所需的数据结构吃掉太多内存）。要实现时间上高效的虚拟化，操作系统就得仰仗硬件支持，包括 **TLB** 之类的硬件特性（我们到时候会学到）。

最后，VM 的第三个目标是**保护(protection)**。操作系统得确保进程之间彼此受到保护，也要确保操作系统本身不被进程祸害。当一个进程做加载、存储或取指令时，它不该能够访问或以任何方式影响其他任何进程、或者操作系统本身的内存内容（也就是它地址空间之外的任何东西）。保护因此让我们得以实现进程之间的**隔离(isolation)** 特性；每个进程都应该跑在自己那个与世隔绝的茧里，免受其他有毛病、甚至恶意进程的蹂躏。

!!! note "边栏：你看到的每个地址都是虚拟的"
    写过打印指针的 C 程序吗？你看到的那个值（一个大数字，常常用十六进制打印），就是一个虚拟地址。有没有想过你程序的代码到底在哪儿？这也能打印出来——没错，既然打印得出来，它同样是虚拟地址。事实上，作为一个用户级程序的程序员，你能看到的任何地址都是虚拟地址。只有操作系统，靠着它那套虚拟化内存的机灵把戏，才知道这些指令和数据到底躺在机器的哪块物理内存里。所以永远别忘了：你在程序里打印出来的地址都是虚拟的，是内存布局的一层幻觉；真正的情况只有操作系统（和硬件）才晓得。

    下面这个小程序（`va.c`）会打印 `main()` 例程的位置（代码所在之处）、`malloc()` 返回的一个堆分配值，以及栈上一个整数的位置：

    ```c
    #include <stdio.h>
    #include <stdlib.h>
    int main(int argc, char *argv[]) {
        printf("location of code : %p\n", (void *) main);
        printf("location of heap : %p\n", (void *) malloc(1));
        int x = 3;
        printf("location of stack : %p\n", (void *) &x);
        return x;
    }
    ```

    在一台 64 位 Mac 上运行时，我们得到如下输出：

    ```text
    location of code : 0x1095afe50
    location of heap : 0x1096008c0
    location of stack : 0x7fff691aea64
    ```

    从这里你能看出，代码排在地址空间最前，接着是堆，而栈则被甩到了这个巨大虚拟空间的另一头。这些地址全都是虚拟的，会由操作系统和硬件负责转换，好从它们真正的物理位置把值取出来。

接下来几章，我们会把探索的重点放在虚拟化内存所需的基本机制上，包括硬件和操作系统的支持。我们还会研究你在操作系统里会遇到的一些更相关的策略，包括如何管理空闲空间，以及内存不够时该把哪些页踢出去。这么一路下来，你就能逐步搞懂一个现代虚拟内存系统到底是怎么运作的[^3]。

[^3]: 或者，我们会劝你退掉这门课。不过别急；要是你能挺过虚拟内存这一关，后面多半也就能一路挺到底了！

## 13.5 小结

我们已经见识了一个重大的操作系统子系统的登场：虚拟内存。VM 系统的职责，是为程序营造出一个又大、又稀疏、又私有的地址空间这层幻觉，让程序把所有指令和数据都搁在里面。操作系统会在硬件的鼎力相助下，把每一次这样的虚拟内存引用都变成物理地址，好拿去交给物理内存，把想要的信息取回来。操作系统会同时为许多进程做这件事，还要确保程序之间彼此受保护、操作系统也不受侵犯。这一整套做法既需要大量机制（一堆底层机械装置），也需要一些关键策略才能转得起来；我们会从最底下往上走，先讲那些关键机制。那就开始吧！

## 作业（代码）

这次作业里，我们只学几个在基于 Linux 的系统上查看虚拟内存用量的实用工具。这不过是蜻蜓点水，让你窥见一点可能性；想真正成为专家，还得自己往深里扎（一如既往！）。

### 问题

1. 第一个该看的 Linux 工具是极简的 `free`。先敲 `man free`，把整个手册页读完；它很短，别怕！
2. 现在运行 `free`，可以带些可能有用的参数（比如 `-m`，以兆字节显示内存总量）。你的系统里有多少内存？还剩多少空闲？这些数字符合你的直觉吗？
3. 接着写一个小程序，让它占用一定量的内存，叫 `memory-user.c`。这个程序应接受一个命令行参数：它将使用的内存兆字节数。运行时，它应分配一个数组，并不断遍历这个数组，逐个触碰每个元素。程序应无限期地这么做，或者，也可以在命令行上再指定一个时长。
4. 现在，一边运行你的 `memory-user` 程序，一边（在另一个终端窗口里、但在同一台机器上）运行 `free` 工具。程序运行时，内存用量总数怎么变？把 `memory-user` 程序杀掉之后呢？数字符合你的预期吗？试试不同大小的内存用量。用超大内存量时会发生什么？
5. 再试一个工具，叫 `pmap`。花点时间，仔细读完 `pmap` 的手册页。
6. 要用 `pmap`，你得知道自己关心的那个进程的进程 ID。所以，先运行 `ps auxw` 列出所有进程；然后挑一个有意思的，比如某个浏览器。这种情况下你也可以用自己的 `memory-user` 程序（其实，为了方便，你甚至可以让那个程序调用 `getpid()` 把它的 PID 打印出来）。
7. 现在对其中一些进程运行 `pmap`，用各种标志（比如 `-X`）揭示进程的诸多细节。你看到什么了？跟我们对代码/栈/堆那套朴素构想相比，一个现代地址空间是由多少种不同的实体构成的？
8. 最后，对不同的内存用量，在你的 `memory-user` 程序上运行 `pmap`。你在这儿看到什么？`pmap` 的输出符合你的预期吗？
