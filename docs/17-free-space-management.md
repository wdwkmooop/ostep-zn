# 第 17 章 空闲空间管理

> 英文原题：*Free-Space Management*

这一章，我们先从虚拟内存的讨论里小小地岔开一下，聊聊任何内存管理系统都绕不开的一个基本方面——不管是 malloc 库（管理进程堆里的那些页），还是操作系统本身（管理进程地址空间的一部分）。具体来说，我们要谈的是空闲空间管理所牵涉的种种问题。

先把问题说得具体点。管空闲空间本来可以很简单，等我们讲到分页(paging)那套概念时就明白了。当你管理的空间被切成固定大小的单元时，一切都很省心：你只要维护一张记录这些固定单元的表，客户端来要一个，把表里第一项交出去就行。

空闲空间管理真正开始变难（也变得有意思）的时候，是你管的空闲空间由**大小不一的单元**组成的时候。这种情况会出现在用户级内存分配库（比如 `malloc()` 和 `free()`）里，也会出现在用**分段(segmentation)** 实现虚拟内存、从而要管理物理内存的操作系统里。不管哪种情形，都会碰上一个叫**外部碎片(external fragmentation)** 的问题：空闲空间被剁成一块块大小各异的小碎片，于是碎裂开来；后续的请求有时就会失败，因为尽管空闲空间的总量比请求量还大，却找不到一整块连续的空间来满足它。

```text
0        10        20        30
+--------+---------+---------+
|  free  |  used   |  free   |
+--------+---------+---------+
```

上图就是这个问题的一个例子。这里可用的空闲空间总共是 20 字节；可惜它被分成了两块各 10 字节的碎片。结果，一个 15 字节的请求就会失败，尽管明明有 20 字节空闲。于是，本章要解决的正题就此登场。

!!! danger "问题核心"
    **在满足大小不一的请求时，空闲空间该如何管理？**

    可以用哪些策略来尽量减少碎片？不同做法在时间和空间上的开销各是多少？

## 17.1 假设

本章大部分讨论会围绕用户级内存分配库里那部了不起的分配器(allocator)史展开。我们主要借鉴 Wilson 那篇出色的综述 [W+95]，但更鼓励感兴趣的读者直接去啃原始文档，那里细节更多[^1]。

[^1]: 它有将近 80 页之长；所以，你得是真感兴趣才行！

我们假设存在一个基本接口，就像 `malloc()` 和 `free()` 提供的那样。具体来说，`void *malloc(size_t size)` 接收一个参数 `size`，也就是应用程序请求的字节数；它返回一个指针（没有特定类型，用 C 的话说就是 void 指针），指向一块该大小（或更大）的区域。与之配套的例程 `void free(void *ptr)` 接收一个指针，把对应那块空间释放掉。注意这个接口的言外之意：用户在释放空间时，并没有把这块空间的大小告诉库；因此，库在只拿到一个指针的情况下，必须自己能算出这块内存有多大。具体怎么做，本章稍后会讲。

这个库所管理的空间，历史上叫做**堆(heap)**，而用来管理堆中空闲空间的通用数据结构，就是某种**空闲链表(free list)**。这个结构里存着指向受管内存区域中所有空闲块的引用。当然，这个数据结构本身未必非得是个链表，只要某种能追踪空闲空间的结构就行。

我们进一步假设，主要关注的是前面说的**外部碎片**。分配器当然也可能有**内部碎片(internal fragmentation)** 的问题；如果分配器发放的内存块比请求的还大，那么这个块里那些没被要求（因而也就没被用上）的空间，就构成内部碎片（因为浪费发生在分配单元**内部**），这又是空间浪费的一例。不过，为了简单起见，也因为外部碎片是两类碎片里更有意思的那个，我们主要盯着外部碎片。

我们还假设，一块内存一旦发到客户端手里，就不能再挪到内存的别处去了。比如说，某个程序调用 `malloc()`、拿到一个指向堆内某块空间的指针，那么在程序通过对应的 `free()` 调用把它还回来之前，这块内存区域基本上就归程序「所有」了（库不能挪动它）。因此，空闲空间没法做**紧凑化(compaction)**——而那本来会是对抗碎片的一件利器[^2]。不过，操作系统在用分段实现虚拟内存时，倒是可以用紧凑化来对付碎片（正如讲分段的那一章所讨论的）。

[^2]: 一旦你把一块内存的指针交给 C 程序，通常就很难找出指向该区域的所有引用（指针）——它们可能存放在别的变量里，甚至在某次执行的寄存器里。在类型更强、带垃圾回收的语言里，情况可能不同，那种语言就能把紧凑化当作对抗碎片的技术来用。

最后，我们假设分配器管理的是一段**连续**的字节区域。某些情况下，分配器可以请求让这块区域长大；比如，用户级内存分配库在空间用光时，可能会陷入内核去让堆变大（通过 `sbrk` 之类的系统调用）。但为了简单，这里就假定这块区域在它整个生命期内是一个固定大小。

## 17.2 底层机制

在钻进策略细节之前，我们先过一遍大多数分配器都会用到的几种常见机制。首先，我们会讲**分割(splitting)** 和**合并(coalescing)** 的基础——这几乎是任何分配器都有的技术。其次，我们看看怎么快速、相对轻松地追踪已分配区域的大小。最后，我们谈怎么在空闲空间**内部**搭起一个简单的链表，来记录哪些空间是空闲的、哪些不是。

### 分割与合并

一条空闲链表里包含若干元素，用来描述堆里还剩多少空闲空间。那么，假设有下面这个 30 字节的堆：

```text
0        10        20        30
+--------+---------+---------+
|  free  |  used   |  free   |
+--------+---------+---------+
```

这个堆对应的空闲链表上会有两个元素。一个描述头一段 10 字节的空闲区（字节 0-9），另一个描述后一段空闲区（字节 20-29）：

```text
head -> [addr:0, len:10] -> [addr:20, len:10] -> NULL
```

如前所述，任何大于 10 字节的请求都会失败（返回 NULL）；根本找不到一块这么大的连续内存。一个恰好 10 字节的请求，随便哪块空闲块都能轻松满足。可要是请求的比 10 字节还小呢？

假设我们只要 1 字节内存。这种情况下，分配器会做一件叫**分割(splitting)** 的事：它找到一块能满足请求的空闲内存，把它劈成两半。第一块返回给调用者；第二块仍然留在链表上。于是在上面的例子里，如果来了一个 1 字节的请求，而分配器决定用链表上第二个元素来满足它，那么 `malloc()` 就会返回 20（这块 1 字节已分配区域的地址），链表则变成这样：

```text
head -> [addr:0, len:10] -> [addr:21, len:9] -> NULL
```

从图里能看到，链表基本保持原样；唯一的改动是空闲区现在从 21 而不是 20 开始，长度也只剩下 9 了[^3]。所以，当请求比任何一个空闲块都小时，分配器通常就会做这种分割。

[^3]: 这段讨论假设没有头部(header)——这是个不现实、但能让事情变简单的假设，眼下先这么用。

许多分配器里还有一种配套机制，叫做空闲空间的**合并(coalescing)**。再把上面的例子拿出来（空闲 10 字节、已用 10 字节、再空闲 10 字节）。

给定这个（很小的）堆，当应用程序调用 `free(10)`、把堆中间那块空间还回来时，会发生什么？如果我们不多想，简单地把这块空闲空间塞回链表，最后可能得到这样一条链表：

```text
head -> [addr:10, len:10] -> [addr:0, len:10] -> [addr:20, len:10] -> NULL
```

问题来了：虽然整个堆现在全是空闲的，它看上去却还是被分成了三块各 10 字节。于是，如果用户请求 20 字节，简单地遍历链表根本找不到这样一块空闲块，只能返回失败。

分配器为了避免这个问题，会在释放一块内存时**合并**空闲空间。思路很简单：把一块空闲内存还回来时，仔细看看这块内存的地址，以及它旁边那些空闲块的地址；如果新释放的空间紧挨着一个（在这个例子里是两个）现有的空闲块，就把它们并成一块更大的空闲块。于是有了合并，最终链表应该长这样：

```text
head -> [addr:0, len:30] -> NULL
```

没错，这正是最开始、任何分配发生之前堆链表的样子。有了合并，分配器就能更好地保证，应用程序手头总有大片的连续空闲空间可用。

### 追踪已分配区域的大小

你可能已经注意到，`free(void *ptr)` 这个接口并没有 size 参数；所以就假定：给一个指针，malloc 库就能迅速判断出正在释放的内存区域有多大，从而把这块空间收回到空闲链表里。

为了做到这一点，大多数分配器会在**头部(header)** 块里存一点额外信息，这个头部保存在内存中，通常就紧挨在发放出去的内存块**前面**。再看一个例子（图 17.1）。这里我们考察的是一块已分配的大小为 20 字节的内存，用 `ptr` 指向它；想象用户调用了 `malloc()` 并把结果存进 `ptr`，比如 `ptr = malloc(20);`。

```text
      malloc 库使用的头部
 hptr
  |
  v
+--------+---------------------------------------+
| Header | The 20 bytes returned to caller        |
+--------+---------------------------------------+
                           ^
                           |
                          ptr
```

*图 17.1：一块已分配区域外加头部。*

头部里至少有这块已分配区域的大小（这里就是 20）；它还可能包含一些额外指针来加速释放、一个用来做完整性检查的**魔数(magic number)**，以及其他信息。我们假设有个简单的头部，里面装区域大小和一个魔数，像这样：

```c
typedef struct __header_t {
    int size;
    int magic;
} header_t;
```

上面的例子就如图 17.2 所示。头部里装着这块区域的 size 和 magic，`ptr` 仍然指向返回给调用者的那 20 字节：

```text
 hptr
  |
  v
+--------+--------+--------------------------------+
| size:  | magic: | The 20 bytes returned to caller |
| 20     | 1234567|                                 |
+--------+--------+--------------------------------+
                           ^
                           |
                          ptr
```

*图 17.2：头部的具体内容。*

当用户调用 `free(ptr)` 时，库就用简单的指针运算算出头部从哪里开始：

```c
void free(void *ptr) {
    header_t *hptr = (void *)ptr - sizeof(header_t);
    ...
```

拿到指向头部的这个指针之后，库就能轻松做两件事：做一次健全性检查，看魔数是否等于预期值（`assert(hptr->magic == 1234567)`）；再用简单的算术算出这块新释放区域的总大小（也就是把头部大小加到区域大小上）。注意最后这句话里那个不起眼却关键的细节：空闲区域的大小 = 头部大小 + 分配给用户的空间大小。因此，当用户请求 N 字节内存时，库要找的不是大小为 N 的空闲块；它要找的是大小为 N **加上头部大小**的空闲块。

### 把空闲链表嵌进空闲空间

到目前为止，我们都把这条简单的空闲链表当成一个概念上的东西：它只是一张描述堆里空闲块的清单。可我们怎么在空闲空间**本身**里把这个链表搭起来呢？

在一条更普通的链表里，分配新节点时，你只要在需要空间时调用 `malloc()` 就行。可惜，在内存分配库**内部**，你不能这么干！你只能把链表搭在空闲空间本身里。如果这话听着有点怪，别担心——确实怪，但没怪到做不成的程度！

假设我们有一块 4096 字节的内存要管（也就是堆是 4KB）。要把它当成空闲链表来管，我们得先把这条链表初始化好；初始时，链表应该只有一个表项，大小是 4096（减去头部大小）。链表节点的定义如下：

```c
typedef struct __node_t {
    int size;
    struct __node_t *next;
} node_t;
```

现在我们看看初始化堆、并把空闲链表第一个元素放进这块空间的代码。这里假设堆是在一块通过系统调用 `mmap()` 拿到的空闲空间里搭起来的；这当然不是搭这种堆的唯一办法，但在本例里够用。代码如下：

```c
// mmap() 返回一个指向一块空闲空间的指针
node_t *head = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
                    MAP_ANON|MAP_PRIVATE, -1, 0);
head->size = 4096 - sizeof(node_t);
head->next = NULL;
```

跑完这段代码后，链表的状态是只有一个表项，大小为 4088。没错，这个堆小得可怜，但对我们来说是个好例子。`head` 指针保存着这段区域的起始地址；我们就假设它是 16KB（其实任何虚拟地址都行）。从视觉上看，堆就如图 17.3 所示。

```text
[virtual address: 16KB]
head
 |
 v
+--------+--------+--------------------------------+
| size:  | next:  | the rest of the 4KB chunk       |
| 4088   | 0      |                                 |
+--------+--------+--------------------------------+
        header: size field
        header: next field (NULL is 0)
```

*图 17.3：只有一个空闲块的堆。*

现在假设有人请求一块内存，比如 100 字节。为了满足这个请求，库先要找一块大到能容纳请求的块；因为只有一块空闲块（大小 4088），所以就是它了。然后，这块会被劈成两半：一块大到足以满足请求（外加头部，如前所述），另一块是剩下的空闲块。假设头部是 8 字节（一个整型 size 加一个整型 magic），堆里的空间现在就如图 17.4 所示。

```text
[virtual address: 16KB]
+----------------+-----------------------------------+
| size: 100      | head -> size: 3980                |
| magic: 1234567 |         next: 0                   |
| ptr            |                                   |
| The 100 bytes  | The free 3980 byte chunk          |
| now allocated  |                                   |
+----------------+-----------------------------------+
```

*图 17.4：一次分配之后的堆。*

于是，收到 100 字节的请求后，库从仅有的那块空闲块里切出 108 字节，返回一个指向它的指针（上图里标着 `ptr`），把头部信息偷偷塞在这块已分配空间的前面，供日后 `free()` 时使用，并把链表里那个空闲节点缩小到 3980 字节（4088 减 108）。

现在看看有三个已分配区域、每个 100 字节（含头部则是 108 字节）时的堆。图 17.5 给出了这个堆的可视化。

```text
[virtual address: 16KB]
+------------------+------------------+------------------+------------------+
| size: 100        | size: 100        | size: 100        | head             |
| magic: 1234567   | magic: 1234567   | magic: 1234567   | size: 3764       |
| ...              | ... sptr         | ...              | next: 0          |
| 100 bytes        | 100 bytes        | 100 bytes        |                  |
| still allocated  | still allocated  | still allocated  | free 3764-byte   |
+------------------+------------------+------------------+------------------+
```

*图 17.5：三个已分配块时的空闲空间。*

从图里能看到，堆的前 324 字节现在已分配，因此那块地方有三个头部，以及调用程序正在使用的三个 100 字节区域。空闲链表依旧乏善可陈：只有单个节点（由 `head` 指向），但在三次分割之后，它现在只剩 3764 字节。可是，当调用程序通过 `free()` 归还一些内存时，又会发生什么呢？

在上面的图里，应用程序归还的是中间那块已分配内存，它调用的是 `free(16500)`（16500 这个值，是把内存区域的起点 16384，加上前一块的 108，再加上本块头部的 8 字节得到的）。这个值用指针 `sptr` 标出。

库立刻算出这块空闲区域的大小，然后把空闲块放回空闲链表。假设我们插在空闲链表的头部，空间现在如图 17.6 所示。

```text
[virtual address: 16KB]
+------------------+------------------+------------------+
| size: 100        | head             | size: 3764       |
| magic: 1234567   | size: 100        | next: 0          |
| ...              | next: 16708      |                  |
| 100 bytes        | sptr ...         | free 3764-byte   |
| still allocated  | (now a free      | chunk            |
|                  |  chunk of memory)|                  |
+------------------+------------------+------------------+
```

*图 17.6：两个已分配块时的空闲空间。*

于是现在这条链表以一块小的空闲块（100 字节，由链表头指向）打头，后面跟着一大块空闲块（3764 字节）。

我们的链表终于有不止一个元素了！没错，空闲空间碎片化了——这很不幸，但也很常见。

最后一个例子：现在假设最后两个在用块也被释放了。不做合并的话，你可能得到一条高度碎片化的空闲链表（见图 17.7）。

```text
[virtual address: 16KB]
+------------------+------------------+------------------+------------------+
| size: 100        | size: 100        | head             | size: 3764       |
| next: 16492      | next: 16708      | size: 100        | next: 0          |
| ...              | ...              | next: 16384      |                  |
| (now free)       | (now free)       | (now free)       | free 3764-byte   |
|                  |                  |                  | chunk            |
+------------------+------------------+------------------+------------------+
```

*图 17.7：一条未合并的空闲链表。*

从图里能看出，我们现在一团糟！为什么？很简单，我们忘了合并链表。尽管所有内存都是空闲的，它却被切得七零八落，于是一块本不碎片化的内存看起来就像碎片化的。解决办法很简单：遍历链表，把相邻的块并起来；做完之后，堆就又完整了。

### 让堆长大

最后再谈一个许多分配库里都有的机制。具体说，要是堆的空间用光了，你该怎么办？

最简单的办法就是直接认输。有些情况下这是唯一的选择，所以返回 `NULL` 也是个体面的做法。别难过！你试过了，虽然败了，但虽败犹荣。

大多数传统分配器一开始只有一个很小的堆，用光了就向操作系统再要一些内存。通常这意味着它们得做某种系统调用（比如大多数 UNIX 系统里的 `sbrk`）来让堆生长，然后从新空间里分配块。为了满足 `sbrk` 请求，操作系统会找出空闲的物理页，把它们映射进发起请求那个进程的地址空间，然后返回新堆末尾的值；这时，一个更大的堆就可用了，请求也就能顺利满足。

## 17.3 基本策略

现在手里有些家什了，我们来过一遍管理空闲空间的一些基本**策略(policy)**。这些做法大多基于相当简单的方针，你自己多半也想得出来；读之前先试试，看看你能不能把各种方案（也许还有新点子！）都想到。

理想的分配器又**快**、又能**尽量减少碎片**。可惜，分配和释放请求的序列可以任意而来（毕竟它们由程序员决定），所以再好的策略，碰上不对的输入也可能表现得很糟。因此，我们不会去讲某个「最好」的办法，而是聊聊一些基础的，并讨论它们各自的优劣。

### 最佳匹配

**最佳匹配(best fit)** 策略相当简单：先搜一遍空闲链表，找出那些不小于请求大小的空闲块；然后，在这堆候选里挑出**最小**的那个返回——也就是所谓的最佳匹配块（其实叫最小匹配也行）。搜一趟空闲链表就足以找到该返回的正确块。

最佳匹配背后的直觉很简单：返回一块尽量贴近用户请求大小的块，好减少浪费的空间。但这是有代价的；天真的实现在做穷举搜索、寻找正确空闲块时，会付出沉重的性能代价。

### 最差匹配

**最差匹配(worst fit)** 做法和最佳匹配相反：找出最大的块，把请求的量给它，剩下的（大）块留在空闲链表上。最差匹配想借此留下大块空闲，而不是最佳匹配做法会产生的一大堆小块。不过话说回来，它同样需要搜遍整个空闲空间，所以也可能代价不菲。更糟的是，多数研究表明它表现很差：既导致过度的碎片，又要背负高昂的开销。

### 最先匹配

**最先匹配(first fit)** 方法就是：找到第一块足够大的块，把请求的量返回给用户。和前面一样，剩下的空闲空间留着应付后续请求。

最先匹配的好处是**快**——不需要对所有空闲空间做穷举搜索——但有时会用小对象把空闲链表的开头弄脏。于是，分配器怎么管理空闲链表的顺序就成了个问题。一种做法是按地址排序；让链表按空闲空间的地址有序，合并会更容易，碎片也往往更少。

### 下一个匹配

**下一个匹配(next fit)** 算法不总是从链表头开始做最先匹配搜索，而是额外保存一个指针，记着上一次搜到哪里。它的想法是让空闲空间的搜索更均匀地散布在整条链表上，从而避免链表开头被打成碎片。这种做法的性能和最先匹配相当接近，因为同样不用做穷举搜索。

### 例子

下面是上述策略的几个例子。设想一条空闲链表上有三个元素，大小分别是 10、30、20（这里忽略头部和其他细节，只看策略怎么运作）：

```text
head -> [10] -> [30] -> [20] -> NULL
```

假设来一个大小为 15 的分配请求。最佳匹配会搜遍整条链表，发现 20 最合适，因为它是能容纳该请求的最小空闲空间。结果链表：

```text
head -> [10] -> [30] -> [5] -> NULL
```

就像这个例子里发生的、最佳匹配也常常发生的那样，现在剩下一小块空闲碎片。最差匹配做法类似，但它找的是最大的块，在这个例子里是 30。结果链表：

```text
head -> [10] -> [15] -> [20] -> NULL
```

这个例子里，最先匹配策略做得和最差匹配一样，也是找到第一块能满足请求的空闲块。差别在搜索成本上：最佳匹配和最差匹配都要看完整条链表；最先匹配只检查空闲块，直到找到合适的为止，因此降低了搜索成本。

这些例子不过是分配策略的冰山一角。想理解得更深，需要用真实负载、以及更复杂的分配器行为（比如合并）做更细致的分析。也许，该留到作业里去琢磨，你说呢？

## 17.4 其他做法

除了上面讲的基本做法，人们还提出过一大堆技巧和算法，从某些方面改进内存分配。这里列出几个供你参考（也就是说，别光想着最佳匹配一种分配方式）。

### 分离链表

一个流行了一阵子的有趣做法，是使用**分离链表(segregated list)**。基本想法很简单：如果某个应用程序有一种（或少数几种）常被请求的固定大小，那就专门留一条链表来管这种大小的对象；其余请求统统转给一个更通用的内存分配器。

这种做法的好处显而易见。有一块内存专门伺候某一种大小的请求，碎片问题就远没那么要紧了；而且，当请求正好是那个大小时，分配和释放能做得相当快，因为不需要对链表做复杂搜索。

不过，就像一切好点子一样，这种做法也会给系统引入新的麻烦。比如，相比通用池，你该给那个专门服务特定大小请求的内存池分多少内存？有一个特别的分配器——由大神级工程师 Jeff Bonwick 打造的 **slab 分配器(slab allocator)**（当初是为 Solaris 内核设计的）——就相当漂亮地处理了这个问题 [B94]。

具体来说，内核启动时会为那些很可能被频繁请求的内核对象（比如锁、文件系统 inode 等）分配一批**对象缓存(object cache)**；这些对象缓存各自就是一条固定大小的分离空闲链表，能快速响应内存分配和释放请求。当某个缓存的空闲空间快用光时，它就向更通用的内存分配器要一些 **slab**（总请求量是页大小和该对象大小的整数倍）。反过来，当某个 slab 里对象的引用计数全都归零时，通用分配器就可以把它们从专用分配器那里回收，这在 VM 系统需要更多内存时经常发生。

!!! note "边栏：伟大的工程师是真伟大"
    像 Jeff Bonwick 这样的工程师（这人不仅写了我们这儿提到的 slab 分配器，还是了不起的文件系统 ZFS 的带头人）正是硅谷的心脏。几乎每一件伟大的产品或技术背后，都有一个人（或一小撮人），其天赋、能力和投入都远超常人。正如 Facebook 的马克·扎克伯格所说：「某个岗位上出类拔萃的人，可不只是比一个还不错的强一点点。他们强上 100 倍。」这就是为什么直到今天，一两个人就能创办一家永远改变世界面貌的公司（想想 Google、Apple 或 Facebook）。努力干，你也许也能成为这样一个「100 倍」的人。做不到的话，就跟这样的人共事吧；你一天学到的，比大多数人一个月学到的还多。再做不到，那就难过吧。

slab 分配器还超出了大多数分离链表做法——它让链表上的空闲对象保持**预先初始化**的状态。Bonwick 证明了数据结构的初始化和销毁代价高昂 [B94]；把释放的对象以其初始化后的状态留在特定链表里，slab 分配器就避免了每个对象频繁地初始化、销毁，从而明显降低了开销。

### 伙伴分配

因为合并对分配器至关重要，有些做法就是围绕「让合并变简单」来设计的。一个很好的例子是**二进制伙伴分配器(binary buddy allocator)** [K65]。

在这种系统里，空闲内存首先在概念上被看成一大块大小为 $2^N$ 的空间。当来一个内存请求时，寻找空闲空间的过程会递归地把空闲空间一分为二，直到找到一块大到足以容纳请求的块（再分一次就太小了）。这时，把请求的块返回给用户。下面是一个 64KB 空闲空间在为 7KB 块寻找空间时被分割的例子：

```text
                    +----------------+
                    |     64 KB      |
                    +----------------+
            +----------------+----------------+
            |     32 KB      |     32 KB      |
            +----------------+----------------+
        +--------+--------+
        | 16 KB  | 16 KB  |
        +--------+--------+
     +----+----+
     |8KB |8KB |   <- 最左边 8KB 被分配（深灰）
     +----+----+
```

在这个例子里，最左边那块 8KB 被分配（用更深的灰色表示）并返回给用户；注意这种方案会有内部碎片，因为你只能发放大小是 2 的幂的块。

伙伴分配器的精妙之处体现在那块内存被释放的时候。把 8KB 块还回空闲链表时，分配器会检查它的「伙伴(buddy)」8KB 是不是也空闲；如果是，就把两块并成一块 16KB。接着分配器再检查这块 16KB 的伙伴是否空闲；如果是，就再并。这个递归合并过程顺着树往上走，直到要么恢复出整块空闲空间，要么发现某个伙伴正在使用而停下。

伙伴分配之所以这么好用，是因为判断某块的伙伴很简单。你问怎么判断？想想上面空闲空间里各块的地址。仔细想想你会发现，每一对伙伴的地址只差**一个比特**；具体是哪一位，取决于它在伙伴树里的层次。于是，你就对二进制伙伴分配方案怎么运作有了基本概念。更多细节，一如既往，见 Wilson 的综述 [W+95]。

### 其他想法

上面许多做法的一个主要问题是**可扩展性(scalability)** 不足。具体说，搜索链表可能相当慢。因此，高级分配器会用更复杂的数据结构来对付这些开销，用简单性换性能。例子包括平衡二叉树、伸展树(splay tree)、偏序树(partially-ordered tree)等 [W+95]。

现代系统往往有多个处理器、运行多线程负载（这些你会在本书并发那一部分详细学到），所以人们花了很多力气让分配器在多处理器系统上也能好好工作，这毫不奇怪。两个精彩的例子见 Berger 等人的工作 [B+00] 和 Evans 的工作 [E06]；细节自己去瞧。

这些不过是人们多年来对内存分配器上千个想法中的两个；好奇的话就自己读下去。实在不行，读读 glibc 分配器是怎么工作的 [S15]，感受一下真实世界长什么样。

## 17.5 小结

这一章里，我们讨论了内存分配器最基础的那些形态。这样的分配器无处不在：它们链进你写的每一个 C 程序，也存在于底层操作系统里——操作系统给自己管理内存时同样要用它们。和许多系统一样，搭这么个系统要做出许多权衡；你对交给分配器的确切负载了解得越多，就越能把它调得适配那份负载。打造一个又快、又省空间、又可扩展、还能应付各种负载的分配器，至今仍是现代计算机系统里一个持续存在的挑战。

## 作业（模拟器）

程序 `malloc.py` 让你探索本章所描述的一个简单空闲空间分配器的行为。其基本操作的细节见 README。

### 问题

1. 先用 `-n 10 -H 0 -p BEST -s 0` 这几个标志跑一跑，随机生成一些分配和释放。你能预测 `alloc()`/`free()` 会返回什么吗？每次请求之后，你能猜出空闲链表的状态吗？随着时间推移，你对这条空闲链表有什么发现？
2. 用 WORST 匹配策略来搜空闲链表（`-p WORST`）时，结果有什么不同？什么变了？
3. 用 FIRST 匹配（`-p FIRST`）又如何？用最先匹配时，是什么变快了？
4. 对上面这些问题，链表的排序方式会影响某些策略找到空闲位置所花的时间。用不同的空闲链表排序（`-l ADDRSORT`、`-l SIZESORT+`、`-l SIZESORT-`），看看策略和排序方式如何相互作用。
5. 空闲链表的合并可能相当重要。把随机分配的次数调大（比如 `-n 1000`）。随着时间推移，更大的分配请求会怎样？分别在开启和不开启合并的情况下运行（也就是不带和带 `-C` 标志）。你看到的结果有什么不同？每种情况下空闲链表随时间有多大？这种情况下链表的排序还有影响吗？
6. 把已分配比例 `-P` 调到高于 50 时会怎样？当它接近 100 时，分配会怎样？接近 0 时又如何？
7. 你能发出什么样的特定请求，来制造高度碎片化的空闲空间？用 `-A` 标志创建碎片化的空闲链表，看看不同的策略和选项如何改变空闲链表的组织。
