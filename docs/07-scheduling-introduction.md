# 第 7 章 调度：介绍

> 英文原题：*Scheduling: Introduction*

到这会儿，运行进程的各种底层机制（比如上下文切换）应该已经清楚了；要是还不清楚，就翻回前一两章，把那些东西是怎么运作的再读一遍。不过，操作系统调度器采用的高层**策略(policy)**，我们还没搞明白。这一章就来补上这一课，介绍一系列调度策略（有时也叫调度**规程(discipline)**）——它们都是许多聪明又勤奋的人多年来琢磨出来的。

说起来，调度的历史比计算机系统本身还早；早期做法直接取自**运营管理(operations management)** 领域，再搬到计算机上。这也不奇怪：流水线，以及人类许多其他活动，同样需要调度，其中有很多相似的关切，比如对效率那种激光般精准的执念。于是，我们的问题来了：

    **如何制定调度策略？**

    我们该怎样搭建一个思考调度策略的基本框架？关键假设有哪些？哪些指标重要？最早的计算机系统用过哪些基本做法？

## 7.1 负载假设

在探讨各种可能的策略之前，我们先对系统中的进程作一些简化假设，这些进程合在一起有时称为**负载(workload)**。确定负载是制定策略的关键一环；你对负载了解得越多，策略就能调得越精细。

这里给出的负载假设大多不切实际，但（暂时）没关系，因为我们会一路把它们放宽，最终开发出一套我们会称之为……（戏剧性停顿）……**完全可用的调度规程**[^1]。

我们对系统中运行的进程（有时叫**作业(job)**）作如下假设：

1. 每个作业运行时间相同。
2. 所有作业同时到达。
3. 作业一旦启动，就一直运行到完成。
4. 所有作业只使用 CPU（也就是不做任何 I/O）。
5. 每个作业的运行时长是已知的。

我们说过这些假设大多不切实际，但正如奥威尔《动物庄园》[O45] 里有些动物比其他动物更平等，本章里有些假设也比另一些更不切实际。特别地，"每个作业运行时长已知"这一条可能会让你不安：这会让调度器变成全知全能的神仙。这虽然（大概）挺棒，但短期内恐怕不会成真。

## 7.2 调度指标

除了对负载作假设，我们还需要一件东西，才能比较不同的调度策略：一个**调度指标(metric)**。指标就是我们用来衡量某样东西的尺子，而调度中有好几种有意义的指标。不过为了省事，我们现在只用一个指标：**周转时间(turnaround time)**。一个作业的周转时间，定义为它完成的时间减去它到达系统的时间。更正式地，周转时间 $T_{turnaround}$ 为：

$$T_{turnaround} = T_{completion} - T_{arrival} \tag{7.1}$$

由于我们假设所有作业同时到达，眼下 $T_{arrival} = 0$，因此 $T_{turnaround} = T_{completion}$。等我们放宽前面那些假设，这个等式就会变。

你应该注意到，周转时间是个性能指标，也是本章关注的头等大事。另一个让人感兴趣的指标是**公平性(fairness)**，可以用（例如）Jain 公平指数 [J91] 来衡量。性能和公平在调度中常常互相打架：比如，一个调度器可能优化了性能，代价却是让少数作业迟迟得不到运行，公平性因此受损。这个两难告诉我们，生活并不总是完美的。

## 7.3 先来先服务（FIFO）

我们能实现的最基本的算法，叫做**先来先服务(First In, First Out, FIFO)** 调度，有时也叫**先到先服务(First Come, First Served, FCFS)**。

[^1]: 用一样的语气念出来："一台完全可用的死星。"

FIFO 有不少优点：显然很简单，因而容易实现。而且，在现有假设下，它运行得相当不错。我们一起快速算个例子。想象三个作业 A、B、C 几乎同时到达系统（$T_{arrival} = 0$）。由于 FIFO 总得把某个作业放在最前面，我们不妨假设它们虽然同时到达，但 A 比 B 早了一丝丝，B 又比 C 早了一丝丝。再假设每个作业运行 10 秒。这些作业的平均周转时间是多少？

| 作业 | 开始 | 完成 |
|---|---|---|
| A | 0 | 10 |
| B | 10 | 20 |
| C | 20 | 30 |

*图 7.1：FIFO 简单示例。*

由图 7.1 可见，A 在 10 完成，B 在 20，C 在 30。因此，三个作业的平均周转时间就是 $\frac{10+20+30}{3}=20$。算周转时间就这么简单。

现在放宽其中一个假设。具体来说，放宽假设 1，不再假定每个作业运行时间相同。这时 FIFO 表现如何？你能构造出什么样的负载，让 FIFO 表现得很糟？

| 作业 | 开始 | 完成 |
|---|---|---|
| A | 0 | 100 |
| B | 100 | 110 |
| C | 110 | 120 |

*图 7.2：为什么 FIFO 没那么好。*

如图 7.2 所示，作业 A 先跑了整整 100 秒，B 和 C 连上场的机会都没有。于是系统的平均周转时间高得难受：足足 110 秒（$\frac{100+110+120}{3}=110$）。这个问题通常称为**护航效应(convoy effect)** [B+79]——一群相对较轻的资源消费者，被一个重量级消费者堵在了后面。这个场景也许会让你想起超市里排的那一条队，以及当你看到前面那位推着三辆购物车、还掏出支票本准备付账时的感受：有得等了。[^2]

!!! tip "提示：SJF 的原则"
    最短作业优先代表了一条通用的调度原则，适用于任何"每位顾客（在我们这儿是作业）感知到的周转时间"很重要的系统。想想你排过的任何一条队：如果那家店在乎顾客满意度，它多半会考虑 SJF。比如，超市常设一条"十件以下"快速通道，就是为了让只买几样东西的顾客不至于被堵在某个正为核冬天囤货的家庭后面。

那该怎么办？面对"作业运行时长各不相同"这个新现实，怎样开发出更好的算法？先想想，再往下读。

## 7.4 最短作业优先（SJF）

事实证明，有一个非常简单的办法能解决这个问题；其实这主意是从运筹学 [C54, PV56] 里借来、用到计算机作业调度上的。这个新调度规程叫做**最短作业优先(Shortest Job First, SJF)**，名字很好记，因为它把策略描述得相当完整：先跑最短的作业，再跑次短的，以此类推。

| 作业 | 开始 | 完成 |
|---|---|---|
| B | 0 | 10 |
| C | 10 | 20 |
| A | 20 | 120 |

*图 7.3：SJF 简单示例。*

拿上面那个例子改用 SJF 调度，图 7.3 展示了运行 A、B、C 的结果。希望这张图能让你看清，为什么 SJF 在平均周转时间上表现好得多。仅仅把 B 和 C 排在 A 前面，SJF 就把平均周转时间从 110 秒降到 50 秒（$\frac{10+20+120}{3}=50$），提升了一倍还多。

事实上，在所有作业同时到达的假设下，我们可以证明 SJF 确实是最优调度算法。不过你上的是系统课，不是理论课、也不是运筹学课；这里不许证明。

!!! note "边栏：抢占式调度器"
    在批处理的旧时代，人们开发了不少**非抢占式(non-preemptive)** 调度器；这类系统会把每个作业跑完，才考虑要不要运行新作业。现代的调度器几乎全是**抢占式(preemptive)** 的，很乐意为了运行另一个进程而停掉当前进程。这意味着调度器用上了我们之前学过的那些机制；具体来说，调度器可以执行一次上下文切换，暂时停掉一个正在运行的进程，再恢复（或启动）另一个。

## 7.5 最短完成时间优先（STCF）

要解决这个顾虑，我们得放宽假设 3（作业必须运行到完成），那就放宽吧。此外，调度器本身也需要一些机制。你可能已经猜到了，结合前面讲的时钟中断和上下文切换，B 和 C 到达时调度器当然可以做点别的事：它可以抢占作业 A，决定先运行另一个作业，也许稍后再继续 A。按我们的定义，SJF 是非抢占式调度器，因此才会遭遇上面那些问题。

幸运的是，真有一个调度器就是这么做的：给 SJF 加上抢占，叫做**最短完成时间优先(Shortest Time-to-Completion First, STCF)**，也叫**抢占式最短作业优先(Preemptive Shortest Job First, PSJF)** 调度器 [CK68]。每当新

| 时间 | 事件 |
|---|---|
| 0 | A 开始运行 |
| 10 | B、C 到达，A 被抢占 |
| 10 | B 开始运行 |
| 20 | B 完成，C 开始 |
| 30 | C 完成，A 恢复运行 |
| 120 | A 完成 |

*图 7.5：STCF 简单示例。*

作业进入系统，STCF 调度器就在所有剩余作业（含新作业）中挑出剩余时间最少的那个来运行。于是在我们的例子里，STCF 会抢占 A 并让 B、C 跑到完成；只有它们都结束后，才会调度 A 剩下的时间。图 7.5 展示了一个例子。

结果平均周转时间大有改善：50 秒（$\frac{(120-0)+(20-10)+(30-10)}{3}$）。和之前一样，在新假设下，STCF 可证明是最优的；既然所有作业同时到达时 SJF 是最优的，你大概也能看出 STCF 为何最优的直觉所在。

## 7.6 新指标：响应时间

这么说，如果我们知道作业长度、作业又只用 CPU、而且唯一指标是周转时间，那 STCF 会是很棒的策略。事实上，对一些早期的批处理系统来说，这类调度算法确实讲得通。然而，**分时机器(time-shared machine)** 的出现把一切都改变了。如今用户会坐在终端前，要求系统同时提供交互式体验。于是一个新指标诞生了：**响应时间(response time)**。

我们把响应时间定义为作业到达系统到它第一次被调度之间的时长。[^3] 更正式地：

$$T_{response} = T_{firstrun} - T_{arrival} \tag{7.2}$$

例如，对上面那个调度（A 在时刻 0 到达，B 和 C 在时刻 10 到达），每个作业的响应时间是：A 为 0，B 为 0，C 为 10（平均 3.33）。

你可能已经想到了，STCF 及其同类策略对响应时间并不友好。比如三个作业同时到达时，第三个作业得等前两个从头到尾跑完，才轮到自己被调度一次。这对周转时间很棒，对响应时间和交互性却相当糟糕。想象一下：你坐在终端前打字，却因为别的作业插到了你前面，得等上 10 秒

[^3]: 有人定义得略有不同，例如把"直到作业产生某种响应"也计入；我们的定义是其中最好的情形，本质上假设作业产生响应是瞬时的。

才看到系统的回应——这可不太愉快。于是，又留下一个问题：怎样构建对响应时间敏感的调度器？

## 7.7 轮转（RR）

为解决这个问题，我们引入一个新调度算法，经典地称为**轮转(Round-Robin, RR)** 调度 [K64]。基本思路很简单：RR 不把作业跑完，而是让作业运行一个**时间片(time slice)**（有时叫**调度量子(scheduling quantum)**），然后切换到运行队列里的下一个作业；如此反复，直到作业全部完成。正因如此，RR 有时也叫**时间切片(time-slicing)**。注意，时间片的长度必须是时钟中断周期的整数倍；所以如果时钟每 10 毫秒中断一次，时间片可以是 10、20，或 10 ms 的任意倍数。

要更仔细地理解 RR，我们看个例子。假设三个作业 A、B、C 同时到达系统，各自想运行 5 秒。SJF 调度器会把每个作业跑完才运行下一个（图 7.6）。相比之下，时间片为 1 秒的 RR 会快速地轮流切换（图 7.7）。

| 作业 | 时间线 | 响应时间 | 完成时间 |
|---|---|---|---|
| A | 0–5 | 0 | 5 |
| B | 5–10 | 5 | 10 |
| C | 10–15 | 10 | 15 |

*图 7.6：又是 SJF（对响应时间不利）。*

| 时间 | 运行 | 时间 | 运行 | 时间 | 运行 |
|---|---|---|---|---|---|
| 0 | A | 5 | B | 10 | C |
| 1 | B | 6 | C | 11 | A |
| 2 | C | 7 | A | 12 | B |
| 3 | A | 8 | B | 13 | C |
| 4 | B | 9 | C | 14 | A |

*图 7.7：轮转（对响应时间有利）。*

RR 的平均响应时间是：$\frac{0+1+2}{3}=1$；SJF 的平均响应时间则是：$\frac{0+5+10}{3}=5$。

可以看到，时间片长度对 RR 至关重要。时间片越短，RR 在响应时间指标下表现越好。但把时间片设得太短也有问题：上下文切换的开销会一下子盖过整体性能。于是，决定时间片长度就成了系统设计者面临的一个权衡——既要长到能摊销切换开销，又不能长到系统失去响应性。

!!! tip "提示：摊销能降低成本"
    当某个操作有固定开销时，系统中常用**摊销(amortization)** 这项通用技术：通过降低该操作发生的频率（也就是少做几次），系统的总成本就降下来了。例如，时间片设为 10 ms、上下文切换开销为 1 ms，那么大约 10% 的时间花在上下文切换上，白白浪费掉。想摊薄这笔开销，可以把时间片加大，比如加到 100 ms；这样花在上下文切换上的时间不到 1%，时间切片的成本就被摊销掉了。

    注意，上下文切换的成本并不只是操作系统保存、恢复几个寄存器那些动作。程序运行时，会在 CPU 缓存、TLB、分支预测器以及其他片上硬件中积累大量状态。切换到另一个作业会让这些状态被清掉，再引入与当前运行作业相关的新状态，这可能带来不容忽视的性能成本 [MB91]。

时间片设置合理时，如果响应时间是唯一指标，RR 是极好的调度器。可我们那位老朋友周转时间又怎么样呢？再看上面那个例子：A、B、C 各运行 5 秒，同时到达，RR 的时间片是（较长的）1 秒。从上图可以看到，A 在 13 完成，B 在 14，C 在 15，平均 14。相当难看！所以毫不奇怪，如果以周转时间为指标，RR 其实是最差的策略之一。直觉上也讲得通：RR 所做的是把每个作业尽量拖长——每个都只跑一小会儿就换下一个。因为周转时间只关心作业何时完成，RR 近乎最劣，很多情况下甚至比简单的 FIFO 还差。

更一般地说，任何公平的策略（比如 RR），也就是在小时间尺度上把 CPU 均匀分给活跃进程的策略，在周转时间这类指标上都会表现很差。这确实是一种固有的权衡：如果你愿意不公平，就能把较短的作业跑完，代价是响应时间；如果你看重公平，响应时间就低，代价是周转时间。这类权衡在系统里很常见；你没法既拥有蛋糕又吃掉它。[^4]

我们已经开发出两类调度器。第一类（SJF、STCF）优化周转时间，但对响应时间不利。第二类（RR）优化响应时间，却对周转时间不利。而且，还剩两个假设有待放宽：假设 4（作业不做 I/O）和假设 5（每个作业的运行时长已知）。接下来就来处理它们。

[^4]: 这句谚语把人绕晕，因为它本应是 "You can't keep your cake and eat it too"（你不能留着蛋糕又把它吃掉——这不是明摆着的嘛？）。神奇的是，维基百科居然有这一条；更神奇的是，读起来还挺有意思 [W15]。就像意大利人说的：你没法 Avere la botte piena e la moglie ubriaca（又要酒桶满，又要老婆醉）。

!!! tip "提示：重叠能提高利用率"
    只要可能，就让各种操作重叠起来，以最大化系统利用率。重叠在很多领域都有用，包括做磁盘 I/O 或向远程机器发消息时；这两种情况下，先把操作发起、再切换到别的工作都是好主意，能提高系统的整体利用率和效率。

## 7.8 把 I/O 纳入考虑

首先放宽假设 4——当然，所有程序都会做 I/O。想象一个不要任何输入的程序：它每次都会产生同样的输出。想象一个没有输出的程序：它就是那句谚语里倒在森林中的树，没人看见，它跑没跑过都无所谓。当一个作业发起 I/O 请求时，调度器显然要作出决策，因为当前运行的作业在 I/O 期间不会用 CPU——它在阻塞等待 I/O 完成。如果 I/O 发给一块硬盘，进程可能被阻塞几毫秒甚至更久，取决于硬盘当前的 I/O 负载。因此，这时调度器大概应该在 CPU 上调度另一个作业。

I/O 完成时，调度器同样要作决策。那一刻会触发中断，操作系统运行起来，把发起 I/O 的进程从阻塞状态移回就绪状态。当然，它甚至可以决定此时就运行那个作业。操作系统该怎样对待每个作业呢？

要更好地理解这个问题，假设有两个作业 A 和 B，各需要 50 ms 的 CPU 时间。但有一个明显区别：A 运行 10 ms 后发出一个 I/O 请求（这里假设每次 I/O 耗时 10 ms），而 B 只是连续用 CPU 50 ms，不做任何 I/O。调度器先运行 A，之后运行 B（图 7.8）。

| 时间 | CPU | 磁盘 |
|---|---|---|
| 0–10 | A | |
| 10–20 | B | A 的 I/O |
| 20–30 | B | |
| 30–40 | B | |
| 40–50 | B | |
| 50–60 | B | |
| 60–70 | | |
| 70–80 | A | |
| 80–90 | B | A 的 I/O |

*图 7.8：资源利用不佳。*

假设我们要构建一个 STCF 调度器。它该如何考虑"A 被拆成 5 个 10 ms 的子作业，而 B 只是一个 50 ms 的 CPU 需求"这一事实？显然，单纯地跑完一个再跑下一个、完全不考虑 I/O，是毫无道理的。

一种常见做法，是把 A 的每个 10 ms 子作业都当作一个独立作业。于是系统启动时，它的选择就是：调度

| 时间 | CPU | 磁盘 |
|---|---|---|
| 0–10 | A | |
| 10–20 | B | A 的 I/O |
| 20–30 | A | |
| 30–40 | B | A 的 I/O |
| 40–50 | A | |
| 50–60 | B | A 的 I/O |
| 60–70 | A | |
| 70–80 | B | A 的 I/O |
| 80–90 | A | |
| 90–100 | B | A 的 I/O |

*图 7.9：重叠让资源利用更好。*

一个 10 ms 的 A，还是一个 50 ms 的 B。用 STCF，选择很明确：挑更短的那个，这里就是 A。接着，A 的第一个子作业完成后，只剩 B，于是 B 开始运行。然后 A 的新子作业被提交，它抢占 B、运行 10 ms。这样做就实现了重叠：一个进程在用 CPU 时，另一个进程的 I/O 正在等待完成，系统因此得到更好的利用（见图 7.9）。

!!! note "译注"
    图 7.8 和图 7.9 的原文是 CPU、磁盘两条并行时间轴，这里按时间顺序拆成表格以适配 Markdown，含义不变。

于是我们看到调度器可以怎样把 I/O 纳入考虑。通过把每个 CPU 突发当作一个作业，调度器确保那些"交互式"进程能被频繁运行。当这些交互式作业在做 I/O 时，其他 CPU 密集的作业在运行，从而更好地利用处理器。

## 7.9 不再有神谕

基本的 I/O 处理方式就位后，我们来到最后一个假设：调度器知道每个作业的长度。如前面所说，这大概是我们能作出的最糟的假设了。事实上，在一个通用操作系统（比如我们关心的那些）里，操作系统通常对每个作业的长度几乎一无所知。那么，怎样构建一种行为像 SJF/STCF、却无需这种先见之明的办法？进一步说，怎样把我们从 RR 调度器那里见到的思路吸收进来，让响应时间也相当好？

## 7.10 小结

我们介绍了调度背后的基本思想，并开发出两大类方法。第一类运行剩余最短的作业，因而优化周转时间；第二类在所有作业之间轮流切换，因而优化响应时间。两者各有所长，也都各有所短——唉，这就是系统中常见的一种固有权衡。我们还看到了怎样把 I/O 纳入这幅图景，但仍未解决操作系统最根本的无力之处：它看不透未来。很快我们就会看到如何克服这个问题：构建一个用最近的历史来预测未来的调度器。这个调度器叫做多级反馈队列，是下一章的主题。
